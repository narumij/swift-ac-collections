# OPS-215 reduced placement probe

Purpose: separate the effect of **code placement** from **data placement** for the loop
that regressed in the CI artifacts (NextPermutations `subscript sequential access (batched)`).

This is a **reduced probe**. It runs the exact machine code of the inner measured closure
(222 bytes, sha256 `181a43648561b4938f90c50b20e22bf26b682aca533d898fdf05ac506ed13a7e`,
identical in all six CI binaries of `Benchmarks/_Artifacts/PerformanceCI/benchmark-performance-results{, 2, 3}`)
called from C. It does not reproduce the Swift benchmark harness (Timer, outer closure,
GateKeeper lifetime, blackHole, validation). A result here is evidence about this
machine code on this CPU, not a full reproduction of the Swift measurement.

## What it does
- `probe_copies.S` holds 10 byte-identical copies of the closure. Each copy starts at
  `4096*k + pad`; the vector loop is at entry `+0x80`, so its address mod 64 equals `pad`.
  Pads: `0 8 16 24 32 40 48 56 32 48`. Pad 32 is the placement of the fast CI binaries,
  pad 48 that of the slow ones. The duplicated 32 and 48 are same-placement controls.
  The whole 222-byte function moves together; this is not a vector-loop-only experiment.
- **code sweep**: one fixed input buffer (buffer 0, 4096-aligned), all 10 copies.
- **data sweep**: two fixed copies (pad 32, pad 48), 9 input buffers at offsets
  `0 0 8 16 24 32 48 64 2048` from separate 4096-aligned allocations
  (two offset-0 buffers are the same-placement data control).
- Sizes 64, 256, 1024. `reps = elements_per_sample / size` is fixed per size for all
  placements, so the work does not depend on placement.
- Each round shuffles all tasks with a fixed-seed xorshift (re-runnable with `--seed`);
  warm-up rounds are recorded but flagged; `--max-seconds` caps total time.
- Every call's result is checked against `reps * n(n-1)/2` (wrapping), in the CSV `ok` column.

## Calling convention assumption
The closure is a Swift-convention function that only uses `rdi rsi rdx rcx r8 r9`,
assigned like System V: `reps, elements, count, gate object, generation, &result`.
It does not touch `r12/r13/r14`, uses only `rbp` on the stack, clobbers caller-saved
registers, and traps (`ud2`) if `reps < 0`, `count < 0` or `gate[+16] != generation`.
See the comment in `driver.c`.

## Files
| file | role |
| --- | --- |
| `extract_bytes.py` | extracts the 222 bytes from the CI `benchmark.asm` files, checks they are identical, writes `closure_bytes.inc` / `closure_bytes.h` |
| `gen_probe_asm.py` | generates `probe_copies.S` from `closure_bytes.inc` (run by `build.sh` into OUTDIR) |
| `closure_bytes.inc`, `closure_bytes.h` | generated by `extract_bytes.py`, checked in so the probe builds without the artifacts |
| `driver.c` | runs the tasks, checks bytes/placement of each copy at runtime, validates options, writes CSV |
| `verify_layout.py` | checks bytes and placement of each copy in `objdump -d` output (non-zero exit on mismatch) |
| `analyze.py` | medians/quartiles per placement, ratios, same-placement controls (non-zero exit on empty/invalid data) |
| `build.sh`, `run.sh` | build + verify; full run on native x86-64 Linux |

## Running (native x86-64 Linux only)
Requirements: bash, C compiler (`cc`), GNU binutils `objdump`, `python3`, `taskset`.
OUTDIR is required; use a location that git does not track, for example
`Benchmarks/_Artifacts/LoopLayout/<run-name>` from the repository root:
```sh
Benchmarks/Probes/LoopLayout/run.sh Benchmarks/_Artifacts/LoopLayout/local-$(date +%Y%m%d-%H%M%S)
```
Defaults: `SEED=20261102 ROUNDS=21 WARMUP=2 MAX_SECONDS=300 SIZES=64,256,1024
ELEMENTS_PER_SAMPLE=16777216`; `CPU` defaults to the lowest core in the process's
affinity mask. The driver rejects out-of-range options (sizes 1..2^20, rounds 1..1000,
warmup 0..100, max-seconds 1..3600, elements-per-sample 1..2^30).

Evidence in OUTDIR: `environment.txt` (CPU, kernel, compiler, affinity, governor, load),
`probe_copies.S`, `probe.objdump`, `verify_layout.txt`, `probe-meta.txt` (runtime
addresses of copies and buffers), `results.csv` (raw per-call times), `summary.md`.
`run.sh` refuses non-Linux / non-x86-64 hosts and hosts without `taskset`. Do not use
emulation for timing. A non-zero exit (verify mismatch, checksum failure, early stop by
`--max-seconds`, empty or incomplete CSV) means the run is not a result; partial output is
kept for inspection only.

## Reading the result
- Supports code-placement sensitivity: in the code sweep, time changes with loop mod32/mod64
  (e.g. pad 48/16 slower than pad 32/0) beyond the same-placement controls, while the data
  sweep stays within the same-placement data control.
- Points elsewhere: a data-offset effect in the data sweep, or no code effect (then factors
  removed by the reduction, or this CPU, matter). Not reproducing here does not refute the
  CI observation.
- A periodic pattern is supporting evidence, not proof of a CPU-internal mechanism.

## GitHub Actions
Run the **Loop Layout Probe** manual workflow (`loop-layout-probe.yml`) on the desired
branch. It does not run on push or pull requests and does not build the Swift package.
The job has a ten-minute limit, and the build/verification/measurement step has a
five-minute limit. Download `loop-layout-results` after either success or failure.
It includes the executable, generated assembly, disassembly, raw samples, summaries,
runtime addresses, CPU/compiler information, and the checked-out commit SHA.

The hosted runner's CPU model is not selected by this workflow. Compare results on
the recorded CPU, and do not equate a different CPU with the original EPYC result.
A green job means the probe completed its checks, not that a performance cause or
prevention has been established.
