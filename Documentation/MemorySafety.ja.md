# メモリ安全性の設計

[English](MemorySafety.md) | 日本語

本ライブラリの木は、検索・削除の実測では、`std::set` と同等の性能が出ています。この文書は、その性能が安全性の検査を省いた結果ではないことを説明します。

要点は、検査を置く場所です。木の内部には、もとから安全な範囲があります。そこには検査を足さず、C++ と同じ手順のまま動かします。前提が崩れうるのは、利用者の操作が入る場所だけです。検査はそこに集めています。

## 1. 素の赤黒木の強さと弱さ

本ライブラリの木は、LLVM libc++ の `__tree` をもとにしています。

この木の強さは、内部操作が閉じていることです。挿入、削除、回転、再彩色は、木の不変条件が成り立つ状態から始めれば、生きているノードだけに触れ、不変条件が成り立つ状態で終わります。正しい入力に対しては、既存のアルゴリズムだけで足り、メモリ違反は起きません。

弱さは、前提を外れた操作までは面倒を見ないことです。

- **範囲外への移動**: `end` から次へ、`begin` から前へ進むと、ヌルまたはノードでない領域を読みます。
- **無効になった位置**: 削除済みのノードを指すイテレータからの移動やアクセスは、解放済み領域を読みます。
- **別の木の位置**: 他の木のイテレータを渡しても、区別がつきません。

C++ ではこれらはすべて未定義動作で、防ぐ責任は利用者にあります。

## 2. 番兵がもたらすもの

本ライブラリでは、ヌルポインタの代わりに、実体のある番兵ノードを使います。葉の先など、本来ヌルが入る場所は、この番兵を指します。番兵は木をまたいで共通で、その left、right、parent はすべて番兵自身を指します。

根の親は、これとは別のノードです。木ごとに `end` ノードがあり、その left が根につながります。`end` の right と parent は番兵を指します。`end` は木の一部で、番兵は木の外縁です。

これにより、リンクを辿る操作が確保済み領域の中で閉じます。有効なノードから左、右、親のどれを何度辿っても、行き先は生きているノード、`end`、番兵のいずれかです。番兵のリンクをさらに辿っても、番兵に留まります。範囲外への移動は、違反ではなく、番兵への到達として現れます。

効果は2つあります。

- **範囲外への移動が、構造上、ヌルポインタ参照になりません。** 検査で防いでいるのではなく、ヌルを踏む経路がありません。
- **ヌル検査を移動の前に置く必要がありません。** 番兵に到達した後の検査で間に合うため、走査の途中の分岐が減ります。

番兵が守らないものもあります。番兵に値はないので、値の読み出しには別の検査が必要です。削除済みノードや別の木の位置は、番兵では区別できません。番兵が保証するのは「有効な位置から始めた移動」だけです。

## 3. Resultが覆う範囲

`Result` を使うのは、利用者の不正な操作が混じりうる経路だけです。

不正な操作が混じらない範囲では、`Result` を使いません。キーによる挿入・検索・削除の木内部は、通常のノードポインタで処理します。通常のイテレータによる走査は、終了位置と比較しながら進み、各移動を `Result` には包みません。これらは1節のとおり、既存のアルゴリズムだけで閉じています。木の内部では C++ と同じ手順を使い、各段階に位置の再検証や `Result` による失敗処理を追加する必要がありません。検査を省いたのではなく、検査が要らない範囲です。

利用者のインデックスを起点にするアクセスや移動は、事情が違います。`startIndex` から `index(after:)` を繰り返す走査も、こちらに入ります。位置が失効していたり、移動が範囲を越えたりするためです。範囲を越える移動については、番兵が失敗を「違反」から「到達可能な状態」に変えます。位置の失効は、解決の段階で失敗として検出します。これらの失敗を取りこぼさず呼び出し元まで運ぶのが `Result` です。

この経路では、移動や解決の操作は、ノードそのものではなく、成功か失敗かを含む値を返します。ポインタを直接返す設計では、失敗は「特別なポインタ値」になり、呼び出し側が検査を忘れれば、そのまま次の操作に使えてしまいます。`Result` では、成功と失敗のどちらを扱っているかが、コード上で明示されます。

操作をつなぐときは `flatMap` を使います。途中で失敗すれば、その後の処理は実行されず、失敗がそのまま末尾まで届きます。失敗した位置を起点に、さらに移動やアクセスを重ねることがありません。

失敗が値として残るので、公開APIはそれを `nil`、`false`、空のビュー、トラップのどれに変えるかを、API ごとに選べます。

`Result` が保証するのは、失敗の扱いが明示されることまでです。成功の中に入るポインタが正しいことは、型では保証されません。それを担うのは、成功を作る側の検査と、次節の境界です。

## 4. 境界で守るもの

2節と3節の保証には、「有効な位置から始める」という前提があります。その前提を成り立たせるのが、公開APIの境界です。

**内側から外側へ: ヌルを漏らさない。** 番兵を指す位置は、公開インデックスとして外に出ません。利用者が受け取るのは、要素を指すインデックス、`endIndex`、`nil` のいずれかです。外に出た時点では、インデックスは必ず有効な位置を指しています。

**外側から内側へ: 戻ってきた位置を確かめる。** 受け取った時点で有効だったインデックスも、その後の削除などで失効します。外に出たものは、出たときのまま戻ってくるとは限りません。このため、利用者が渡すインデックスは、内部に入る前に、現在の木で利用できる位置へ解決し、要素の存在や世代を確認します。確認できないものは通常の内部操作へ通さず、有効な位置を要求するAPIではトラップします。この検証も、確保済み領域だけを読みます。

出るときに有効であることを保証し、戻るときに今も有効であることを確かめる。この2つで、内部操作に入る位置は常に有効になります。

守っているのは、内部の不変条件です。境界の内側では、位置が有効であることを前提にでき、内部操作で同じ検査を繰り返さずに済みます。安全性の検査を境界に集め、内側は構造上安全に保つ、という分担です。性能と安全性を引き換えにしていないのは、この分担によります。

## まとめ

| 層 | 対象 | 手段 |
| --- | --- | --- |
| 木のアルゴリズム | 不正が混じらない内部操作 | 不変条件の維持。`Result` なしで C++ と同じ手順 |
| 番兵 | 範囲外への移動 | ヌルを踏む経路をなくす |
| `Result` | 利用者のインデックスを起点にする操作 | 失敗を値として運び、`flatMap` で止める |
| 公開APIの境界 | 無効な位置の流出と流入 | 出るときに保証し、戻るときに確かめる |

木の内部がもともと持つ安全性を保ち、前提が崩れうる経路を残りの3層で補っています。この分担が、安全性と速さの両立を支えています。
