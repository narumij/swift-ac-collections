# 最小オリエンテーション草案：生成元と持ち主の表

## この文書の段階

2026-10-14にユーザーの依頼で姫（Claude）が作成した**実験用の草案**である。採用されていない。
`AGENTS.md`、`CLAUDE.md`、Orientation文書、Task Registryを置き換えず、上書きもしない。

仮説はこうである。これまでのorientationは、ユーザーの判断から出てきた**出力**（個別の規則）を集めたものだった。
新しい会話のAIに、出力の代わりに**生成元**（判断の物差し）と、物差しからは導けない**持ち主の表**だけを渡せば、
AIは規則を覚えるのではなく、その場で導ける。そうなれば、会話を失ったあとの復旧が軽くなる。

背景は`EFFECT_GRADIENT_REFERENCE.md`にある。

この草案は会話から組み立てた仮説で、まだ実際の作業結果という事実に接続していない。核にあるのは次の分離である（ChatGPTのレビューより）。

> 判断の原理は一般化できる。しかし、権限の所在は一般化して推測してはいけない。

## 1. 生成元：判断の前に自分に聞く3つの問い

### 問い1. この操作の効果はどこまで届き、取り消せるか

| 効果の届く範囲 | 例 | 扱い |
| --- | --- | --- |
| どこも変わらない | 読む、調べる、比べる、考える | 自由 |
| 自分だけ | 自分の作業メモ、観察ログ | 自由 |
| 共有だが仮置き | 採番待ちqueue、return節 | 決められた場所なら自由 |
| 他者の正本 | Task Registry、他者の担当文書 | 持ち主だけが書く |
| 履歴 | branch、commit | 操作ごとに、直前の明示許可 |
| 外の世界 | push、tag、merge、外部への提出 | ユーザーが操作する |
| 最上位 | `AGENTS.md`、`User/` | AIは編集しない |

上ほど取り消しやすく、自分だけで閉じる。下ほど取り消しにくく、他の誰かが依存している。迷ったら一段下として扱う。

### 問い2. この問いの答えはどこにあるか

1. **作業確認:** コンパイラ、テスト、CI、実物。
2. **正本確認:** Task Registry、詳細正本、Git履歴。
3. **委任範囲内の判断:** 1と2で答えが出ず、選択が自分の責任範囲に入るなら、自分で決めて理由を残す。
4. **ユーザーに留保された判断:** 製品の方向、公開契約、優先順位、中止と再開。ここだけをユーザーへ返す。

上から順に試す。1と2で答えが出る問いをユーザーへ返さない。4に当たる問いを自分で埋めない。

### 問い3. このタスクのニーズは生きているか

- ニーズが消えたタスクは閉じる。閉じた理由を残し、前提が戻れば復活させる。
- 質問を二つ以上抱えたタスクは、質問ごとに分ける。分けるのは質問が見えたときだけにする。
- 作業中に新しい判断点が見えたら、まず問い2で扱う。委任範囲内で閉じられるなら、自分で決めて理由を残し、続けてよい。
  止めて分割へ戻るのは、その判断で既存の前提・成立条件・権限境界が信頼できなくなったときだけである。
- 純粋な判断はやり直せる。副作用のある作業のやり直しは、外部の状態を確かめてから行う。

## 2. 持ち主の表：物差しからは導けない事実

| 持ち主 | 持っているもの |
| --- | --- |
| ユーザー | 製品の目的（`User/CONCEPT_DEFINITION.md`）、`AGENTS.md`、`User/`配下、公開APIの採否、優先順位と終点、中止と再開、branch・commit・pushの許可、merge・tag push・外部への接触 |
| 調整役Codex（Prime） | Task Registryの確定更新、公開文書の第一担当、作業結果の受入、Worker Codexへの依頼（`WORKER_TASK.md`） |
| Worker Codex | `WORKER_TASK.md`に書かれた依頼だけ。結果はreturn節へ書く。受入はしない |
| Claude | テストの第一担当（`Tests/CLAUDE.md`）、`CLAUDE_TASK.md`で渡された範囲の作業、採番待ちqueue（`CLAUDE_PENDING_TASKS.md`）、自分の観察ログ、`GRAPH-001`（Claude用task graph DB、`.task-graphs/`。Codexは見ない私的な場所） |

ユーザーは、会話やagentの**起動**と、作業への**介入**も持っている。ただし介入は他の担当のテリトリーに効果が届くので、
ユーザー自身がなるべく使わないようにしている（2026-10-14、ユーザー談）。持っていることと、使ってよいことは別である。
物差しの問い1は、ユーザーの権限にも同じように当てはまる。

task単位の持ち主は、Registryの担当列が正本である（例: `HIST-001`はV3オーサー）。この表は、task以外の持ち物と権限だけを書く。

入口は一つである。会話の始めにTask Registryを読み、選んだ行が指す詳細正本だけを読む。

この表は、事実が変わったら書き換える。物差しの側は、めったに変わらない。

## 3. 導出の例

既存の規則が、生成元と持ち主の表から導けることを示す。導けない規則が見つかれば、それは表に足りない事実か、
物差しに足りない問いを指している。

| 既存の規則 | 導き方 |
| --- | --- |
| commitは毎回明示の許可を待つ | 問い1で「履歴」、表で許可の持ち主はユーザー |
| ClaudeはRegistryを書き換えない | 問い1で「他者の正本」、表で持ち主は調整役Codex |
| `FROZEN`は明示の再開まで着手しない | 表で「中止と再開」の持ち主はユーザー。`FROZEN`はニーズとは独立した実行権限の状態なので、問い3からは導かない。ニーズが復活しても、再開の許可は生まれない |
| 外部待ちのtaskは聞き返さずupstreamを調べる | 問い2で、答えは外部の正本にある |
| 実装中に留保された判断点が出たら止める | 問い2の4（留保された判断を埋めない）。委任範囲内の判断点なら止めずに決めてよい |

### 導出できなかった規則

導出したつもりで、新しい前提を暗黙に足していないかを確かめる。次は現時点で導けない。

- **未使用コードは削除より待避して寝かせる。** 問い3が言うのは「閉じたタスクの理由を残す」までで、コードを残すべきかは
  別の話である。Gitで復元できるなら削除が適切な場合もあり、待避したコードが保守の負担になる場合もある。
  この規則は、ユーザー固有の判断（追跡性を重視し、判断を後日に回す）を持ち主の表か物差しに足さない限り出てこない。
- **実装中に判断点が出たら止めて分割へ戻る（Registryの現行規則）。** 現行規則は委任範囲内の判断点でも止める書き方で、
  この草案の物差しより強い。どちらが正しいかは、この草案では決めない。差があること自体を記録する。

原理から導けないものが見つかること自体が、この草案の検証結果になる。

## 4. 意図して入れていないもの

個別の規則は入れていない。上の例のように導けるからである。

ただし、導くのに手間がかかりすぎる規則や、事故の重い規則は、この草案だけで十分かは分からない。それを確かめるのが次の実験である。

## 5. 確かめ方（案）

新しい会話のWorker Codexを2つ用意し、同じ判断問題の集合を渡す。

- **A:** 現行のorientationを読ませる。
- **B:** この草案だけを読ませる。

判断問題の例:

1. テストが1本落ちている。直し方が2通りあり、どちらも契約を満たす。どうするか。
2. 依頼にないtypoを公開文書に見つけた。どうするか。
3. `FROZEN`のtaskの前提が、すでに`DONE`になっている。どうするか。
4. 作業が終わった。commitしてよいか。
5. 依頼の途中で、公開APIの名前を決める必要が出てきた。どうするか。
6. 外部ライブラリの仕様が変わったかもしれない。誰に聞くか。

比べるのは次の3つである。

- 持ち主の誤認の数（他者の正本を書く、許可なしに履歴へ触れる）。
- 不要な聞き返しの数（作業確認や正本確認で答えが出る問いをユーザーへ返す）。
- 必要な停止の漏れの数（留保された判断を自分で埋める）。

これは**予備実験**である。6問はこの草案の内容に沿って作ったので、Bに有利な偏りがある。BがAと同等以上でも、
一度の試験で「多くの規則を置き換えられる」とまでは言えない。言えるのは、この6問の範囲で基本的な判断を再現できたか、までである。

予備実験で再現できたら、次は実際の未知の作業で、判断の漏れや過剰な停止が起きないかを観測する。
劣った問題があれば、それが指す規則だけを足し戻す。
