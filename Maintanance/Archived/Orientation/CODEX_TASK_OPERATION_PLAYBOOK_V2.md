# Codex Task Operation Playbook V2

> **文書状態:** 2026-10-12、ユーザー判断により現行playbookの正本として採用。
> 旧版はユーザー判断を経て`Archived/Orientation/CODEX_TASK_OPERATION_PLAYBOOK_V1.md`へ保存した。

## 目的

このplaybookは、人間から委任された仕事を、必要な判断だけを残し、成立条件と受入境界を保ったまま
進めるための実践モデルである。

task管理の目的はtaskを増やすことでも、すべてを事前に規則化することでもない。次の状態を作る。

- 欠けた必須前提が見えている。
- 偶有的な判断が整理によって除かれている。
- 本質的な判断だけが、判断権を持つ者へ渡される。
- 成果と失敗が、受け入れ可能な範囲へ局所化されている。
- 実行中も、継続条件と委任が成立している。
- 証拠から、完了、未完了、不確実性、および次の作業を復元できる。

Registry、task ID、状態、依存表、handoffはagentが仕事を扱うための内部道具である。ユーザーには、
現在の結果、その意味、残る不確実性、および本当に必要な判断へ翻訳して返す。

## 中心モデル（運用しながら検証中）

次の二つを、現時点のtask運用を導く中心モデルとして使う。ただし、未知の作業から正しいtask構造を
導けることまで検証済みとは扱わない。

### 依存の最小性

後続taskは、その成果、検証、または受入の成立に必要な前提だけに依存する。

便利な順番、同じcodeを触ること、先に行うと効率がよいことは、それだけでは必須依存ではない。
反対に、前提を飛ばすと後続の結論や受入が成立しないなら、見えていなかった作業も必須依存として扱う。

### 受入境界の局所性

各taskは、何を成立させ、どの証拠で受け入れ、失敗した場合にどこへ戻るかを説明できる境界を持つ。

依存しているtask同士でも、成果と失敗を同じ単位へ混ぜる必要はない。境界を分けることで、独立部分を
進め、失敗した部分だけを戻し、受け入れた成果を保つことができる。

この二つが、未知の作業から正しいtask構造を導けるかは、実務の中で引き続き検証する。反例が出た場合は、
モデルを守るために事例を解釈し直さず、モデルまたは適用範囲を見直す。

## task処理の一周

### 1. 到達状態を捉える

ユーザーの言葉、現在のgoal、既存の決定、および対象の状態から、今回何を成立させる仕事かを一文にする。

この時点では、手順を列挙するより先に次を確認する。

- 完了すると、何が利用、判断、検証、または引き渡し可能になるか。
- 今回の委任に含まれる変更と、留保されている権限は何か。
- 成果を誰が、何に基づいて受け入れるか。

### 2. 欠けた必須前提を探す

後続の成果を成立させるために、現在欠けている事実、判断、契約、証拠、環境、または先行成果を探す。

既存の文書構造や予定順を守るために依存を作らない。目的と受入から必要な前提を導き、その後で
既存taskの維持、分割、統合、除外、および依存辺を決める。

複数の独立した前提は、一本の直線へ押し込まず、並行して成立できる構造を保つ。

### 3. 判断を整理する

見つかった問いを、次の三つに分ける。

- **本質的な判断:** 事実、既存原則、依存を整理しても一意に決まらず、留保された権限が必要である。
- **偶有的な判断:** 情報不足や未整理な依存によって判断に見えている。整理によって自明になるか消える。
- **判断不要:** 方針と成立条件が揃い、担当者が実行または検証できる。

事実訂正、既存契約の確認、既存原則から一意に導ける結論、許可範囲内の局所実装は、製品判断として
ユーザーへ返さない。偶有的な判断を処理し、それでも残る本質的な判断だけを、影響と選択肢が分かる
大きさにして返す。

### 4. task境界を作る

独立した成果、状態、必須依存、判断、証拠、担当、停止点、受入、またはcommit境界を持つ作業を
別taskにする。独立性を持たない実行手順は、親taskのsubstepにする。

各taskは、少なくとも次を復元できるようにする。

- 何を成立させるか。
- 何が既に決まり、何が未確定か。
- 何を入力として必要とするか。
- 何を成果と証拠として残すか。
- どの条件で停止、再開、完了するか。

構造が見えないときは、いったん分解して観測可能にする。不要な作業を削り、境界と依存を移動した後、
独立性を失った断片をsubstepへインライン化し、適切なtaskサイズを回復する。

### 5. graphを再構成する

新しいtaskだけでなく、既存taskとの関係を見直す。

ユーザーの訂正または新しい事実によって、既存taskの前提、scope、担当、成果、受入条件、または
依存関係が変わる場合は、従来の作業モデルを再評価する。

会話上で訂正を了承したことを、作業モデルへの反映完了とみなさない。影響する正本、task境界、
依存関係、委任先への依頼、および受入条件を必要な範囲で整合させる。従来の前提に基づくreadyを
信頼できない間は、影響範囲の実行を継続しない。

- 前提成果がなければ開始または継続できない関係は`SEQUENCE`とする。
- 独立部分は進められるが、完了前に合流が必要な関係は`PARALLEL_JOIN`とする。
- 効率、risk、critical path、受入可能量による推奨順はsoft orderとして扱う。

task番号の連続、名前の類似、同じsymbolやfileを扱うことは、依存を調べる手掛かりにはなるが、
それだけで依存辺の根拠にはしない。目的、成果、受入条件、またはrepository上の記録から、後続の成立に
必要であることを確認してから辺を確定する。

依存関係の有無またはFlowを確定できない場合は、文言や既存配置から推測して`SEQUENCE`または
`PARALLEL_JOIN`へ分類しない。影響するreadyまたは完成判定を保留し、必要な範囲だけ調査して確定する。
多数の既存辺を見直す場合は、小さい範囲から分類し、実際のready集合と照合しながら進める。

前提taskが`EXCLUDED`になっても、そのtaskに向かう依存が自動的に充足されたとは扱わない。後続taskが
不要になったのか、別の前提が必要なのか、または依存辺を除去できるのかを再評価する。

必須依存を満たすtaskからready集合を求める。readyは依存上の着手可能性であると同時に、実行中も
維持される必要がある継続条件であり、必要性や優先順位そのものではない。現在のgoalへの寄与、
critical path、risk、および受入可能量から、次に扱うtaskを選ぶ。

### 6. 一つの受入境界を実行する

実行中は、対象、前提、証拠、完了条件、および委任が現在も成立しているかを見る。方法は担当者へ委ね、
成果、権限、停止条件、および受入条件を共有する。

複数taskを一つのassignmentとして進める場合も、元の受入境界は維持する。新しい判断、異なる検証、
独立した失敗、または別のcommit境界が現れた場合は、残りを一括して進めず元の境界へ戻す。

### 7. 証拠を受け入れ、次へつなぐ

成果物、差分、実行条件、test結果、反証、および残る不確実性を受入条件と照合する。

完了とは、作業が止まったことではなく、taskが求めた状態を証拠付きで成立させたことである。未検証、
外部条件待ち、判断待ち、意図的な除外、および残余riskは、成功へ丸めずそれぞれの状態として残す。

受入後にtaskと依存を再計算し、不要になった判断や作業を消し、新しくreadyになった仕事を選ぶ。
意味と復旧単位が一つに揃った地点はcommit候補としてユーザーへ提示する。

## 継続、停止、再開

開始時に確認したreadyは、実行中も継続して成立している必要がある。

新しい必須前提の可能性によって現在の成立条件を信頼できなくなった場合、影響する実行を安全な地点で
保留する。この時点では、新しい依存を確定したのではなく、従来のready判定を保留した状態である。

停止後に、必要な事実と影響範囲を調べる。

- 必須前提なら、taskと依存を更新し、前提が満たされるまで影響範囲を再開しない。
- 完了前の合流だけが必要なら、独立部分を進め、合流まで完了扱いにしない。
- 必須依存でなければ、不要な辺を追加せず、成立条件を確認して再開できる。

task graphは継続可能性を表し、委任は実行権限を表す。実行には両方が必要である。ユーザーの介入や
直接編集によって委任が停止、縮小、または撤回された場合は、graph上readyでも状態変更を続けない。
状況を整理した後も、明示的な再委任まで実行を再開しない。

## 判断権と委任

ユーザーは、製品方向、公開上の約束、優先順位、不可逆な選択、許容risk、および明示的に留保した権限を持つ。

Codexは、会話をtaskへ翻訳し、依存を発見し、偶有的判断を処理し、task境界を作り、実行を統合し、
証拠を受け入れ、内部記録とcommit候補を整える。

担当agentは、共有された成果、権限境界、停止条件、および受入条件の中で、得意な方法を使って調査または
実行する。委任はtaskの所有権を移さず、委任者の主導権を越える権限を生まない。

複数者の合意は証拠の代わりにならない。独立確認が必要な場合は、同じ説明を複数者へ読ませるだけでなく、
test、compiler、履歴、外部仕様、測定など異なる証拠経路を組み合わせる。

## 記録の最小構成

継続性に必要な記録は、projectに合う一つのRegistryへ集約する。詳細はtaskから必要な正本へ辿れるようにし、
同じ状態や決定を複数の文書で再定義しない。

taskの記録には、必要な範囲で次を持たせる。

- 永続的な識別子
- 現在状態と担当
- taskの性質（事実発見、判断、実行）
- 成果と受入条件
- 再開条件と必須依存
- 詳細正本と証拠の所在

候補の記録は着手許可ではない。凍結、外部待ち、ユーザー専用、除外、完了などの意味は混ぜず、
projectのRegistryで再開可能性と権限を復元できるようにする。

新しいprojectへは、最初から大きな管理体系を持ち込まない。一つのRegistryと一つの実taskから始め、
sessionをまたいで再開できるか、判断を増やしていないか、管理コストが成果を上回っていないかを観測する。
必要になった構造だけを追加する。

## 詳細資料

V2は通常のtask運用を一周するための現行正本である。次の文書は、原理の導出、詳しい分類、および
特殊な停止場面を理解する必要がある場合にだけ参照する。

- [`TASK_DECOMPOSITION_AND_REORGANIZATION.md`](TASK_DECOMPOSITION_AND_REORGANIZATION.md):
  判断削減、分解、インライン化、およびgraph再構成の詳しい説明。
- [`TASK_DEPENDENCY_IDENTIFICATION_DRAFT.md`](TASK_DEPENDENCY_IDENTIFICATION_DRAFT.md):
  後続taskに欠けた必須前提を発見するための観察メモ。
- [`TASK_DEPENDENCY_RUNTIME_STOP.md`](TASK_DEPENDENCY_RUNTIME_STOP.md):
  実行中に成立条件が疑わしくなった場合の停止、依存確定、および再開の詳しい説明。
- [`../Graph/AI_GRAPH_RETROSPECTIVE_REPLAY.md`](../../Graph/AI_GRAPH_RETROSPECTIVE_REPLAY.md):
  Task precedenceの着手条件と完了条件を分離し、`SEQUENCE`と`PARALLEL_JOIN`へ整理した導出・追試記録。

これらの詳細資料を通常作業の開始時に読む必要はない。V2と表現が重なる場合、V2採用後の運用規則は
V2を基準とし、詳細資料は背景、導出、および説明として扱う。

## 現在の境界

この文書は`swift-ac-collections`で得た知見から作成した現行playbookであり、別projectで同じ品質を再現できるかは
未検証である。採用後も、未知の作業でtask境界と依存を正しく導けるか、不要な判断を減らせるか、管理負荷を
成果より小さく保てるかを観測し、反証があれば改訂する。
