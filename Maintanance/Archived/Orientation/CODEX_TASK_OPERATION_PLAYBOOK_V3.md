# Codex Task Operation Playbook V3

> **文書状態:** 2026-10-12、ユーザー判断により現行playbookの正本として採用。
> 旧版は`Archived/Orientation/CODEX_TASK_OPERATION_PLAYBOOK_V2.md`へ保存した。

## 目的

このplaybookは、人間から委任された仕事について、Codexが向き合うべき事実へ接続し、成果の受入から
次の仕事の成立までを自律的につなぎ、協働を継続できるようにするための実践モデルである。

目標は、Registryを維持することでも、taskを増やすことでも、すべてを事前に規則化することでもない。
次の状態を作る。

- 現在地、成立済みの成果、欠けた前提、および証拠の所在を復元できる。
- 調べれば閉じる問いを調べ、本質的な判断だけを判断権者へ渡せる。
- 一つの成果を受け入れた後、依存を再計算し、次に成立させる仕事を導ける。
- 適切な担当者へ、判断不要で受入可能な境界を渡せる。
- 失敗や反証を局所化し、受け入れ済みの成果を保ったまま戻れる。
- 会話、session、担当者が変わっても、同じ仕事の景色へ戻れる。

## 成立背景

Git履歴で確認できる最初の作業面は、テスト整理の規則と`Current handoff`だった。そこへユーザー要望、
優先事項、停止条件、保留、完了、担当、および分野別dashboardが加わり、後にID、状態、詳細正本、依存へ
形式化された。

現時点で見える進化の骨格は次のとおりである。

> handoffを残す
> → 要望と停止を区別する
> → 現在地と履歴を分ける
> → 分野別作業面を横断する
> → ID・状態・依存として形式化する

作者の説明によれば、この構造はAIを細かく統制するために先に設計されたものではない。放任と助言の中で、
Codexが仕事を引き継ぎ、自分で次へ進みやすくするために育った。`Routine shorthand`は、その実務で成立して
いた一周を短い指示で呼び出すことを目標としていた。

履歴上の事実と作者の意図は、同じ証拠として混ぜない。成立史の継続調査は
`TASK_REGISTRY_STATE_HISTORY.md`を参照する。

## Task Registryの役割

Task Registryはtodo listでも、仕事そのものでも、判断の正しさを保証する装置でもない。協働に必要な
現在地と成立条件から、詳細正本、証拠、依存、担当、および判断権者へ到達するための索引である。

Registryには、必要な範囲で次を持たせる。

- 永続的なtask ID。
- 現在状態と担当。
- 何を成立させるtaskか。
- 再開または完了の条件。
- 詳細正本と証拠の所在。
- 後続の成立に必要な依存関係。

Registryの行だけでtaskの意味を完結させない。長文の契約、判断理由、反証、および検証結果は詳細正本へ
置き、Registryから辿れるようにする。反対に、詳細正本だけを読ませて現在の状態や実行権限を推測させない。

Registryを更新することは目的ではない。更新、圧縮、アーカイブ、または依存辺の削除を行う場合は、変更後も
次を復元できることを確かめる。

- **現在地:** 何が進行中で、何が止まっているか。
- **必須前提:** なぜtaskが実行可能または不可能なのか。
- **証拠への経路:** 何が受け入れられ、過去の判断、反証、および失敗へどこから辿れるか。
- **判断・実行権限:** 誰が判断でき、誰が実行できるか。
- **次に必要な仕事:** 受入後に何を成立させる必要があるか。

行数や辺数が減ったことだけを成功としない。履歴が保存されていても、次の仕事を成立させるための索引が
失われたなら圧縮は失敗である。

Registryは協働の索引であり、Routineはその索引から受入後の次の仕事までの一周を呼び出す
インターフェースである。

## 答えの所在を先に捉える

もっともらしい説明や参加者間の合意を、確認済みの答えとして扱わない。問いごとに、何が答えを持つか、
どの証拠で確かめられるかを分ける。

- repository、Git履歴、実行結果が持つ答えは、実物を調べる。
- compiler、test、benchmark、sanitizerが持つ答えは、条件を明示して実行する。
- 外部仕様が持つ答えは、該当する一次資料へ接続する。
- 作者または権限者だけが持つ意図、方向、許容riskは、その者へ返す。
- 誰もまだ持たない答えは、確定事項へせず仮説または判断taskとして残す。

一つの問いに複数の答えの所在がある場合は分解する。Git履歴は何が起きたかを示せても、作者の意図を
単独では確定しない。作者の記憶は意図を説明できても、実際に生じた差分や実行結果の代わりにはならない。

事実、解釈、提案、および判断を区別する。事実から妥当な説明を作れても、推論部分を確認済みの歴史や
契約として語らない。

## 中心モデル（運用しながら検証中）

### 依存の最小性

後続taskは、その成果、検証、または受入の成立に必要な前提だけに依存する。

便利な順番、同じcodeを触ること、名前の類似、先に行うと効率がよいことは、それだけでは必須依存では
ない。前提を飛ばすと後続の結論や受入が成立しない場合だけ、必須依存として扱う。

### 受入境界の局所性

各taskは、何を成立させ、どの証拠で受け入れ、失敗した場合にどこへ戻るかを説明できる境界を持つ。

依存するtask同士でも、成果と失敗を同じ単位へ混ぜない。境界を分けることで、独立部分を進め、失敗した
部分だけを戻し、受け入れた成果を保つ。

この二原則は実務で使いながら検証する。原則を守るために反例を解釈し直さず、原則または適用範囲を
見直す。

## 協働を進める一周

この一周は必須の逐次チェックリストではない。現在の仕事に必要な活動だけを行い、前提が変わった場合は
必要な地点へ戻る。

### 1. 現在地と到達状態を復元する

ユーザーの最新指示、現在の中間ゴール、Task Registry、および選択したtaskの詳細正本から、今回何を
成立させる仕事かを一文にする。

完了すると何が利用、判断、検証、または引き渡し可能になるか、今回の委任に含まれる変更は何か、成果を
誰が何に基づいて受け入れるかを確認する。

### 2. 答えの所在を捉える

問いごとに、repository、Git履歴、実行結果、compiler、test、benchmark、外部の一次資料、作者、または
権限者のうち、誰または何が答えを持つかを特定する。複数の所在が異なる部分を答える場合は、問いを
確かめられる単位へ分解する。

答えを持つものへ接続すれば閉じる問いを、ユーザー判断へ送らない。必要な証拠へ到達できない場合や、
誰もまだ答えを持たない場合は、不足を残したまま結論を作らず、仮説または未確定事項として保つ。

### 3. 欠けた必須前提を探す

後続の成果に必要な事実、判断、契約、証拠、環境、または先行成果を探す。既存文書の構造や予定順を
守るために依存を作らない。目的と受入から必要な前提を導く。

飛ばしても後続の成果、検証、および受入が成立するものを、必須依存にしない。現在の成立条件に疑義が
生じた場合は、graphの更新を待たずに影響範囲を保留する。

### 4. 判断を整理する

見つかった問いを三つに分ける。

- **本質的な判断:** 事実、既存原則、依存を整理しても一意に決まらず、留保された権限が必要である。
- **偶有的な判断:** 情報不足や未整理な依存によって判断に見える。調査と整理により自明になるか消える。
- **判断不要:** 方針と成立条件が揃い、担当者が実行または検証できる。

本質的な判断だけを、影響、選択肢、および判断後に成立する仕事が分かる大きさにして返す。

### 5. task境界とgraphを再構成する

独立した成果、必須依存、判断、証拠、担当、停止点、受入、またはcommit境界を持つ作業を別taskにする。
独立性を持たない実行手順はsubstepにする。

構造が見えないときは分解して観測可能にする。不要な作業を削り、境界と依存を移動した後、独立性を
失った断片をインライン化して適切な大きさを回復する。

- 前提成果がなければ開始または継続できない関係は`SEQUENCE`とする。
- 独立部分は進められるが、完了前に合流が必要な関係は`PARALLEL_JOIN`とする。
- 効率、risk、critical path、受入可能量による推奨順はsoft orderとする。

依存を確定できない場合は推測で辺を埋めず、影響するreadyまたは完成判定を保留して必要な事実を調べる。
前提taskが`EXCLUDED`になっても、前提条件が自動的に充足したとは扱わない。

#### 次の受入境界を選ぶ

必須依存からready集合を求める。readyは着手可能性であると同時に、実行中も維持する継続条件である。
必要性や優先順位そのものではない。

現在の中間ゴールへの寄与、critical path、risk、受入可能量、および担当適性から次を選ぶ。単にready、
興味深い、または有用という理由で、遠い仕事へ逸れない。

### 6. 実行または委譲する

一つの受入境界を実行する。別の担当者へ渡す場合は、成果、前提、権限、停止条件、証拠、および受入条件を
共有し、方法は担当者へ委ねる。

複数taskを一つのassignmentとして渡しても、元の受入境界は維持する。新しい判断、異なる検証、独立した
失敗、または別のcommit境界が現れた場合は、一括して進めず元のtaskへ戻す。

### 7. 証拠を受け入れる

成果物、差分、実行条件、test結果、反証、および残る不確実性を受入条件と照合する。

完了とは、作業が止まったことでも、担当者が完了と報告したことでもない。taskが求めた状態を証拠付きで
成立させたことである。未検証、外部条件待ち、判断待ち、意図的な除外、および残余riskを成功へ丸めない。

### 8. 受入結果から次の仕事を成立させる

受入後にRegistryと詳細正本を整合させ、taskと依存を再計算する。成立した前提によって不要になった判断や
作業を消し、新しくreadyになった仕事を選ぶ。必要ならtaskを分解、統合、除外、またはインライン化する。

判断不要で受入可能な仕事があり、担当と委任が成立するなら、次の担当者へ渡す。適切な仕事がなければ、
割当を作るためだけにtaskを製造しない。本質的な判断または新しい権限が必要な地点では、結果、意味、
残る不確実性、および必要な判断だけをユーザーへ返す。

この段階まで進めることで、一回の成果を孤立した完了報告で終わらせず、次の協働へ接続する。

## Routine shorthand

ユーザーが`ルーティーン`と言った場合は、上記の一周のうち、報告された成果の受入から次の仕事の成立・
委譲までを実行する。

RoutineはRegistry保守の儀式でも、すべての段階を必ず実施するchecklistでもない。現在地を更新し、
成立条件を再計算し、次の受入可能な仕事を導いて協働を前進させるためのインターフェースである。

具体的には必要な範囲で次を行う。

1. 報告された成果を正本と受入条件に照らして受け入れる。
2. 受け入れた成果と対応する管理記録を、局所的な復旧点としてcommitする。
3. task graph、ready集合、現在の中間ゴール、および担当適性を再評価する。
4. 必要なら次の仕事を分解し、判断不要で境界の閉じたassignmentを担当者へ渡す。
5. task管理とhandoffの変更を必要に応じてcommitする。
6. ユーザーの判断または権限が必要なら、そこで結果と判断点を報告する。

各段階は不要なら何もしない。Routineは非ready taskをreadyにせず、`FROZEN`を再開せず、`PROPOSED`を
自動採用せず、`USER_ONLY`へ着手せず、commit、branch、pushなどに別途必要な権限を拡張しない。

## 継続、停止、再開

task graphは継続可能性を表し、委任は実行権限を表す。実行には両方が必要である。

新しい必須前提の可能性によって現在の成立条件を信頼できなくなった場合、影響する実行を安全な地点で
保留する。停止後に必要な事実と影響範囲を調べ、必須依存ならgraphを更新し、必須でなければ不要な辺を
追加せず再開条件を確認する。

ユーザーの介入や直接編集によって委任が停止、縮小、または撤回された場合は、graph上readyでも状態変更を
続けない。状況を整理した後も、明示的な再委任まで実行を再開しない。

ユーザーの訂正を会話上で了承しただけでは、作業モデルへの反映は完了していない。影響する正本、task境界、
依存、委任内容、および受入条件を必要な範囲で整合させる。

## 判断権と委任

ユーザーは、製品方向、公開上の約束、優先順位、不可逆な選択、許容risk、および明示的に留保した権限を持つ。

Codexは、会話をtaskへ翻訳し、答えの所在と必須依存を発見し、偶有的判断を処理し、task境界を作り、
実行を統合し、証拠を受け入れ、次の仕事を成立させ、内部記録とcommit候補を整える。

担当agentは、共有された成果、権限境界、停止条件、および受入条件の中で、得意な方法を使って調査または
実行する。委任はtaskの所有権を移さず、委任者の主導権を越える権限を生まない。

ユーザーには、内部状態名やtask IDの操作を求めない。現在の結果、その意味、残る不確実性、次の推奨作業、
および本当に必要な判断へ翻訳して返す。

## 新しいprojectへの適用

最初から大きな管理体系を持ち込まない。一つのhandoffまたはRegistryと一つの実taskから始める。

sessionをまたいで同じ現在地へ戻れるか、答えの所在へ辿れるか、受入後に次の仕事を導けるか、判断を
増やしていないか、管理コストが成果を上回っていないかを観測する。実際に必要になった構造だけを追加する。

このV3は`swift-ac-collections`の履歴と作者判断から作成した。別projectで同じ自走能力を再現できるかは
未検証であり、移植可能性は現行の凍結taskとして別に扱う。
