# Codex taskオリエンテーション V4

> **文書状態:** 2026-10-14、ユーザー判断により現行のtaskオリエンテーション正本として採用。

## この文書の役割

この文書は、会話と中間ゴールを、事実確認、製品判断、実行、依存、受入へ変換する方法を示す。
現在のtask状態は複製せず、Task Registryを正とする。状態遷移や記録形式の詳細は
`CODEX_TASK_OPERATION_PLAYBOOK_V4.md`を正とする。

本書は、task処理に必要な具体性だけを扱う。協業体制の設計理由は`AI_COLLABORATION_PHILOSOPHY_V4.md`、
調整役としての行動原理と参照先は`CODEX_ORIENTATION_V4.md`で扱う。

## task管理が解く問題

task管理の目的は、項目を多く登録することではない。仕事を適切に分け、次を会話の記憶や担当者の勘だけに
依存させないことである。

- 現在の到達状態は何か。
- 何が事実として不足しているか。
- agentが判断不要で実行できる範囲はどこか。
- ユーザー判断が本当に必要か。
- 何が後続成立に不可欠な依存か。
- readyな仕事のうち、現在の中間ゴールへ進むものはどれか。
- 誰が何を証拠として検収し、どこへ渡せば完了か。

## 1. 中間ゴールを到達状態として確認する

taskを列挙する前に、現在の中間ゴールを、作業方法ではなく判断可能または引渡可能な状態として確認する。

- 作業方法: コメントを書く。
- 到達状態: 全公開対象について、ユーザーが契約内容をレビューできるコメントドック・ドラフトを揃える。

中間ゴールはtaskではない。ID、担当、状態を持たず、`FROZEN`や`USER_ONLY`を開始する権限にもならない。

## 2. 今回の権限と成果を分ける

ユーザーの言葉から、最終的に何を渡すのかと、今回どこまで実行してよいのかを分ける。目的の提示を、branch作成、
commit、push、公開、不可逆操作の許可へ拡張しない。

ユーザーの最新指示が既存taskに対応する場合は、そのtaskを選ぶ。新しい具体的な仕事であれば、既存taskとの重複、
現在の中間ゴールへの必要性、責任境界を確認してから、適切な正本と受入条件を与える。

## 3. 必要な情報だけを読む

Task Registryから選択したtaskの詳細正本だけを読む。分からないことがある場合も、まず現在の問いを明示し、
その問いへ答える資料だけを追加する。

次の理由だけで読書範囲を広げない。

- 同じ対象やfileに関係する。
- 将来必要になる可能性がある。
- 品質上重要である。
- 過去の経緯を知れば安心できる。
- Archiveやhandoffに未完了らしい記述がある。

情報不足と製品判断の未決を混同しない。資料を増やす前に、現行実装、Test as Specification、詳細正本、既決事項で
現在の問いが解けるか確認する。

## 4. 事実、判断、実行を分ける

- `DISCOVERY`: 事実、選択肢、依存、既存決定が不足している。
- `DECISION`: 証拠を閉じても複数の妥当な製品上の選択が残る。
- `EXECUTION`: 必要な判断が確定し、実装、文書反映、検証だけが残る。

新しい疑問を見つけたこと自体は、ユーザー判断を作る理由にならない。調査で消える疑問を先に消し、最後まで
残った製品上の選択だけを、一判断一taskでユーザーへ渡す。

`EXECUTION`中に新しい公開契約やrisk受容の選択が見つかった場合は、推測で埋めて実装を続けず、停止して
`DISCOVERY`または`DECISION`へ分け直す。

## 5. taskの成立条件を与える

各taskには、少なくとも次を与える。

- 目的と現在の中間ゴールへの関係
- 範囲と対象外
- 担当と責任境界
- 詳細正本
- 完了条件と引渡先
- 停止条件
- 必要な証拠
- 必須依存

これらが未確定な項目は、実行可能なtaskではなく候補として扱う。複数のユーザー判断を一つへ束ねない。

## 6. 依存を必要条件に限定する

Task precedenceには、後続taskの成立に不可欠なAND依存だけを書く。

- `SEQUENCE`: 前提成果なしには後続を開始できない。
- `PARALLEL_JOIN`: 独立部分は先行できるが、後続の完成前に前提成果との合流が必要。

便利な順番、同じfileを触ること、同じgoalに属すること、品質上有用であることは必須依存ではない。推奨順は
soft orderとして扱う。

上流の判断や証拠によって後続の必要性が消えた場合、後続を惰性で実行しない。依存、完了条件、状態を更新し、
ready集合を計算し直す。cycleが出た場合は辺を無視せず、task境界または判断順序の誤りとして停止する。

## 7. readyとnextを区別する

依存上readyであることは、現在必要または次に行うべきことを意味しない。

1. 必須依存が完了しているか確認する。
2. 状態、担当、再開条件、最新のユーザー指示を確認する。
3. 現在の中間ゴールとの関係を評価する。
4. critical path、risk、soft order、検収可能量からnextを選ぶ。

| 距離 | 意味 |
| --- | --- |
| `DIRECT` | 完了により現在のゴールの一部を直接閉じる、または判断可能にする |
| `NEAR` | `DIRECT`な仕事に必要な入力 |
| `FAR` | 現在のゴールに必要だが、複数の中間taskやgateを経る |
| `LATER` | 明示された後続ゴールまたは後続phaseに属する |
| `OUTSIDE` | 記録されたゴールへ寄与しない |

有用、興味深い、品質向上に役立つという理由だけで、`LATER`や`OUTSIDE`を現在の仕事にしない。

## 8. 実行前に受入まで設計する

成果物を作ることとtask完了は同じではない。必要な検証、既知の未確認事項、正本との整合、引渡先を定める。

担当agentの`完了`、test、DocC、CIなど、一つの報告や証拠だけで完成判定しない。一方、到達条件がレビュー可能な
ドラフトの引渡しなら、ユーザーによる実レビューや公開可能な初版を余分な完了条件として加えない。

Codexは成果を検収し、受け入れた結果を詳細正本とTask Registryへ反映する。公開判断や重要なrisk受容が残る場合は、
証拠、選択肢、影響を一問へ絞ってユーザーへ返す。

## 初回理解確認

初回または大きな会話消失後は、下のOptionalArray事例だけを使って確認する。確認のためにArchive、過去のhandoff、
追加の詳細正本を探索しない。この節に記載された事実だけで説明する。

### 確認事例: OptionalArrayの命名とコメントドック

ある段階で、「現行契約をコメントへ記載する実行」と「公開型名を将来も維持するかという製品判断」が、同じ仕事の
前提として扱われていた。

しかし、当時の近い到達条件は、現行契約をユーザーがレビューできるコメントドック・ドラフトにすることだった。
公開可能な初版の完成は後続phaseであり、名称の最終判断もそこで必要になる。

この分解により、現行名でドラフトを書く`EXECUTION`は先に進められ、名称維持の`DECISION`は公開可能な初版を
扱う後続へ送られた。「名称が決まるまでドラフトを書けない」という依存は、到達条件に不要だったため除かれた。

### 確認する観点

次を自分の言葉で説明できることを確認する。

1. 元の仕事では、どの事実、判断、実行が混ざっていたか。
2. 到達条件を確認したことで、どの依存またはtaskが不要になったか。
3. 何が既存証拠から一意に決まり、何が製品上の選択として残ったか。
4. 誰が実行し、誰が検収し、残った選択を誰が決定するか。
5. 文書生成やtestが確認できることと、製品名の妥当性という意味判断をどう区別するか。
6. 後続phaseの未確認事項を残したまま、なぜ近い到達条件を受け入れられるか。

これは固定解、過去のCodexの語彙、人格を再現する試験ではない。次のtaskへ入る前に、判断を不要に増やす、
後続phaseを現在へ混ぜる、機械検査を意味判断へ拡張する、といった重大な取り違えを発見するために行う。

## 分からないときの停止点

次の順で処理する。

1. 現行実装とTest as Specificationから事実を確認する。
2. 選択taskの詳細正本から既存決定と受入条件を確認する。
3. 現在の問いに必要な範囲だけ追加資料を読む。
4. 証拠不足なら`DISCOVERY`へ戻す。
5. 結論が一意ならCodexが処理し、`EXECUTION`へ渡す。
6. 複数の妥当な製品選択が残る場合だけ、一判断の`DECISION`をユーザーへ返す。

質問を作る場合は、何と比べ、なぜ既存証拠では決まらず、答えがどの後続taskを変えるかを示す。これを説明できない
場合は、まだ調査または分解が不足している可能性が高い。
