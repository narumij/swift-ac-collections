# Codex Task Operation Playbook

最終更新: 2026-10-09 / Codex

## 目的

この文書は、このrepositoryで得たtask運用の知見を、別projectでもCodexが同程度の品質で
再現するための移植可能なplaybookである。

ここでいう品質は、task数や進行速度ではない。次を満たす状態を指す。

- 人間の判断とagentの実行を混同しない。
- 未完了、待機、凍結、除外、完了をsessionをまたいで復元できる。
- 変更の理由、証拠、検証結果、残る不確実性を追跡できる。
- agentが判断不足を推測で埋めず、適切な地点で停止できる。
- 実装、文書、test、履歴、taskの間のずれを完成判定前に検出する。

この初版は`swift-ac-collections`で実証した運用から抽出した仮説であり、別projectでの再現試験は
まだ行っていない。repository固有の名称や担当agentは例であり、必須要件ではない。

2026-10-08、ユーザー指示により、このplaybookの追加整理と再現試験は保留した。2026-10-09、
taskインライン化の検討だけを再開して本書へ反映した。別projectでの再現試験を含む広い追加整理は、
引き続き明示的な再開指示があるまで行わない。

## 基本モデル

### 0. 内部管理をユーザーへ返さない

Registry、task ID、状態名、handoff、依存表はagentが作業を再開・統合するための道具である。ユーザーに
「このfileを見れば分かる」と案内して状態確認を返さない。agentが正本を読み、現在地、その意味、次の
選択肢、本当に必要なユーザー判断へ翻訳して答える。

ユーザーが保持するのは、製品方針、公開上の約束、優先順位、不可逆な選択、明示的に留保した権限である。
会話からtaskへの翻訳、分解、依存確認、担当割当、受入、Registry更新、commit境界は統合担当が引き取る。
ユーザーが内部記録そのものを求めた場合は提示してよいが、日常の進捗確認に内部fileの閲覧を要求しない。

評価・感想・retrospectiveは、運用知見を発見して理由を保存する場所であり、session開始時の正本ではない。
別conversationでも守る必要がある知見は、長い記録を毎回読ませず、最小の行動規則へ抽出してAGENTS規則
またはこのplaybookへ昇格させる。

### 1. 正本を一つにする

残taskの状態、担当、再開条件、必須依存を一つのTask Registryへ集約する。会話、古いchecklist、
handoff、個々のagentのmemoryは正本にしない。詳細はtask行から一つのcanonical documentへ辿る。

session開始時はRegistryだけを読み、選択後にそのtaskの詳細正本だけを読む。全資料の再走査は、
古い作業の復活、状態の誤読、context消費を招く。

### 2. 永続IDと状態を分離する

task IDは意味、担当、状態が変わっても維持する。状態名は運用上の属性であってIDではない。
最低限、次を区別する。

- `PROPOSED`: 会話や調査で発見したtask候補。忘失防止の記録であり、着手許可ではない
- `ACTIVE`: 現在着手可能または進行中
- `WAITING_USER`: 人間の判断・操作待ち
- `WAITING_EXTERNAL`: 外部条件待ち
- `FROZEN`: 明示的な再開指示があるまで触らない
- `USER_ONLY`: agentは着手、代行、催促をしない
- `EXCLUDED`: 実施しないと確定した履歴
- `DONE`: 完了条件と受入確認を満たした
- `ARCHIVED`: 現行Registryから履歴へ移し、移動先を記録済み

`FROZEN`と`EXCLUDED`と`DONE`を同じ「今はやらない」に潰さない。それぞれ再開可能性と意味が違う。
`PROPOSED`も未着手task一般とは区別し、範囲と完了条件を確定して`ACTIVE`などの実行可能な状態へ
移すまで、調査、実装、委任を開始しない。

### 3. taskを判断の型で分ける

- `DISCOVERY`: 事実、選択肢、依存、判断候補を発見する。仕様を決定しない。
- `DECISION`: 人間の判断を一つだけ閉じ、後続taskの入力にする。
- `EXECUTION`: 判断済みの方針に従って実装、文書反映、検証を行う。

一つのtaskに複数のユーザー判断を束ねない。`EXECUTION`中に新しい判断が必要になったら、agentが
埋めずに停止し、`DISCOVERY`または一判断ごとの`DECISION`へ分ける。

#### 条件付き判断を早期にtask化しない

`一つのtaskに一つの判断`は、必要性が確定した判断の粒度を定める規則である。DISCOVERYで見つけた
すべての判断候補を、その場でstable taskへ変える規則ではない。

判断候補が複数ある場合は、先に、その答えが後続候補の必要性や範囲を変える上流判断を特定する。
過去の決定で閉じていないことを確認したうえで、現在必要な最上流の判断だけをtask化する。答え次第で
消える、統合される、または内容が変わる後続判断は、詳細正本に条件付き候補として残し、まだstable IDを
与えない。

上流判断が終わるたびに後続候補の必要性を再計算する。これにより、一つの回答から不要な分岐を順に閉じ、
ユーザーへ実在しない選択肢や時期尚早な判断を渡すことを防ぐ。

### 4. goalとtaskを混同しない

中間goalは、複数taskをまたぐ到達状態であり、優先順位を考えるための座標である。状態や担当を持つ
実行単位ではない。goalに含まれることを理由に、凍結taskや人間専用taskを開始しない。

goalは「何をするか」ではなく「何が判断・引き渡し可能になったか」で書く。例:

- 公開APIをユーザードキュメント作業へ渡せる状態にする。
- 文書作業後、1.0採用を判断できる状態にする。

taskの`ready`は「依存上は着手できる」ことしか表さず、「現在のgoalに必要」「次に行うべき」を意味しない。
taskを作成、選択、分解、委任する前に、現在の中間goalへの寄与と距離を定性的に確認する。

| 距離 | 意味 | 運用 |
| --- | --- | --- |
| `DIRECT` | 完了により現在のgoalの一部を直接閉じる、または判断可能にする | 必要なものを優先する |
| `NEAR` | `DIRECT`なtaskの成立に必要な入力 | 必須依存とriskを見て進める |
| `FAR` | 現在のgoalに必要だが、複数の中間taskまたはgateを経て到達する | critical pathと先行riskを見て着手時期を決める |
| `LATER` | 明記済みの後続goalまたは後続phaseに属する | 現goalだけを理由に進めない |
| `OUTSIDE` | 記録されたgoalへ寄与しない | ユーザーの明示変更なしに進めない |

これはRegistry状態やTask precedenceを置き換えない選択観点である。goalとtaskの関係が形式化されて
いない場合、根拠のない数値距離を付けない。近いこと自体を優先度へ読み替えず、必要な`FAR`はcritical
pathや不確実性に応じて早く始める。有用、面白い、依存上readyというだけで`LATER`または`OUTSIDE`の
作業を作らず、現在のgoalに不要なら候補、凍結、後続phaseのまま維持する。

### 5. 必須依存と推奨順を分ける

Task precedenceには、後続taskの成立に不可欠なAND依存だけを書く。調査効率や優先度による順番は
soft orderとして別に示す。順番が便利というだけで依存辺を足すと、不必要な待機が生じる。

各辺の`Barrier`は同期位置を表す。`HEAD`は前提taskの完了を後続taskの開始前に待ち、`LAST`は後続taskを
並行して進められるが、その完了前に前提taskの完了を待つ。どちらも前提taskの状態そのものではない。

### 6. トポロジカル判定はready集合を求めるために使う

Task precedenceは、有向非巡回graphとして扱う。トポロジカルな判定の目的は全taskへ一意の作業順を
与えることではなく、必須依存を満たしていないtaskを除外し、現在着手可能なready集合を求めることに
限定する。

基本手順は次のとおり。

1. 現行Registryに存在するtaskと必須依存辺を読む。
2. `HEAD`の前提taskがすべて`DONE`であるtaskを依存上のready候補にする。`LAST`はready判定を止めない。
3. `PROPOSED`、`FROZEN`、`USER_ONLY`、`WAITING_USER`、`WAITING_EXTERNAL`をready候補から除く。
4. task固有の再開条件、担当、ユーザーの最新指示を確認する。
5. 残ったready集合を現在の中間goalへの必要性と`DIRECT / NEAR / FAR / LATER / OUTSIDE`で見直す。
6. 必要な`DIRECT`・`NEAR`・`FAR`の中から、critical path、soft order、risk、受入可能量を使って
   次taskを選ぶ。

完成判定では、`HEAD`と`LAST`の前提taskがすべて`DONE`であることを確認する。`LAST`が未完了なら作業成果を
先に作れても、後続taskを`DONE`へ移さない。

`EXCLUDED`は自動的に前提達成とみなさない。前提taskが不要になった結果、後続taskも不要なら後続も
`EXCLUDED`にする。別経路で後続taskが成立するなら、依存辺と完了条件を明示的に更新してからreadyを
再判定する。

graphにcycleがあれば、作業順の問題として適当に辺を無視しない。task分割、親子関係、相互判断の
どこかが誤っている可能性があるため、実行を止めてRegistryを修正する。

トポロジカル順序が複数あることは正常である。同じ層のtaskに順番を付けたい場合はsoft orderを使い、
単なる優先順位を必須依存へ昇格させない。

### 7. 候補の記録と着手許可を分ける

会話や調査で有用なtask候補を見つけても、その場でscope、完了条件、依存を確定できるとは限らない。
忘れないためにRegistryへ`PROPOSED`で登録し、候補範囲と発見理由を残す。

`PROPOSED`から着手可能な状態へ移す前に、少なくとも次を確定する。

- taskの型（`DISCOVERY / DECISION / EXECUTION`）
- 対象範囲と明示的な対象外
- 担当と受入担当
- 詳細正本
- 完了条件と停止条件
- 必須依存の有無
- 既存taskとの重複、包含、衝突

確定後、すぐ着手可能なら`ACTIVE`へ、条件待ちなら対応する`WAITING_*`または`FROZEN`へ移す。
採用しない、重複している、親taskへ吸収すると判断した場合は、理由と移管先を残して`EXCLUDED`にする。
IDは提案時点から永続とし、昇格や除外時に採番し直さない。

## taskを作る手順

1. ユーザーの言葉から、期待する到達状態と今回の許可範囲を抽出する。
2. 既存Registryで同じ目的、凍結中の親task、既存の決定を確認する。
3. 対象codeの隣を引く。利用箇所、仕様test、文書、直近の変更、同じsymbolを扱うtaskを見る。
4. 未知を、事実不足、ユーザー判断、実行作業へ分類する。
5. 判断候補のうち、答えが後続候補の必要性や範囲を変える上流判断を特定する。
6. 現在必要な最上流の判断だけをtask化し、条件付きの後続候補は詳細正本へ残す。
7. 必要性が確定した複数判断を分割し、判断済みの実行だけをagentへ渡す。
8. 各taskへ担当、完了条件、停止条件、canonical document、必須依存を与える。
9. 現在の中間goalへの必要性と距離を確認し、不要または後続なら今は着手させない。
10. 全体goalへの寄与と、完了後の受入担当を確認する。

この情報がまだ揃わないが候補を失いたくない場合は、無理にtask descriptionを完成させず
`PROPOSED`として登録する。

task descriptionには最低限、次を含める。

- 目的と対象範囲
- 読む正本と変更可能な場所
- 既に決まっていること
- 決めてはいけないこと
- 必要な証拠と検証構成
- 新しい判断点を見つけた場合の停止条件
- 成果物と完了条件

## taskのインライン化

task分解とassignmentの間に、必要に応じてインライン化を行う。ここでいうインライン化は、永続taskを
削除、改名、統合することではない。判断、依存、履歴を細粒度taskとして保持したまま、連続した実行を
一つのassignment packageへまとめることである。

### 目的

- 分解によって得た停止点と追跡可能性を失わない。
- 判断不要な短い実行taskごとに、ユーザーやagentが受け渡しを繰り返す負荷を減らす。
- 実行時はまとまった作業として扱い、受入時は元のtask単位へ結果を戻せるようにする。

### インライン化できる条件

次をすべて満たす`EXECUTION` taskだけを、一つのassignment packageへまとめてよい。

- 必要な`DECISION`と`DISCOVERY`が完了し、新しい製品判断を含まない。
- 必須依存が確定し、package内の順序が一意または明示できる。
- 担当agent、受入担当、詳細正本が同じである。
- 変更範囲、検証構成、停止条件、commit境界を共通化できる。
- package途中の成果を、別taskが独立して待っていない。
- 一件だけ失敗した場合に、どの元taskへ戻すか判別できる。

`DECISION`、未確定な`DISCOVERY`、`FROZEN`、`WAITING_USER`、`WAITING_EXTERNAL`、`USER_ONLY`は
インライン化しない。状態が違うtask、担当や受入責任が違うtask、独立した監査証拠を必要とするtaskも
まとめない。

### 記録方法

- stable ID、Registry行、Task precedenceは維持する。
- assignmentには含めるtask ID、実行順、共通の対象外、停止条件、検証、提出物を列挙する。
- package名は一時的な作業名であり、新しいstable task IDにしない。
- 完了報告と受入結果は、元のtaskごとにRegistryと詳細正本へ戻す。
- packageを一つのcommitにできるのは、元taskが同じ意味的変更と検証結果を共有する場合だけとする。

### 解除条件

実行中に次のいずれかが起きたら、残りを自動継続せずpackageを解除する。

- 新しいユーザー判断、公開契約、trade-offが見つかった。
- 前提、対象範囲、担当、検証構成がtask間で分かれた。
- 一件の失敗が後続taskの成立を変えた。
- 個別の証拠またはcommit境界が必要になった。

新しいtaskを分解するときも、独立した状態遷移、依存、判断、受入を持たない単なる手順は、最初から
親taskのsubstepとして記述し、stable IDを増やさない。構造が確定する前に畳まず、確定後も履歴を
消すためのインライン化は行わない。

## 実行と進捗処理

### 着手

着手時に、Registryの状態、前提task、凍結条件、worktreeを確認する。古い文書の未完了表現だけを
根拠にtaskを復活させない。変更前に、仕様test、履歴、現在の実装がtaskの前提と衝突しないかを見る。

### 進行中

事実、推論、判断を分けて記録する。長い作業では、ユーザーに短い中間報告を返す。agentへ委任した
場合も、担当agentの完了報告をそのまま完成判定にしない。

次の場合は実装を止めて分解へ戻る。

- 未記録の公開契約を決める必要が出た。
- 性能、安全性、互換性のtrade-offが判明した。
- 当初の前提と既存testまたは履歴が衝突した。
- taskのscopeが完了判定できないほど広がった。
- 許可された変更範囲を越える必要がある。

### 受入

Codexは成果物を、task description、diff、test結果、根拠記録と照合する。受入時には次を分類する。

- task内で完了したもの
- 別taskへ分離すべきもの
- 判断待ちにするもの
- 意図的に見送るもの
- 前提誤りにより`EXCLUDED`とするもの

`DONE`は、作業者が終了した時ではなく、完了条件を証拠付きで満たし、Registryと正本文書が同期した
時に付ける。

### commit

一つの意味的な変更単位をcommitする。commit前に対象file、意図しない差分、format error、必要な
testを確認する。task状態の更新と成果物が同じ完成単位なら同じcommitに含める。無関係な既存変更は
取り込まない。

### Registryの掃除

Registryと同じ状態を別のsummaryやchecklistへ書き写さない。派生snapshotは更新漏れによって正本と
矛盾しやすく、古いtaskを復活させる原因になる。人間向けの概要が必要なら、Registryの状態、担当、
再開条件を複製せず、中間goalや現在の律速などRegistryだけでは読み取りにくい情報に限定する。

完了した中間goal、完了taskだけを並べたsoft order、現状と一致しない概要は現行部から削除する。
完了理由、証拠、commitなど再開判断に必要な履歴はtask行またはArchived記録へ残し、単に古いという
理由で消さない。

## 委任モデル

委任は責任の放棄ではない。作業担当と完成責任を分ける。

- ユーザー: 優先順位、公開契約、重大なtrade-off、中止・再開を決める。
- Codex: 要求をtaskへ翻訳し、分解、割当、統合、受入、Registry更新を行う。
- 担当agent: 境界の確定した調査または実行を行い、事実と不確実性を返す。

agentの適性は固定的な人格評価ではなく、実績で更新する。委任先には、一つの判断も含まないtask、
または明示的に一つだけの判断材料を集めるtaskを渡す。判断権がないagentに曖昧な裁量を渡さない。

高リスク領域では独立確認を使う。ただし、複数agentの一致を正しさの証明にしない。同じ資料と前提を
共有すれば、同じ誤りを再生産できる。test、compiler、履歴、外部仕様など異なる証拠経路を組み合わせる。

## 失敗から得た規則

- taskを細かく分けても、親の前提が誤っていれば全taskが不要になる。逆向きの過去決定と仕様testを
  分解前に確認する。
- `一判断一task`を全判断候補の即時task化と解釈すると、上流判断で消える分岐まで増殖し、
  ユーザー判断を過剰に要求する。
- code scopeの共有はtask依存を意味しない。性能測定や証拠の帰属は、code上独立でも順序依存を作る。
- 文書上の契約が実装で検査されないことは、直ちに不一致ではない。呼び出し側の事前条件を区別する。
- graphや検索の「0件」は対象範囲を検証するまで証拠にならない。既知の違反を一時的に作るなどして
  検出器の感度を確かめる。
- task、code、taskと往復する依存は、DBだけでは判断できない。構造は候補を示し、意味と責任は人間と
  統合担当が持つ。
- 完了報告が増えるほど、統合、重複排除、状態同期の負荷も増える。委任量ではなく受入可能量を基準にする。

## 運用規則の掃除判断(2026-10-09)

既存規則を一括で削除せず、次の一判断ずつ順に扱う。各判断の後に必要な文書反映と検証を終えてから、
次の判断を再開する。

1. **決定済み:** 終了・除外済みの`GRAPH-004`を参照するルーティーンfallbackは削除する。
2. Task precedenceの同期位置は、前提taskを後続taskの開始前に待つ`HEAD`と、終わりに待つ`LAST`で
   表す。段階移行用のBarrier `UNCLASSIFIED`を廃止するか。現行8辺の分類は一括判断せず、
   一辺につき一つのユーザー判断taskとして順に閉じ、その後に廃止自体を判断する。
   - Index完了ゲート←公開Index表現・完了範囲: `LAST`。Comparable採否の外部依存とは分離する。
   - Index完了ゲート←Comparable採否: `LAST`。外部依存は判断task側に残し、他のIndex作業の
     着手を止めない。
3. 上流判断前に採番済みとなった条件付きtaskを、結果待ちで保持するか、不要と判定できる時点で
   `EXCLUDED`へ送るか。
4. 2026-10-16までのCodex低燃費運用を、期限後に削除、更新、または継続するか。

Claude専用task graph DBはこの掃除対象に含めない。Claude自身の継続記憶とチューニング記録を保持する
storageでもあり、Codexの構造lintとは役割が異なる。

## 新projectへの導入

最初から大きな管理体系を作らない。次の順で導入する。

開始時は[`PROGRESS_OVERVIEW_TEMPLATE.md`](PROGRESS_OVERVIEW_TEMPLATE.md)をコピーし、placeholderと
例示taskを実projectの内容へ置き換える。

1. 一つのRegistryと状態語を作る。
2. 現在のgoalと、明示的に凍結する範囲を書く。
3. 一つの実taskを`DISCOVERY / DECISION / EXECUTION`へ分けて試す。
4. 完了条件、停止条件、証拠、commit境界を実地で調整する。
5. sessionを切り替え、RegistryとGitだけで再開できるか確認する。
6. 委任する場合は小さな事実確認から始め、受入結果で適性表を更新する。
7. project固有の例外だけを追加し、playbook本体へ安易に一般化しない。

## 再現性の評価

別projectで同品質を再現できたと判断するには、少なくとも次を確認する。

- 新しいsessionが、会話履歴なしで正しい次taskを選べる。
- 人間判断待ち・凍結・人間専用・外部待ちのtaskを誤って開始しない。
- agentが新しい判断点で停止し、勝手に仕様を埋めない。
- task完了時にcode、test、文書、Registry、commitが同期する。
- 前提誤りを発見したとき、実装を正当化せず`EXCLUDED`や再分解へ戻せる。
- ユーザーがIDや内部状態語を覚えなくても、通常の言葉で運用できる。
- 管理コストが成果より大きくなった場合、粒度や記録量を減らせる。

## この初版の限界と次の検証

- 単一repository・少人数・Git中心の運用から抽出しており、大規模組織には未検証である。
- project tracker、issue、PRを正本にする環境への写像は未定義である。
- 緊急修正、複数release branch、並行する複数人レビューの扱いは未検証である。
- 「同品質」を測る定量指標はまだなく、上の再現性条件を暫定gateとする。

次の段階では、別projectまたは独立した小規模課題へこのplaybookを適用し、必要だった追加説明、
誤作動、管理負荷を記録する。その差分だけを一般知見として本書へ戻す。
