# 判断と判断キャッシュのDB管理検討

## TL;DR（人間向け）
判断の内容・根拠・依存関係とコピー判断をDBで扱うと、探索と再確認を減らせるか検討する。V3切替後の調査を再開し、既存判断3件の隔離試行案まで具体化した。移行の実行は未承認。

OPS-158 / ACTIVE / Astra / 2026-10-19。親OPS-103。ユーザー「それも検討して」に基づく検討のみ。

## 検討範囲

- 元判断：不変ID、内容・理由・根拠・決定者・適用範囲・版と改訂履歴。
- 依存：根拠/適用先の接続変更と、判断内容の再確認を区別する。辺の変更だけで意味の妥当性が保証されたとは扱わない。
- コピー判断：元ID/版、要約、見直し条件。根拠変更から影響するコピーだけを要確認にする案。キャッシュは独立の決定権を持たない。
- 少数の既存判断で、現在の記録方式との手間/探索/再確認を比較する案を作る。未計測の効果を確定しない。
- 文章はDB本文にも保持できる。テキストを読み書きしやすい成果/仕様のMarkdown維持と両立させる。

## 初期整理

DBは依存の照会と履歴保存を機械化できるが、根拠が判断を支えるかの確認は残る。元判断の版を固定し、変更は新しい版と接続変更履歴として残す案を優先する。循環/欠損参照、訂正、撤回、バックアップ/書き出しも比較項目。自動的な再判断/実作業開始はしない。

## 停止点

少数試行の設計と利点/負担/残る判断をまとめるまで。実DB移行、RegistryのDB正本化、既存キャッシュ全量移行は行わない。ユーザーとのRegistry DB移行相談は関連背景で、実装承認とは扱わない。

## 関連するユーザー意向（2026-10-19）

マイルストーンも、フォーカスを保てるならDB化したいという相談があった。保存形式を変えることと、概念の境界を変えることは区別する。HEADから現在区間だけ取得し、版内の順序・START/END・ゲートと固定ID接続を維持しながら、Studioでは全体を俯瞰できることを検討条件として残す。今回の連絡DB実装には追加しない。

## 最小設計のたたき台（Astra、2026-10-19・未採用）

### まず答えたい問い
「この作業で使う判断は何か」「誰が何を根拠に決めたか」「この要約はどの版を写したものか」「根拠が変わったら何を読み直すか」。自動的な正誤判定や判断の生成を目標にしない。

### 小さく始める記録
- 判断ID：同じ判断の改訂を束ねる安定ID。改訂本文は上書きせず、決定者、適用範囲、理由、元の記録への参照を保持する。採用/撤回などの効力は明示記録に基づき、日付の新しさだけで決めない。
- 根拠参照：判断改訂に結び付ける出典。commit・path・節/行・確認時点を記録できる。ユーザーの方針決定と実装の事実を同じ証拠種別にしない。
- コピー：元判断のIDと改訂、要約、利用範囲。独立の決定権を持たず、参照元が変われば要確認にする。元判断が特定できないものは推測で紐付けない。
- 利用先：taskやゲートへの参照。所属や接続から自動的な着手条件を作らない。

### 初回試行の完成条件
姫が照合する既存3件だけを固定した入力として、元記録を辿る照会とコピーの版照合を試す案。正本化はまだ行わない。変更を一つ与えたとき、影響するコピーだけが「要確認」になり、判断本文・効力・task状態は勝手に変わらないことを示す。出典のないコピーや、方針と事実の混同を見つけたら、その不足を結果として残す。

探索時間や使用量の改善率を推測で宣言しない。少なくとも、照会で表示された材料だけで答えられる問いと、元文書へ戻る必要がある問いを区別する。試行のために全キャッシュの構造を揃えない。

### 今は作らないもの
自動的な判断の有効/無効化、全量移行、LRU、ランキング、汎用推論エンジン、UI編集。必要性が出たものを後で判断する。

### 受入時の補正

- `TASK_REGISTRY_V3_DESIGN.md`の旧「移行判断へ残す事項」は、当該箇所に未決表現が残ることをAstraも確認した。ただし**決定前の提案・未決記録はコピー判断ではない**。歴史上正しかった記録を誤りへ自動分類せず、「後続決定への案内が必要か」を要確認とする。本調査では元文書を修正しない。
- D2の実装・試験への参照だけで「今も履行されている」とは断定できない。DBが返すのは、何をどの版で確認したかと再確認先。現在のコード差分や試験結果の確認を置き換えない。
- 方針決定の出典と、その方針を実装が守る証拠は別物。試験成功はユーザー方針の正しさを証明しない。
- 発見した関係だけを対象にする。未登録の説明や依存が存在しないとは主張しない。

### 初回試行の設計

既存の本番DBから分離した一時SQLiteに、3判断と少数の参照だけを手で登録する案。D1〜D3は試行内IDであり、本番採番ではない。

最小構成は判断改訂と参照記録の2系統。参照種別で原記録・コピー・過去の提案・根拠・実装/試験・利用先を区別する。却下案、理由、再確認条件はまず文章として保持し、照会上必要になるまで個別テーブルへ細分化しない。判断改訂は不変とし、採用・撤回の記録を別に明示する。

原文はMarkdownまたは連絡DBに残す。出典はcommitとpath/節/行、またはletter IDで固定し、引用範囲の変更検知と判断内容の変更を区別する。全文ハッシュが変わっただけで全判断を失効させない。

試行では3照会を人の読み取りと照合し、コピーが参照する版と、元記録に戻る必要のある事項を表示する。模擬的な出典変更・判断改訂を与えた際は、登録済みの関係先だけを要確認にする。判断の効力やtask状態は自動変更しない。旧提案には後続判断の参照を示すが、コピーの版不一致とは区別する。

### 効果の確かめ方と区切り

各照会について、DBだけで得られた情報、原文を読む必要が残った情報、登録・更新に必要だった作業を記録する。既に読んだ情報の手動照会を再現して使用量削減率を作らない。初期登録コストと次回の再利用効果を分け、少数例から全体の効果を外挿しない。

この設計で初期調査の停止点に到達。次の具体的な実行範囲は「3判断の隔離SQLite試行と結果記録」。本番移管・既存キャッシュ全量移行・UI・自動再判断を含めない。実行に進む判断はユーザーへ返す。
