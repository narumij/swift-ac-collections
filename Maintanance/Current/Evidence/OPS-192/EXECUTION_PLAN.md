## 2. 手順（順に、1区切り1パッチ）

### 1. T1 つながり

  - 送り手が前の連絡の当事者でない。

### 2. D1 連絡を起点に読む

- 流れ：`GET /letters/<id>/thread`。つながった連絡のすべての出来事を、`sequence`の順に返す。各出来事には、その本文の版（連絡ID・依頼か返答か・版・記録した人・時刻）と、閉じた連絡の出来事も付ける。
- 前後と、読んだ証拠を分けて表す：
  - 流れの中の「補正を送った時点で、前の連絡の最新の返答はv1だった」は、順番からの文脈として出す。
  - それは送り手がv1を読んだ証拠ではない。だから「見直した」とは出さない。
  - 送り手が読んだ版を確かに示す欄は、今はない。足すかどうかは後で決める。
- 差分：2種類あり、どちらも出す。
  - (a) 続きの連絡の本文。前の連絡に対する新しい内容。
  - (b) 改訂。読み手が受領で読んだ版から、今の版への行の差。読むときに作る。元の版は両方とも残る。
- CLI：
  - `comm.py letter read <id>`：差分
  - `comm.py letter read <id> --full`：流れの全体を原文で
  - `comm.py letter text <id> --part … --revision N [--sha256 H]`：版を固定した1つの本文（出典のP1）
- 読むだけで、何も記録しない。
- ファイル：`studio_store.py`（流れと行の差）・`serve.py`・`comm.py`・`test-studio-letters.py`。

### 3. B1 正本を起点に読む

- コマンド：`comm.py letter doc <path> [--section 見出し] [--full]`。口は`GET /letters?brief=1&doc=…&section=…`（今の一覧の口に引数を足す）。
- 一致の決まり：
  - パスは、送るときと同じ正規化をしたリポジトリからの相対パスで、完全に一致するもの。見出しは、文字が完全に一致するもの。
  - 依頼か返答の、どれか1つの版にその参照があれば一致とする。閉じた連絡も含める。
  - 本文から推測しない。参照の欄だけを見る。
- 版で参照が付いた・変わった場合：
  - 各連絡に「どの部分のどの版が、その参照を持つか」を出す。たとえば「依頼v2から」「返答v1だけ」。
  - その部分の最新の版がまだその参照を持つかも出す（今の参照か、前の参照か）。
  - 前の版だけの参照も、記録として一覧に残す。
- つながったスレッドの中の、関係のない連絡：
  - 一覧には出さない。
  - 一致した連絡を`read --full`で開いたときに、流れの文脈として「この正本を参照していない」と付けて出す。
- 読み方：
  - 既定：一致した連絡ごとに、その参照を持つ最新の本文。それが改訂なら、前の版からの差。
  - `--full`：一致した連絡の本文のすべての版を、出来事の順に出す。
- ファイル：`studio_store.py`（参照の照会。一覧は本文の列を読まない）・`serve.py`・`comm.py`・`test-studio-letters.py`。

### 4. N1 返したあとの改訂の通知（範囲を限った直し）

- 権限と今の操作は変えない。続きの連絡を使うやり方を、既定にもしない。返したあとの改訂も、今のまま使える。
- 3つを分け、記録で確かめられることだけを扱う。
  - 知らせた：watchの表示は、手元に出るだけで、DBには残らない。だから「知らせた」は記録として扱わない（今と同じ）。
  - 読んだ：受け手が明示の操作で記録したときだけ、読んだことにする。
  - 答えた：受け手が明示の操作で記録したときだけ、答えたことにする。
- 新しい出来事を2つ足す。`letter_events.event`の新しい値を使うだけなので、schemaは変わらない。どちらも状態は変えない（`_letter_state`は`revised`と同じく数えない）。
  - `read`（読んだ）：`comm.py letter read-revision <id> --actor 宛先 --revision N`。`text_sequence`に、読んだ依頼の版の本文の行を入れる。
  - `answered`（答えた）：`comm.py letter answer <id> --actor 宛先 --revision N --body-file F`。
    - 返答の改訂（新しい版）と、`answered`の出来事を1つの取引で書く。`answered`の`text_sequence`には、答えた依頼の版Nの本文の行を入れる。
    - どの返答が答えかは、同じ取引で書いた返答の版。2つの行は同じ`operation_id`を持つので、ちょうど1つに決まる。
    - 本文は必ず要る（省略はできない）。今の返答をそのまま答えにしたいときも、本文を渡して新しい版として記録する。
    - 版の範囲の外、受け手以外、閉じた連絡は拒否する。
- 未回答の判定は、答えた版で行う（出来事の順だけでは決めない）。
  - Rを、依頼の最新の版とする。
  - Rが、最後の有効な`returned`より後の改訂でできた版（返したあとの改訂）で、Rを指す有効な`answered`がないとき、未回答とする。
  - Rを指す`answered`があれば、未回答ではない。古い版を指す`answered`は、Rについて何も変えない。
  - だから、v3が来たあとのv2への答えでは、v3は未回答のまま残る。v3への答えで消える。v3に答えたあとに、v2への答えが遅れて届いても、未回答には戻らない（判定はRだけを見る）。
  - Rが返す前からある版なら、未回答とも回答済みとも判定しない（今と同じ「返答済み」）。
  - 誤字の直し（`revise --part reply`）は`answered`を作らないので、答えにならない。
- 前からある記録：
  - `answered`はないので、返したあとに依頼の改訂がある古い連絡は「回答の記録なし」として未回答に出る。答えたと推測はしない。
  - 閉じた連絡は出ない（今と同じ）。
- 届け方：
  - `inbox`は、未回答の連絡を`revisedAfterReply: true`付きで返す。
  - watchは、inboxを出た連絡の最後の印を`seen`に残す。決まった履歴で1回だけ検知する。
    - 着手の時点の状態ファイルからなら`['state','revision']`。
    - 新しい状態ファイルなら`['new']`。
- 受け手の一巡：
  1. Astraが、返したあとの依頼をv2に改訂する。
  2. 姫のinboxに出て、watchが1回知らせる。
  3. 姫が`letter read L1`で差を読み、必要なら`read-revision --revision 2`で読んだことを記録する。
  4. 姫が`answer --revision 2 --body-file 返答.md`で答える。ここで未回答が消える。
  5. 誤字だけを直す場合は、今の`revise --part reply`のまま。未回答は消えない。
- ファイル：`studio_store.py`（`TRANSITIONS`の外の、状態を変えない2つの出来事・`inbox`の判定）・`serve.py`（`LETTER_FIELDS`）・`comm.py`（`read-revision`・`answer`・watch）・`test-studio-letters.py`。

### 6. X1 発言の順番とNOP（店とCLI）

- 議論：T1でつながったスレッドに、参加者の並びと発言の順番を持たせたもの。
- 記録：新しい表`thread_turns`（追記だけ）。出来事の種類は次の5つ。
  - `participants`：参加者の並びを決める・変える
  - `mode`：本人が「参加」「閲覧」を切り替える
  - `speak`：発言
  - `nop`：本人が、発言なしで順番を渡す
  - `auto_skip`：サーバーが閲覧中の人を飛ばした
- 各出来事は`turn`（何番目の順番か）と操作IDを持つ。いまの番は、出来事をたどって出す。
- 発言は二重に起こさない：
  - 発言は、次の番の人を宛先にした`--follows`の続きの連絡を送ること。
  - `speak`の出来事は、その送信と同じ取引で書く。1回の操作で、連絡1通と発言1つだけができる。
  - 順番が進むのは`speak`・`nop`のときだけ。連絡の受領・着手・返すでは進まない。
- 自動NOP（`auto_skip`）：
  - `speak`か`nop`を書いた同じ取引の中で、サーバーが、次の番が閲覧中なら`auto_skip`を書いて飛ばす。これを、参加中の人に当たるまで続ける。
  - `recorded_by`は`server`、`actor`は飛ばされた人、理由は「閲覧中」。本人の発言は作らない。サーバーが何をしたかは、記録で確かめられる。
  - 全員が閲覧中なら、1周したところで止める。「全員閲覧中のため順番は止まっている」と出し、それ以上`auto_skip`は書かない（無限には回らない）。
- 同時の操作と再送：
  - `speak`・`nop`は、前提の`turn`を持つ。BEGIN IMMEDIATEで1つずつ並べ、前提が古ければ拒否する（同じ番を2回進めない）。
  - 同じ操作IDの再送は、記録した結果を返す。
- `mode`の切り替えは本人だけが記録できる。効くのは、次に順番が来たときから。
- NOP・自動NOPは、賛成・承認・作業の完了ではない。連絡の状態も、N1の未回答も、別に要るユーザーの判断待ちも変えない。
- 担当の交代（参加者の入れ替え）は、この段の範囲に入れない。過去の発言者は変えない。
- ファイル：`approvals.py`（表とtrigger）・`studio_store.py`（順番・`speak`と送信を同じ取引に・`auto_skip`）・`serve.py`・`comm.py`・`test-studio-letters.py`。

## 3. 例（順番を直した）

1. Astraが依頼L1を送る（正本§Aを参照）。
2. 姫が受ける・着手・返す（返答v1）。
3. Astraが`--follows L1`で補正L2を送る（依頼v1、§Bを参照）。
4. 姫がL2を受ける（v1を読む）。
5. 姫が返す前に、AstraがL2の依頼をv2に直す。
6. 姫がL2を返す。

差分の読み方（`comm.py letter read L2`、姫）：

```
L2 ← follows L1  ［文脈］送信の時点で、L1の最新の返答はv1（姫）
今回（L2 依頼、受領で読んだv1 → いまv2、Astra）:
 1. 戻しに鍵を放すことを含める
-2. 中継の結果
+2. 中継の結果を、画面まで保つ
```

全体の読み方（`--full`）：L1の送信（依頼v1の原文）→ 受領・着手 → 返す（返答v1の原文）→ L2の送信（依頼v1の原文）→ 受領 → 改訂（依頼v2の原文）→ 返す（返答v1の原文）。出来事の順で出す。

正本の読み方（`comm.py letter doc Maintanance/Current/X.md`）：L1（依頼v1が§Aを参照、今の参照）とL2（依頼v1・v2が§Bを参照、今の参照）の2通が出る。同じスレッドでも§Aと§Bのどちらも参照しない連絡は、一覧に出ない。

N1の場面：6のあとに、AstraがL1の依頼をv2に改訂したとする。

1. 姫のinboxにL1が戻る（`revisedAfterReply`）。watchが1回だけ知らせる。
2. 姫が`letter read L1`で、v1→v2の差を読む。
3. 姫が`letter answer L1 --revision 2 --body-file 返答.md`で答える。ここで未回答が消える。
4. 誤字だけを直す`revise --part reply`では、未回答は消えない。

| X-A2 途中参加 | ユーザーが「参加」に切り替えると、次に回ってきた番でユーザーが発言者になる。ユーザーのNOPを記録すると、次へ渡る。「閲覧」に戻すと、また自動NOPになる |
| X-A6 二重に起こさない | 1回の発言の操作で、連絡1通と`speak`1つだけができる。その連絡の受領・返すでは、順番は進まない |

| X-A8 同時と再送 | 同じ番に2つの`nop`を同時に送ると、片方だけが通る。同じ操作IDの再送では、順番は進まない |
| X-A9 自動NOPの記録 | `auto_skip`は`recorded_by: server`で、飛ばされた人の発言や`nop`は作られない |
| X-A3 NOPは何も認めない | NOPと自動NOPの前後で、連絡の状態・N1の未処理・承認の記録が変わらない |
| X-A4 切り替えは本人だけ | ほかの人がユーザーの`mode`を記録すると拒否する |
| X-A5 判断の出典 | ユーザーが送り手の本文だけが、ユーザーの判断の出典になる。NOP・自動NOP・閲覧・Astraのまとめは出典にならない |

## 5. 戻し

- 各区切りはパッチを戻せば外れる。
- 広げたDB（`letter_links`・`thread_turns`の行）を残したまま、前のコードで起動・読み・書き・再送ができることを、試験で確かめる。そのとき前のコードは、流れ・正本の読み方・N1を持たない。
- 記録は消さない。backupからの復元は、この戻しには使わない。

## 6. 話し合う点

技術的な事実は上のとおり。本当に残る判断は次の2つ。

- 答えたことの明示（`answer`）を、受け手の手間として受け入れるか。代わりはない。順番だけで推す案は取り下げた。
- X1の順番の決め方と例外（正本に「まだ採用されていない」とある）。
  - 参加者の並びを誰が決めて変えるか。案は、議論を始めた人が最初に並べて、変えるのも記録に残すこと。
  - 発言の途中で割り込む場合や、順番を飛ばす場合をどう扱うか。
  - 担当の交代は、別の段で扱う。
