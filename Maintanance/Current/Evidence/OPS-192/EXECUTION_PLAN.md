## 1. 前・今（実例から）

前のやり方（OPS-187、ファイル経由の依頼）では、1つの文書に、依頼→返却→検収が時間の順に並んでいた。上下の位置で対応が分かり、全体は文書、差分は`git log -p`で読めた。

今（OPS-192、連絡DB）は次のとおり。

- 連絡の本文は、前の依頼を写している。E9929557は3,898字のうち2,143字が写し。

## 2. 最小の案（連絡DB・CLI・Studio）

### 使える今の仕組み（確かめた事実）

- `letter_events.sequence`は、全部の連絡で1本の連番（AUTOINCREMENT）。だから、つながった連絡の出来事を、この番号でそのまま時間の順に並べられる。
- 本文と出来事は、`text_sequence`で結ばれている。送信は依頼の本文、返すは返答の本文、改訂は改訂の本文につながる。
- 本文の版は、すべて残っている。`(letter_id, part, revision)`はUNIQUEで、追記だけ。

### 足すもの

- **T1 つながり**（新しい表を1つ。今は連絡どうしの関係がないので、これだけは要る）
  - `letter_links`（`follows_id`・`thread_id`）。
  - `comm.py letter send --follows <前の連絡>`で、送る取引の中で書く。
  - 拒否するのは、もうない連絡を指すときと、当事者でない人が送るとき。
  - 後からのつなぎと、昔の連絡を推測してつなぐことはしない。
- **D1 2つの読み方**（読むだけ。記録は何も変えない）
  - 時間の順の流れ：`GET /letters/<id>/thread`は、つながった連絡のすべての出来事を`letter_events.sequence`の順に並べて返す。
    - 出来事：送信・受領・着手・返す・改訂・閉じる。
    - 各出来事に、その本文の版（ID・依頼か返答か・版・書いた人・時刻）を付ける。
  - 差分：今回の新しい内容と、前の版との差の2種類。
    - (a) 続きの連絡では、その連絡の本文そのものが「前の連絡に対する新しい内容」になる。送り手は新しい内容だけを書く。前の内容は、つながりで辿る。
    - (b) 改訂では、前の版から今の版への行の差（unified diff）を、読むときに作って返す。元の版は両方とも残る。
    - 差分を読むと、(a)と、受け手が受領で読んだ版からの(b)が出る。(b)がないときは(a)だけ。
  - CLI：`comm.py letter read <id>`（差分）、`comm.py letter read <id> --full`（流れの全体を原文で）。
  - 一行の参照だけを差分の代わりにはしない。差分として出すのは、変わった本文そのもの。
- **T2 Studio**
  - 連絡の詳細を2つの欄にする。
    - 「今回」：本文（a）と、あれば改訂の差（b）。
    - 「スレッドの流れ」：時間の順の出来事の行。押すと、その版の原文が開く。
  - 選ぶだけで、受領にはならない。GETだけを使う。

### 対応の表し方（明示）

- 返答と依頼：同じ連絡の中にあるので、構造で対応が分かる。
- 補正と答え：
  - 補正は、前の連絡を`follows`で指す新しい連絡。その答えは、その連絡の返答。
  - 補正が見た前の返答は、流れの中で、補正の`sent`より前にある、前の連絡の最後の返答の版。出来事の連番で決まり、推測は要らない。

### 変えないもの

- 改訂の権限。前からある連絡はつながりのない1通のまま。
- 返したあとの改訂が届かない穴（N1）は、開いたまま残す。新しいやりとりでは、返したあとの補正を続きの連絡で送れば、この穴を通らない。
- 自動の要約、判断の取り出しと一覧、権限の追加は、範囲の外。

## 3. 例：2つの読み方

1. Astraが依頼L1（v1）を送る。
2. 姫が返す（L1の返答v1）。
3. Astraが`--follows L1`で補正L2を送る。L2の本文は「1. 戻しに鍵を放すことを含める 2. …」だけ。
4. 姫がL2を返す。
5. あとで、Astraが返す前のL2の依頼をv2に直す。

差分の読み方（`comm.py letter read L2`、姫・事情の分かっている人）：

```
L2 ← follows L1（L1の最後の返答：v1 姫 06:00:47）
今回（L2 依頼 v2、Astra）:
 1. 戻しに鍵を放すことを含める
-2. 中継の結果
+2. 中継の結果を、画面まで保つ
受領で読んだ版：v1 → いま：v2
```

全体の読み方（`--full`、初めての人）。流れを時間の順に、原文で出す：

```
L1 送信 Astra 05:58:12  [依頼 v1 原文…]
L1 受領・着手 姫
L1 返す 姫 06:00:47  [返答 v1 原文…]
L2 送信 Astra（follows L1） [依頼 v1 原文…]
L2 改訂 Astra [依頼 v2 原文…]
L2 返す 姫 [返答 v1 原文…]
```

## WP2 スレッドと、返したあとの改訂の通知

### N1：通知の最小（今の権限は変えない）

- 目的：返したあとに依頼が改訂されたら、受け手に届く。もう一度答えたら、未処理ではなくなる。返したあとの改訂も、今の操作も、そのまま使える。
- 未処理と判定する：状態がreturnedで、最新の依頼の版が、答えた版より新しいとき。
- 届ける：
  - `inbox`は、上の判定が真の連絡も返す。目印は`revisedAfterReply: true`。
  - `watch`は、inboxを出た連絡の最後の印を`seen`に残す（今は捨てている）。戻ってきたときに`['state','revision']`と出る。試作で確かめた（`prototype-output.txt`）。
- 版の識別：依頼の版の番号（今の`revision`）。
- 答えたことの記録：
  - `letter_texts`に、空でもよい列`answers_revision`を1つ足す（`ALTER TABLE ADD COLUMN`。追記だけのtriggerはそのまま）。
  - `returned`の出来事と`revise --part reply`は、`--answers N`を任意で受ける。
  - 範囲は1以上、今の依頼の版以下。外れていたら拒否する。
  - 付けなかった場合は、新しい版に答えたことにしない。だから、誤字だけの直しでは未処理のまま。
  - 答えた版は、返答の行の`answers_revision`の最大値。値がない行の扱い：
    - 返す（`returned`）：受領で読んだ版に答えたものとする。
    - 返答の改訂：答えた版を変えない。
- 前からある記録：列はNULLになる。NULLは「答えた版が記録されていない」という意味で、確かに答えた版が分かるわけではない。
  - 提案する扱い（控えめな仮の規則。決めるのはユーザーとAstra）：NULLの返す（`returned`）は、受領で読んだ版に答えたものとして扱う。NULLの返答の改訂は、答えた版を変えない。
  - この扱いでは、受領のあとに依頼が改訂された古い連絡（例：9FE8ADABは、v1を受領して返したあとにv2がある）は、閉じていなければ未処理として出る。閉じた連絡は出ない。
  - 代わりの扱いもある：古い連絡は「答えた版が分からない」として、未処理とは別の印で出す。
  - どちらにするかも、話し合いで決める。
- 競合と再送：
  - 依頼の改訂と、返す／返答の改訂は、BEGIN IMMEDIATEで1つずつ並ぶ。`--answers`の範囲は、取引の中の最新の版で確かめる。
  - 送り手がv3を足すのと同時に受け手がv2に答えれば、未処理のまま残る（正しい）。
  - 再送は今の操作IDのまま。`answers`はpayloadに入れるので、同じIDで違う値を送れば拒否される。
  - `watch`の状態ファイルは、今と同じく表示のあとに保存する。
- 今ある操作：返したあとの依頼の改訂、返答の改訂、返す、どれも今のまま使える。`--answers`を付けないときの振る舞いは、今と変わらない。
- 決めること：上の答え方の規則は、ユーザーとAstraと話して決める。
  - 任意の`--answers`で、付けなければ答えにしない。
  - 列を足す。
  - 代わりの規則も1つだけ書いておく。「返答の改訂は、いつも最新の依頼に答えたとみなす」。列は要らないが、誤字だけの直しでも未処理が消える。
  - 返したあとの改訂の禁止は案に含めない。
- ファイル：
  - `approvals.py`：列を足す。
  - `studio_store.py`：`event`・`revise`の`answers`と、`inbox`の判定。
  - `comm.py`：`--answers`と、watchで出た連絡の印を残すこと。
  - `records_service.py`：`LETTER_FIELDS`で`answers`を任意で受ける。R1のあとは、この表は共通サービス側にある。
- 試験（`test-studio-letters.py`に足す。一時DB）：
  1. 送る→受ける→着手→返す→送り手がv2に改訂 → inboxに出る。
  2. watchの出力。前に何を見たかで、出る名前が変わる。決まった履歴だけで確かめる。
     - 履歴A：着手の時点でwatchを1回走らせて状態ファイルを作る → 返す → v2に改訂 → watch。ちょうど1回`['state','revision']`が出る。もう1回走らせると何も出ない。
     - 履歴B：状態ファイルが新しい（まだない）→ v2のあとにwatch。ちょうど1回`['new']`が出る。もう1回走らせると何も出ない。
     - ほかの履歴の名前は求めない。求めるのは「1回だけ検知する」ことだけ。
  3. 返答の改訂で`--answers`なし（誤字） → 未処理のまま。`--answers 2` → inboxから出る。
  4. `--answers 0`・`--answers 3`（版が2のとき） → 拒否する。
  5. 改訂のない返した連絡、閉じた連絡 → inboxに出ない（今と同じ）。
  6. 前からある記録のfixture（列がNULL。一時DBに、今のコードで作る）。結果は提案した仮の規則のときのもので、規則を変えれば期待も変わる。
     - (i) 返したあと何もない → 未処理にならない。
     - (ii) 返したあとに依頼の改訂がある → 未処理として出る。
     - (iii) 返したあとに返答の改訂がある（依頼の改訂なし）→ 未処理にならない。
     - (iv) (ii)のあとに返答の改訂（NULL）がある → 未処理のまま。
  7. 同じ操作IDで`answers`だけ違う → 拒否する。
  8. 既存の25件がそのまま通る。
- 戻し：
  - 試験（下の「広げたDBへ戻す試験」）で確かめる。`dict(row)`に欄が増えるだけ、というのは理由にならない。
  - 戻したあとのコードは、N1の意味（未処理の判定、watchが印を残すこと、`--answers`）を持たない。返したあとの改訂は、また届かなくなる。

## WP4 通しの試験（R3＋L1）

- ファイル：新しい`test-conversation-loop.py`（実プロセス2つ。共通サービスと画面）。駆動部は`letters_e2e.cjs`と`approvals_e2e.cjs`を使い回す。
- 一巡（L1）：
  1. Astraが依頼を送る → 姫が受ける・着手・返す（`--answers 1`）。
  2. 画面を止める。Astraが同じ連絡を改訂する（v2）→ 姫の`watch`が`revision`を検知 → 姫が返答を改訂する（`--answers 2`）。
  3. Astraが`--follows`で続きの連絡を送る → 姫が受ける・返す。
  4. 承認の`add・list`も、画面が止まっている間に通す。
  5. 画面を戻す。ページが、最初の連絡（v1・v2・返答）と続きの連絡を、`thread`の行で辿れる。どれも未処理として出ない。サーバーの記録と表示が一致する。
- 止める・戻すの場面（R3）：
  - 共通サービスを止める → CLIはnot-sentで何も記録しない。ページは「取得不調」で操作を止める。
  - 戻すと、両方とも戻る。
- 戻しの試験：
  - 切り替えのやり方ごとに試す（`BREAKDOWN.md`の補正2回目の1）。共通サービスを止めて鍵が外れたことを確かめ、互換の`serve.py`を起動する。
  - 環境変数のない`comm.py letter inbox`と`approvals.py list`が、同じ記録を返す（`DEFAULT_URL`を変えた場合は、その差し戻しのあとで）。
- 受入の証拠：base・パッチのhash・試験のログ・否定対照。否定対照は次の3つで、それぞれ、どの試験が落ちたかを記録する。
  - 鍵を外す。
  - 中継でunknownをnot-sentにする。
  - watchが出た連絡を捨てる。
