# OPS-056 試作：ゲートとtaskに効く判断を一覧にする

2026-10-16 / Claude（姫、Opus 5.5）。依頼は`Maintanance/CLAUDE_TASK.md`のOPS-056、詳細正本は[ASTRA_DECISION_TRACE_SUPPORT.md](../ASTRA_DECISION_TRACE_SUPPORT.md)。
試作と評価であり、方式の採用ではない。一覧はすべて生成した写しで、判断の本文の正本は各原文である。

## 中身

| ファイル | 役割 |
| --- | --- |
| `marks.json` | 候補の印（実在の判断1件）。正本には書き込まず、原文を引用で指す |
| `test_marks.json` | 試験用の仮想例2件。`--test`のときだけ読む。実在の判断ではない |
| `digest.py` | 抽出器。`registry.json`と印から、判断・矛盾候補・待ち条件を出す（Python標準ライブラリのみ） |

| `out-MS-070.md` | 要望1の確認用（ユーザー実作業を判断待ちと分ける例） |
| `out-DOC-034-test.md` | 要望4の確認用（部分置換と矛盾候補）。仮想例を含む |

再生成はrepositoryの直下で `python3 Maintanance/Current/GateDecisionDigestPrototype/digest.py MS-060`（仮想例を混ぜるなら`--test`）。

## 要望ごとの結果

1. **ユーザー担当と判断待ちを分ける：** Registryの種別と状態で分けた。`[DECISION]`で`USER_ONLY`・`WAITING_USER`なら判断待ち、Userが担当で`[DECISION]`でなければユーザー実作業待ち、ゲートへ`material`の辺で届くものは材料待ち。
   どれにも当たらないものは状態をそのまま出す。DONEは「中身は原文で確認」とし、肯定の判断として扱わない。
   `out-MS-070.md`では、RELEASE-072・075・076（`USER_ONLY`・`[EXECUTION]`）が**ユーザー実作業待ち**に、DOC-036・DOC-037（`[DECISION]`）が**判断待ち**に分かれた。原提案の版は、この二つを同じ「判断待ち」に混ぜていた。
2. **上流探索を入口にし、辺の意味を残す：** 各taskに、ゲートへ向かう辺と、その意味（`SEQUENCE`・`required`・`material`など）を付けた。
   taskを選んだときは、自身・直接の前提・**下流のゲート**を範囲に入れる。これで、ゲート（MS-060）に付いた判断が、ゲートの上流にあるDOC-034へも届く。
3. **原文へ辿る：** 印は原文の引用を持ち、抽出器が実物に引用があるかを確かめ、行番号とファイルhashを出す。実在の判断は、3か所で同じ文を確認できた（RELEASE_0_8_0.md:21、RELEASE_0_6_0.md:91、Registry DOC-034行）。
   引用が見つからなければ「引用不一致（要確認）」と出す（原文が書き換わったことの検知）。
4. **置換は明示されたものだけ：** 印の`supersedes`に書かれた条項（clause）だけを「置き換え済み」にし、残りの条項は有効のまま出す（`out-DOC-034-test.md`で、`fix-count`だけが置き換わり、`verify`・`record`・`defer`が残る）。
   置換の記載がなく、同じ話題で日付の新しい印は「矛盾候補」として出し、自動では失効させない。
5. **印は候補、複数対象に対応：** 1つの印に`targets`を複数書ける（実例は6件：MS-060、DOC-034、DOC-035、MS-080、DOC-038、DOC-039）。既存文書への印付け、書式の制度化、全履歴の走査はしていない。

## 見つかった欠陥（未修正）

- **置換の範囲が対象taskに絞られない。** 試験用の`TEST-partial-narrow`は対象がDOC-034だけなのに、DOC-035を選んでも`fix-count`が「置き換え済み」と出る。置換を条項単位で全体に効かせているため。
  直すには、置換を「条項×対象task」の組で持つ必要がある。印の形が一段重くなる。
- **分類はRegistryの文字列に頼る。** `[DECISION]`の書き方や状態名が変わると、分類がずれる。
- **印のない判断は拾えない。** 今回は実在の判断1件にだけ印を作った。詳細正本の本文を読む処理はなく、語の照合もしていない。

## 減らせる負担と、増える負担

| | 中身 |
| --- | --- |
| 減る | ゲートやtaskの前に、効いている判断・待ち条件・原文の場所が1回の実行で出る。判断待ちとユーザー実作業待ちを読み分ける手間が消える。原文の書き換えを引用不一致で知れる |
| 増える | 判断を記録するたびに、印を1件書く（対象・条項・原文の引用）。今回の1件で約20行のJSON。判断を変えるときは、旧判断の`supersedes`も書く |
| 試作で分かったこと | 実在の判断1件が、原文3か所に同じ文で書かれていた。正本に書く判断が増えるほど同じ文が複数の場所へ散る。それを1つの印でまとめて指せる点は効いている |

## 率直な評価

Astraが日常で使うには、**印の記録の手間がまだ重い**。条項を分けて引用を書くのは、判断のたびにやるには面倒で、抜けやすい。

もっと簡単な案として、印を分けずに、**Registryの行に「効いている判断」への短いリンクを1つ書く**だけでも、要望2・3の大半は満たせる。抽出器はそのリンクを辿って原文を見せればよい。
置換と矛盾の検出（要望4）が本当に要るのは、判断が覆ったときだけなので、そのときだけ`supersedes`を書く運用にすれば、平時の手間はほぼ増えない。

## 推奨する次の一歩

1. 印は「判断が覆ったとき」と「ゲートに効く判断」だけに付ける。それ以外は、Registry行からのリンクで足りるか試す。
2. 置換を「条項×対象」で持つかは、実際に部分置換が起きたときに決める（今は仮想例しかない）。
3. 使い続けるなら、Registry Studioに「ゲートの判断」タブとして載せる。今の`digest.py`の分類と範囲の決め方をそのまま移せる。
