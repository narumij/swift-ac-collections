# Public API naming decisions

## TL;DR（人間向け）

採点と議論を経てユーザーが確定した公開API名の正本。`ElementBuffer`／`OptionalElementBuffer`（1Dは接尾辞なし、2D〜4Dに接尾辞）、多次元のラベル、`element(at:)`／`setElement(_:at:)`、借用参照の`reference(at:)`と標準の`MutableRef`、`NextPermutationModule`とその通常版・借用版のAPI名を採用した。実装と移行計画は名前の選択とは別に管理する。

Status: current naming decisions are adopted. Implementation and migration planning are tracked
separately from the choice of public names.

## Purpose

This is the authoritative record of public API naming decisions produced after scoring and
discussion. The score report, ChatGPT discussion, and reviewer agreement are inputs; none of them
adopts an API by itself. The user makes the final public decision.

Record conclusions rather than conversation transcripts. Preserve material rejected alternatives,
accepted review observations, user priorities, reservations, and implementation consequences so
the decision can be understood and applied later.

| Always-initialized owner base | Adopted | `ElementBuffer` | `BareElements`, `FixedShapeElements`, `BareArray`, `FixedArray`, `HeapArray` | Round 2 converged on `ElementBuffer`: the user scored it neutral 5 and both AIs scored it 7 after reviewing all first-round reasons. | Presence-tracked owner base | Adopted | `OptionalElementBuffer` | `OptionalCache`, `MemoizationTable`, and the other round-1 candidates | Round 3 converged after comparing the promise made by each finalist. `OptionalElementBuffer` identifies the adopted ElementBuffer family and communicates that individual elements may be absent without promising cache policy or restricting the type to memoization | Prefer family coherence and storage semantics over a shorter use-case name; accept the longer spelling as the cost of avoiding false cache behavior | Rename the 1D owner to `OptionalElementBuffer`; with the adopted suffix rule, use `OptionalElementBuffer2D`, `OptionalElementBuffer3D`, and `OptionalElementBuffer4D`. Update production, tests, benchmarks, and documentation together | 2026-10-13 |
| One-dimensional suffix | Adopted | Unsuffixed 1D for both owner families; append `2D`, `3D`, and `4D` for higher ranks | Explicit `1D` for both; preserve the current asymmetry | Codex and Claude independently preferred one predictable base-case rule. Keep higher-rank suffixes explicit and apply the same rule to both families | 2026-10-13 |
| Multidimensional labels | Adopted | `width`, `height` and `depth` for 2D and 3D; `size0` to `size3` for 4D | Unify all ranks on `sizeN`; align the 4D numbering with the old chained-subscript order | The cross-cutting naming decision settled both owner families as one naming system. | Copied value access | Adopted | `element(at:)` / `setElement(_:at:)` | `value(at:)` / `setValue(_:at:)` | Codex and Claude independently preferred the current `element` vocabulary because it names stored elements and does not blur reference-element identity with copied-value access. The user accepted the aligned AI recommendation | Preserve element identity and use the existing tested vocabulary | No production rename. Keep both Array families, tests, benchmarks, and documentation on `element` / `setElement` | 2026-10-13 |
| Borrowed-reference method | Adopted | `reference(at: ...)` | `mutableElement(at: ...)`, `elementReference(at: ...)` | After `MutableRef` was adopted as the result type, round 2 converged on the current short method. The result type already communicates mutability, so repeating it in the method adds less value | Preserve the compact existing call site and let `MutableRef` carry the result semantics | Keep `reference(at:)` for every ElementBuffer rank and update its declared return type and documentation to the canonical `MutableRef` name | 2026-10-13 |
| Borrowed-reference result type | Adopted | Standard-library `MutableRef` directly | Contextual `Reference` alias; project-owned compatibility type; `MutableElementReference` | The current Prime Codex and Claude independently ranked direct `MutableRef` in their top group, and the user accepted that public type identity. After inspecting the standard API and source implications, the user replaced the project-owned lookalike with Swift's `MutableRef` directly | Prefer the standard contract over maintaining a same-named project type. Accept the resulting OS availability boundary instead of silently recreating the type for older environments | `reference(at:)` is mutating, returns the standard-library `MutableRef<Element>`, and is available on Apple OS 27 or later. Callers use its standard `value` property. Compatibility for earlier environments is not provided by this API | 2026-10-13 |
| Borrowed-reference property | Excluded |  | `pointee`, `value` | Round 3 scored both spellings before identifying Swift's existing `MutableRef.value`. The project does not own this vocabulary after adopting the standard type | Do not turn a standard-library API into a separate product naming preference | Preserve the scores only as deliberation history. Tests, benchmarks, fixtures, and current documentation follow the standard `value` property without treating it as a project naming decision | 2026-10-13 |
| Permutation module | Adopted | `NextPermutationModule` | `PermutationModule` | The three-party final-proposal review agreed that the module should share the `NextPermutation` stem with its central entry point and owner. Whether and how to retain `PermutationModule` is not part of the naming decision; settle it in the subsequent migration plan | 2026-10-15 |

| Permutation normal API family | Adopted | `nextPermutations()` / `NextPermutations` / `NextPermutations.Permutation`; generic parameter `Element` | Existing spellings except the former generic parameter; rejected candidates are preserved in the score reports | The entry point and owner already express lexicographic successor generation.
