# Registry V3移行レポート — Astra

## TL;DR
Markdownを人とAIのプロトタイプとして使ってきたRegistryを、構造はSQLite、理由や仕様はMarkdownという分担へ移した。2026-10-19に本番起動と保存・再開・正式反映を確認。実画面の人間操作を全面検証したものではない。

## 対象と到達点
OPS-167。初期設計の一部は引継ぎ記録による把握、終盤の受入と本番確認はAstra自身の実行。95 task、8版、29到達点、最終130参照文書。初回取込は差分ゼロ、世代gen-1d0b9780ab114593931e911eb83e1ae2、基本確認後revision 2。入力・backup・manifestは採用した外部backupフォルダへ保存した。

## 責任の分離
ユーザーが目的、版順の正本、正本を先に作る登録条件、本番配置と切替を決めた。姫が限定実装・試験・返却、Astraが範囲の整理・独立検証・採否・commit・切替を担当した。DBがtask、依存、採番、版順、focus、card完了記録を保持する。Markdownは理由・規則・文書を保持し、DB管理表は生成viewになる。編集保存は正式反映と別で、旧保存は保持・個別照合する。

## 段階移行と検出した問題
- 9572da7d4：既定offのserver接続。並行更新の途中で旧内容と新revisionを組み合わせる不具合を単一read snapshotで補正。
- 0b2685684：隔離起動、DBを残す取込、生成view公開。所有しない一時ファイルを削除し得る実装を補正。複数ファイル公開は全体atomicではなく、部分公開を報告し再実行する契約とした。
- db90a08b8：Astraの部分commitで欠落した試験補助ファイルを追加。
- 223292617：V3文書生成を旧folder構造検査から分離。新しい版がDBにあっても文書更新が止まらない経路を確認。読取専用指定の黙殺を拒否へ変更。
- cca515693：既存機能の移行漏れだったfocusとrecordedDone更新を追加。到達表示と完了記録を分離。
- 1b8ff1892、16871fc17：本番DB正本化、生成view、基本確認。ユーザーがサーバー停止・起動を行った。

姫のnegative controlでlocal-tools.jsonの確認日時が更新された事故は、試験対象とは独立した一時環境設定で対処した。設定値は同じとの返却で、日時を推測復元しなかった。Astraの本番確認での対象欄/送信ヘッダー誤りは保存前の拒否で終わり、既存client経路で再実行した。

## なぜ判断依頼が改善したか
観察：姫の候補をそのまま判断一覧として返さず、既決事項、調査で判明する事実、実装選択、ユーザー方針へ分けた結果、版順と文書先行登録の2点を具体的に聞けた。

なぜ分けられたか：設計だけでなく、旧保存と新規版/cardの挙動を実装・試験で確かめ、廃止しようとしていた操作が既存機能だと照合できた。なぜ照合できたか：固定ID、正本、返却、commit、生成データが同じ対象を指していた。なぜその対応ができたか：ユーザーが概念の境界と正本の所在を継続して選び、AIに任せる方法とユーザー判断を区別してきた。

これは具体例に基づく因果仮説で、比較実験ではない。使用量・判断精度の改善率や他チームへの一般性は未測定。ユーザーの方針決定と訂正をAIの自発的成果へ読み替えない。

## 巻き取りと負荷
背後の調整役から引き取るときは、過去の考えを再現するより、現在の割当・採用済み境界・未決・証拠を復元する必要があった。姫の成果を検証する仕事とは別である。終盤に細部を抱えすぎ、待機の終了と部分commitで失敗した。判断キャッシュやDBがあっても、担当が現在の境界を選ばなければ負荷は戻る。

## 保証範囲と残す制約
独立試験は281件、最後の限定操作は追加6件。姫は全287件とproduction試験成功を報告。本番はAPI保存/再開、CLI反映、DB/HTTP/seed/view照合、backup検証を実施。harnessは実画面操作と同一ではない。

複数view公開には単独writerが必要。viewはDB更新直後に古くなり得る。復元後は最新発行境界が分かるまで書込停止。backupは同じ端末上であり全損保証ではない。旧folderやHEADはV3構造の正本ではない。これらを消すための拡張は今回の完成条件に含めない。
