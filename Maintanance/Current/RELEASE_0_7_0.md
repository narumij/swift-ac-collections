# Release 0.7.0

## マイルストーンとしての管理 2026-10-16

RELEASE-079は重複する独立ゲートとしてEXCLUDEDとし、本書へ集約した。到達範囲と開始のユーザー判断は[リリース手順](../User/RELEASE_PROCESS.md)の候補採用判断へ接続し、同じ判断を再度求めない。最終リリース判断は別段階として維持する。調査・前提充足は開始許可ではない。管理入口は[マイルストーン管理](../MILESTONES.md)。


最終更新: 2026-10-15 / Codex

## 現在の状態

0.6.0 release完了待ち。これはactive release Registryではなく、0.7.0のrelease検討を開始するための
入口と判断境界を保持する文書である。主要タスクはリリース工程準備とSPI登録・公開導線整備に確定。現時点ではrelease候補commit、その他の製品上の到達範囲、
branch方式、下記で確定した文書Validation計画レビュー以外の必須gate、tag位置を確定しない。

`_ReleaseTask/`へ人間向け工程表をコピーする前の段階では、release、branch作成、commit、tag、push、公開を
許可しない。

## Release検討開始条件

0.6.0 releaseが完了し、その完了証拠と0.6.0へ含めた範囲・後続へ残した範囲が現行記録から確認できることを、
0.7.0のrelease検討を始める前提とする。

前提が満たされたことだけでは、0.7.0の開始、到達範囲、残taskの採用、凍結解除は成立しない。開始判断に向けて委任された範囲で、0.6.0後の公開面、残課題、品質・文書状態を判断材料として揃え、
0.7.0へ含める製品上の到達範囲とrelease作業を開始するかを一つの判断として確定する。

## 開始判断までの依存

0.6.0のrelease作業が具体化した時点で、その完了を表すtaskと証拠の置き場を確認し、本書から参照する。現時点では0.6.0の完了taskが存在しないため、架空のtaskや依存辺を作らない。

0.6.0から後続へ残したtaskは、その状態、担当、再開条件を維持する。0.7.0の候補になり得ることを理由に、
`FROZEN`を解除したり、`PROPOSED`を採用したり、`USER_ONLY`へ着手したりしない。

## Release作業の起動

開始条件に到達したら、次の順序で起動する。

1. 0.6.0の完了記録、以後の差分、未完了task、品質・文書状態を確認する。
2. 0.7.0へ含める変更と後続へ残す変更、version固有要件の候補を分ける。
3. ユーザーへ、0.7.0の製品上の到達範囲とrelease作業を開始するかを一問で確認する。
4. Yesの場合だけ、`../User/RELEASE_PROCESS.md`を`_ReleaseTask/`へコピーし、versionを実値へ置き換える。
5. 確定したbranch方式、必要な品質gate、version固有taskを人間向け工程表と通常Task Registryへ反映する。
6. release中の状態と証拠は人間向け工程表と各工程の正本へ記録し、完了または中止時に本書と通常Task Registryへ還元する。

人間向け工程の正本は`../User/RELEASE_PROCESS.md`とする。release専用Task Registryを別に作らない。

## 0.7.0固有要件

### リリース工程準備・公開運用整備

2026-10-16、ユーザーが工程準備を0.7.0側へ配置すると決定した。次の既存作業をここへ接続し、0.6.0の前提にはしない。

| 既存作業 | 0.7.0で扱う内容 |
| --- | --- |
| RELEASE-072 | 人間向け工程表が実際の現在位置・次の操作・証拠・停止点を追えるか確認する |
| RELEASE-075 | 判定基準、証拠取得、停止・復旧などの不足仕様を充当する |
| RELEASE-076 | 充当後の工程をValidation & Verificationする。RELEASE-075への依存を維持する |
| [整形依頼手順書](RELEASE_SHAPING_WORKER_REQUEST_DRAFT.md) | 再利用するワーカー依頼の原型を完成させる。個別releaseの整形実行とは分ける |

上記3taskはUSER_ONLYを維持する。配置変更は着手・代行・完了認定ではない。工程の実作業は必要な単位で具体化する。

0.6.0から移したPages要件：main由来deployの停止、release tag commitからの利用者文書生成、warningをerrorとして検査し検証済み文書だけを公開すること、workflow変更と残る公開経路の記録。実装は0.7.0の工程を具体化してから限定taskへ分ける。本整理でworkflowを変更したり、同じ仕事を重複登録したりしない。

品質は0.7.0を含む各0.x.0で改善する。前版からの変更・残課題に応じた検証と評価を行い、結果と未確認範囲を次版へ渡す。工程整備の完了を製品品質の合格には読み替えない。

### 文書Validation計画レビューのゲート

2026-10-16ユーザー判断。[文書Validation計画のレビュー](DOCUMENTATION_MILESTONES.md#validation計画のレビュー旧doc-032)を0.7.0リリース前のゲートとする。計画の目的・対象・試行方法・判定境界を確認し、レビュー結果と指摘への対応・保留の扱いを同正本へ記録する。現在は未通過。0.6.0の前提にはしない。

ここで確認するのは計画であり、SPI登録後に行う公開ドキュメントの人間レビュー実施は、引き続きSPI登録後から1.0品質判断までに置く。今回の配置は計画レビューや試行の実施・完了認定ではない。

### リリース後のSPI公開

2026-10-16、ユーザーが0.7.0の主要タスクをSPI登録・公開導線の整備と決定した。順序は次のとおり。

1. 必要な検証と最終判断を経て0.7.0をリリースする。
2. 対象版の公開準備をQUALITY-005で判定し、ユーザーの登録可判断と実行委任を得る。
3. DOC-026でSPIへ登録し、package page・互換性表示・DocC結果を確認する。
4. DOC-027で確認済みURL・badgeをREADME・Pagesへ接続する。

登録結果の確認までを「0.7.0の公開整備」として管理する。SPI登録完了をrelease前の条件には置かない。詳細は[SPI公開マイルストーン](SPI_PUBLICATION_MILESTONE.md)へ接続する。登録後の人間レビューは文書が落ち着いてから1.0品質判断までに行い、0.7.0 releaseの前提にはしない。

その他のversion固有要件は未確定。0.6.0の未完了事項や既存taskを、そのまま0.7.0の必須要件へ昇格させない。
開始判断のための照合で必要性、影響範囲、担当、受入条件を確かめ、独立した仕事が必要な場合だけ通常Task Registryへ
追加する。新しい製品判断または公開上の選択が見つかった場合は、推測で埋めず判断taskへ分ける。

## 権限境界

- 0.7.0の製品上の到達範囲とrelease検討開始はユーザーが決定する。
- branch作成、commit、tag作成は、それぞれ直前にユーザーの明示許可を得る。
- candidate branch push、GitHub merge、tag pushはユーザーが実行する。
- Codexは各報告後に対象commitまたはrefをremoteから確認してから後続へ進む。
- release pageやその他の公開操作を行う場合も、対象を示して別途判断する。
