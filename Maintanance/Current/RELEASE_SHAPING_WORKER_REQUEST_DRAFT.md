# リリース整形：ワーカー依頼手順書（ドラフト）

作成者：Astra / 2026-10-16

今後の各リリースでコピーして使う依頼書の原型。未発注であり、このファイルを読むだけでは作業を開始しない。
ユーザーのリリース手順書を置き換えず、今回の版の提供範囲や公開判断を決めるものでもない。

2026-10-16、ユーザー決定により本手順書の完成は0.7.0のリリース工程準備へ配置する。0.6.0の前提にはしない。具体的な整形作業は引き続き未発注。

## 完成後の配置（ユーザー指定）

本手順書の作成が完了したら、`Maintanance/User/RELEASE_SHAPING_WORKER_REQUEST_DRAFT.md`へ移動する。これは各リリースの整形作業の完了ではなく、再利用する手順書自体の完成を指す。ドラフト作成中は現在の配置を保つ。

移動後はユーザー指定の配置として保護し、通常の文書整理・圧縮・アーカイブの対象として移動・改名しない。配置を再変更する場合は、ユーザーの明示指示に従う。完成時の移動では参照元も更新し、Currentに別の正本を残さない。

## 目的と分担

mainから分けたリリースブランチを、その版の配布に必要な形へ整える。mainの開発資材と互換コードは残し、整形した変更はmainへ戻さない。整形後の候補を検証し、最後はユーザーがタグを付けて工程を終える。

- ユーザー：対象版・提供範囲を決め、ブランチ作成、push、PRでの試験起動、リリース判断、最終処理を行う。
- 調整役：依頼範囲と入力をそろえ、ワーカーの差分・検証証拠を受け入れ、Task Registryと工程へ接続する。整形のソース実装を兼任しない。
- ワーカー：明示されたリリース用作業領域で整形・ローカル検証を行い、成果を返す。自ら公開や提供範囲を決めない。

## ワーカーへの依頼本文

あなたの担当は、この依頼書に記入されたリリース候補の整形とローカル検証です。以下の順に進め、依頼本文の条件を自分で変更しないでください。

### 1. 作業位置を確かめる

- 指定されたcheckout、ブランチ、開始SHA、未commit変更を確認する。
- mainや開発ブランチでは削除しない。他の担当の未返却変更があれば整形を開始しない。
- 入力資料と固定ID、今回の許可範囲を確認する。記載に矛盾や不足があれば、その箇所と影響を返す。

### 2. 整形対象を照合する

指定された削除一覧を実物に照合し、残すものとの依存を確認する。

| 対象 | 扱い |
| --- | --- |
| 互換コード | 今回指定された互換機能だけを除去する。旧module名、互換モード、過去の実装という理由だけで一括削除しない |
| manifest・import・再公開・条件分岐 | 指定された除去に必要な範囲だけ整合させる。新たなAPI変更や再設計は行わない |
| 内部資料 | 指定された資料を除去する。利用者向け文書、ライセンス、帰属表示、DocCの入力・リンク先は区別する |
| benchmark結果 | 指定された生成結果を除去する。性能比較に必要なSources、Package.swift、Libraries、スクリプトは残す |
| Tests・fixture・CI | 候補の品質確認に必要なものを残す。廃止対象専用testの扱いも削除一覧に根拠を記す。通すために検査を弱めない |
| AGENTS.md | ワーカー作業と受け入れが済むまで残す。最終削除はユーザーが行う |
| 作業依頼・返却記録 | 削除後も調整役が照合できる場所へ保つ。作業中の記録を消さない |

ファイルの接頭辞、`Documentation`という名前、manifestの`exclude`指定だけでは不要と判断しない。除去対象をmanifestが参照している場合は、その参照も整合させる。

### 3. 整形する

互換除去、内部資料整理、計測結果整理を、差分を追える単位に分ける。各単位で削除・変更したものと残した理由を記録する。関係のない整形やリファクタリングを追加しない。

commitは許可されたときだけ、上の単位に沿って分ける。未許可の場合は、返却に推奨commit区分を書き、未commitで返す。push・merge・tagは行わない。

### 4. 整形後の実物を検証する

- packageのproduct・target・参照パスが、今回残す公開面と一致することを確認する。
- 変更範囲の狭い試験から始め、必要なDebug・Release・Death Testを実行する。通常の寿命検査を無断で除外しない。
- DocCの生成と削除に伴うリンク切れ、benchmark packageと候補CIが必要とする資材の残存を確認する。
- コマンド、toolchain・OS、対象、件数、終了status、skip・除外、ログ保存先を返す。未実行を成功としない。
- macOSのローカル成功とLinuxの候補CI成功を区別する。ASanとDeath Testの個別成功を、併用成功とはしない。

不具合、残す公開面との衝突、未決の削除範囲が見つかったら、その影響部分を止めて根拠を返す。製品修正や提供範囲変更を整形の名目で進めない。

### 5. 返却して占有を手放す

指定された返却ファイルへ次を記入する。

- 対象版、checkout、ブランチ、開始SHAと終了SHA（未commitならその旨）。
- 整形の区分ごとの変更ファイル、削除理由、残す公開面への影響。
- 実行した検証と証拠、未確認・失敗・保留。
- commit一覧、または推奨commit区分。
- 返却対象と「この範囲の変更を終了し、占有を返却する」旨。

返却後は、再委任まで成果を書き換えない。Task Registryの受入・完了更新は調整役が行う。

## 返却後の接続（ユーザー・調整役）

1. 調整役が差分と証拠を独立確認し、受け入れ結果を記録する。
2. ユーザーが候補をpushし、確認用Draft PRを用意する。このPRはmainへの統合用ではない。
3. コメント起動workflowがデフォルトブランチへ反映済みなら、ユーザーが `/test release` を新規コメントする。
4. 結果の対象SHAが試したい候補と一致することと、必要な各試験の結果を確認する。追加変更後はそのSHAに対して再検証する。
5. 公開判断後、ユーザーがAGENTS.mdの削除をcommitし、最終commitへ版タグを付ける。以後はAI作業へ戻らない。検証済み候補からの差分がその最終削除だけであることを確認する。
6. 整形差分をmainへmergeしない。確認用PRを閉じる。

上の接続は今回の会話に基づくドラフト案。`Maintanance/User/RELEASE_PROCESS.md`は未変更であり、候補tag方式との使い分けを含む正式工程への反映はユーザーが決める。
