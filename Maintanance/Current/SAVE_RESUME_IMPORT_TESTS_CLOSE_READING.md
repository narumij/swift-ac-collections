# 保存・復元・Inbox取り込みの試験の精読

CP-20261020-010。

- 対象の試験：`test-serve.py`（`test_save`ほか）、`v3/test_v3_inbox.py`（16件）、`v3/test_browser_roundtrip.py`、`v3/test_mixed_workspace_browser.py`、取り込みに関わる`v3/test_change_groups.py`・`test_structural_groups.py`・`test_proposal_registration.py`
- 突き合わせた実装：`inbox.py`（append_save・latest・record_import・read_imports）、`serve.py`の`save`・`save_v3`・`get_workspace`、`index.template.html`の保存・再開・更新の処理（`resumeWorkspace`・保存ボタン・`beforeunload`）、`v3/studio_adapter.py`の`apply_groups`
- 基準：HEAD `78afefa93`
- 試験は実行していない。判断はすべてコードを読んでのもの。
- 「復元」は、保存した編集版をサーバーの再起動のあとに再開すること、と読んだ。V3 DBのbackupからの復元は、CP-20261020-008で読んだ。

## 指定の3点

### 1. 保存成功と表示した内容が、再起動後も戻るか

- 守られていること：
  - 保存は1回ごとに新しいファイルを作る（`open('x')`）。上書きも削除もしない。
  - 画面が「サーバーに保存しました」と出すのは、サーバーが200を返したあとだけ。失敗すれば「保存できませんでした（編集はそのまま残っています）」と出る。
  - ページを開くと、`/workspace`から最新の保存を読み、それを再開する。
  - 試験：新しいブラウザのcontextで開き直すと、保存した編集が戻る（`test_save_reopen_apply_and_replay`、`test_only_the_v3_save_resumes`）。「更新」で読み直しても、同じ保存が戻る（`test_refresh_keeps_the_resume_and_the_stale_notice`）。壊れたファイルがあっても、正しい保存が再開される（`test_bad_files_are_listed_and_the_valid_save_resumes`）。
- 戻らないことがありうること：
  - サーバーを再起動して再開する試験はない。試験は、同じサーバープロセスのまま、ブラウザを開き直しているだけ。ファイルに書いているので同じに戻るはずだが、確かめてはいない。
  - 書いたあとに`fsync`をしない。200を返したあとに電源が落ちたり、OSが止まったりすると、ファイルが残らないことがありうる。
  - 書く途中で失敗（ディスクが一杯など）すると、名前の付いた途中までのファイルが残る。画面には500が出て正しく失敗と出るが、壊れたファイルは消えずに残る（再開はされず、一覧に「読めない」と出る）。`test_save`は`append_save`をmockにしているので、この場合を試していない。
  - 再開するのは、すべての系列の中で一番新しい保存。タブAで保存したあとにタブBで保存すると、再起動のあとに戻るのはBになる。画面には「別の系列の保存もあります」と出るが、Aの内容は戻らない（ファイルとしては残っている）。
  - 保存の順は、サーバーの時計（savedAt）で決まる。時計が戻ると順がずれる。
  - 同時の保存を守る鍵（`LOCK`）は、プロセスの中だけ。再起動で古いサーバーと新しいサーバーが重なった場合は守れない（保存IDに乱数が付くので、ファイルは別になる）。

### 2. 正本の更新で、未反映の編集が消えたり上書きされたりしないか

- 守られていること：
  - Inboxの保存は、正本の更新（sync、DBへの適用）で書き換えられない。保存は、そのときの土台（legacyはsha256、V3は世代と改訂）を持つ。
  - 再開した画面は、保存した土台と最新の正本を比べて「正本が更新されています」「DBが更新されています」と出す。三方の比較（`canonicalDifferences`）で競合の候補も出す（`test_other_field_changed_meanwhile`、`test_same_field_conflict`、`test_refresh_keeps_the_resume…`）。
  - 未保存の編集があるときは、「更新」も「正本から新しく始める」も止まる。ページを閉じようとしても警告が出る（`beforeunload`）。
  - V3の適用は、保存の前提の値で確かめる。古い前提の変更は、上書きせずにconflictになる（CP-20261020-008）。
  - 古い形式の保存は、V3の画面では再開しないし、消さない。件数を知らせる（`test_newer_legacy_is_reported_not_resumed`、`test_only_the_v3_save_resumes`）。
- 試験の抜け：
  - 画面の「更新」「新しく始める」を未保存の編集があるときに止めることと、`beforeunload`の警告は、試験で確かめていない（コードにはある）。
  - V3の画面では、古い形式の未反映の編集は件数しか出ない。中身はAIが1件ずつ照らすまで見えない。消えはしないが、気づかれずに残りうる。

### 3. 取り込みの一部失敗・再実行で、変更が抜けたり二重適用されたりしないか

- V3の取り込み（`apply_groups`）：
  - 守られていること：
    - 変更のまとまりごとに、保存IDとまとまりのIDから操作IDが決まる。同じ取り込みをもう一度すると、記録した結果が返り、二重には入らない（`test_replay_of_a_adds_no_revision`）。
    - 中身を変えて同じIDで入れようとすると拒否される（changedContent）。
    - 一度使った削除や追加は、ほかの形では使えない（`Interleaving`）。
    - 途中のまとまりが拒否されても、入ったものと入らなかったものを分けて返し、`complete: false`になる（`test_partial_results_are_reported`）。
    - 選ばなかったまとまりは残る（`test_unselected_groups_stay_intact`）。
  - 二重に入りうること：
    - 同じ編集を、再開してから保存し直すと、新しい保存IDになる。taskの変更は「反映済み」、線の追加は「すでにある」で拒否されるので、二重にはならない。
    - ただし下書きのtask（提案）は、保存IDと下書きIDの組で番号が決まる。保存し直した保存では、祖先の保存（`ancestors`）を取り込む人が明示しないと、別の番号でもう一度登録される。
    - 系列の親は`studioSave.parent`に記録されているが、adapterもCLIもそれを使わない（推測しない設計）。祖先を書かずに`independent`と書けば、二重登録になる。
    - 試験は「祖先を明示すれば保留になる」「独立と書けば別の番号になる」ことだけを見ている。取り込みの手順が、系列から祖先を渡すことを確かめる試験はない。
  - 取り込み済みかどうか：
    - V3の保存では、どこまで入ったかがDBの操作にしかない。Inboxの一覧（`inbox.py list`）は、V3の保存の取り込みの状態を出さない。
    - 「この保存は全部入ったか」は、そのたびに`plan_groups`と操作を突き合わせないと分からない。
- 古い形式の取り込み：
  - 正本のMarkdownを、AIが手で直す。そのあと`record_import`で記録する。この2つは1つの取引ではない。
    - 直したあとに記録できなければ、記録がないので、もう一度取り込まれうる。
    - 記録だけして直しが抜ければ、抜けたまま「取り込み済み」になる。
  - `record_import`が防ぐのは、同じ保存IDを二重に記録することだけ。二重の適用は防がない。
  - 記録の鍵（`LOCK`）はプロセスの中だけ。CLI（`inbox.py record`）は別のプロセスで動くので、2つ同時に記録すると、両方が重複の確かめを通りうる。
  - 書いたあとに`fsync`をしない。書きかけの行が残れば、そのあと記録の状態は「不明」になり、記録できなくなる（止まる側に倒れる。`test_record_is_refused_while_unknown`、`test_malformed_records_are_unknown`）。
  - 取り込みの手作業は試験の外。

## まとめ

- 消さない・上書きしない（新しいファイルだけを作る、正本の更新で保存を触らない、前提が古ければ競合にする）は、しっかりしている。V3の取り込みの再実行は、操作IDで二重にならない。
- 弱いところは4つ。
  1. サーバーを再起動して再開する試験がなく、書込みに`fsync`もない。「保存しました」のあとに失われうる。
  2. 書込みの途中で失敗すると、壊れたファイルが残る。その場合の試験もない（mockで飛ばしている）。
  3. 保存し直した編集の下書きtaskは、取り込む人が祖先を書かないと、二重登録になる。系列の親の記録は使われていない。
  4. 古い形式の取り込みは、直すことと記録することが別々で、二重の適用も、抜けたままの「取り込み済み」も起きうる。手作業の部分で、試験の外にある。
