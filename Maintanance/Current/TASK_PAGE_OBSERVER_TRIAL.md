**4. 検証（提案）**
- モデル中心の検証：
  - Python（中心）：`test_canonical_state.py` で `CanonicalState` を直接試験する（`test_work_letter_state.py` の形にならう）。
    - `update` で revision が進み、`comparable` は決めた欄だけになる。
    - 同じ内容なら revision は進まない。
    - `failure` で `failed` になり、値は保たれる。次の `update` で戻る。
    - `wait` は revision が変わったときに返る。
    - V3と旧形式の両方の書き出しを入力にした場面を含める。
  - Python（つなぎ）：偽の `Changes` を鳴らすと、読み取りが1回呼ばれ、状態が更新されることを確かめる（`test_work_letter_state.py` 66–87 にならう）。
  - Python（回復、限定補正1）：`RETRY` を短くして、次を確かめる。
    - 1回目の読み取りが失敗し、2回目で成功する場面では、通知を鳴らさなくても、待ち時間が切れた後に `failed=false` になり、新しい値と新しい revision になる。
    - 成功している間は、待ち時間が何回切れても、読み取りの回数が増えない。
  - Python（順番、限定補正2）：1回目の読み取りの最中に `changed()` を鳴らし、そのまま古い値 v1 を返す偽の読み取りを使う。次を確かめる。
    - 2回目の読み取り（v2）が必ず走り、最後の状態は v2 になる。
    - revision は v1、v2 の順にしか進まない。
  - JS（順番）：偽の EventSource で、同じ `instance` の rev2 → rev1 の順に送ると、`suggestionSnapshot` は rev2 のまま変わらない。別の `instance` の rev1 は受け取る。最初の snapshot の前は案内が出ない。
  - JS（失敗したときの表示、一点補正）：反映済みで案内が出ている状態から始めて、次を確かめる。
    - `failed=true` の snapshot を受け取ると、`suggestionSnapshot` が `null` になり、案内が隠れる。
