# Task Registry V3 — 設計・調査

## TL;DR
タスクとマイルストーンをDBで扱う場合に、現在の概念の区別・フォーカス・俯瞰をどう保つかを設計する。ユーザー承認済み。編集欄のViewModel化（OPS154区切り3）の受入を開始条件とし、残りの共通配線とは分離する。実データの移行はまだ行わない。

## 依頼と境界

ユーザーは「その区切りでタスクレジストリV3着手できる？」に対する設計・調査の提案を承認した。まずDBに載せる構造とMarkdownに残す内容、現行との照合方法を整理する。現行Registry/Milestonesを引き続き正本とし、設計資料や実験DBはそれを置き換えない。

維持する要求：固定ID、状態・担当・親子と依存の区別、版内の順序、START/END/ゲート、HEADから現在区間を読む境界、全体を俯瞰するStudio、ユーザーの保存編集を取り込む手順。予定の変更と実際の到達を混同しない。

成果：概念と所有元の対応表、読み書き境界、少数データでの照合案、段階移行/戻し方、残るユーザー判断。既存の連絡DBをそのままタスクDBとみなさない。判断DBはOPS158の関連検討であり、無条件で統合しない。

開始条件はOPS154全体DONEではなく編集欄区切り3の受入。調査前に該当正本の受入記録だけ確認する。実データ移行、現行正本の削除、実稼働DBへのスキーマ追加は本taskの範囲外。

## 着手と設計案（2026-10-19 Astra）

OPS154区切り3を62fdebefeで受入済み。調査を開始した。姫への読み書き経路調査は連絡DBの `LTR-20261019-151D3013E51C409FBC27B1010BB7D39F`。以下は採用前の設計案であり、現行正本や原型仕様を変更しない。

### 概念と保存先の分担案

| 概念 | V3での候補 | 維持する境界 |
| --- | --- | --- |
| taskの固定ID・状態・担当・詳細正本参照 | DBのtaskレコード | IDは再利用しない。ACTIVEを実行中や開始許可と同一視しない |
| 親子・先行依存・到達点接続 | 区別した関係レコード | 所属から必須依存を推測しない。各グラフのDAG条件・端点存在を検査する |
| 版・中間カード順・ゲート | 版と順序、カードのレコード | START/ENDを含む派生骨格を機械生成。ゲート欠落による未接続を勝手につながない |
| HEAD・現在位置 | 明示的な現在位置レコード | 到達と予定変更を分離。既定照会は現在以後、全体表示は別の照会 |
| 方針・理由・仕様・技術資料 | 当面Markdownと参照 | 構造化に不向きな本文を無理に列へ分割しない |
| ユーザーの保存編集 | 未適用の変更提案と基準版 | 正本とは別。更新で消さず、衝突を黙って上書きしない |
| 実行・連絡の記録 | 既存活動/連絡DBの責務 | task状態と通信状態を混同しない。物理DB統合は未決 |
| 判断とコピー判断 | OPS158で別途設計 | 接続変更を判断の自動変更と扱わない |

原型仕様の保全：ノードIDは全体で一意、同一ノードの参照は同一定義を使う。管理と進捗のグラフを区別する。版内順序・ゲート位置・HEADによるフォーカスを保存形式に依存させない。フォルダ比較方法は利用者が定める事項であり、現行実装の比較方法をこの設計で規則へ昇格させない。

### 読み書き境界の案

最初は現行Markdown/フォルダ → 隔離したDB写し → 現行互換JSONの一方向とする。Studioへ渡すtask/辺/到達点/現在位置の意味を比較する。生成時刻や出典形式の違いを意味の一致と混同しない。

将来の正本切替後は、更新APIのみがDBへ書き込む案を優先する。期待する基準版と変更操作を渡し、検証・更新・履歴を同一トランザクションで確定する。再送には操作IDを使う。画面やAIがDBを直接書き換える経路は作らない。承認・委任と、DBが更新を受け付ける技術的条件は別に保つ。

照会は選択task・直接関係・現在区間・全体を分ける。DB化の効果は全件を安く読み直すことだけでなく、必要な範囲だけを確実に取得できることに置く。

### 採番の案

ユーザーの指摘を受け、採番の機械化も対象とする。prefixごとの使用済み番号・退役番号を取り込み、次番号の確保とtask登録を一つのトランザクションにする。IDの一意制約と操作IDによる再送判定で、並行登録の重複を防ぐ。登録後の取り消しは欠番を許容し、再利用しない。先に番号だけ予約する経路が必要かは、既存運用調査で確認する。

採番表とRegistryの二重手更新をなくす案だが、task化の必要性、分類、委任の判断は自動化の対象としない。移行時は現行行だけで最大値を決めず、採番表と退役済みIDを照合する。

### 移行の区切り案

1. 現行契約を確定し、少数fixtureでDB写しから同じ構造を取り出せるか比較する。
2. 書き込みを許さない写しで、現行一式との照合と現在区間/全体照会を試す。
3. 隔離環境で編集差分・衝突・採番の並行実行・再送・失敗時の全取消を試す。
4. ユーザーの切替判断後に正本を一つへ切り替える。旧Markdownを同時編集可能な第二正本にはしない。

切替前は写しを捨てれば戻れる。切替後はDBで受け付けた変更を保った書き出し/復元が必要で、古いMarkdownへの単純な巻き戻しは不可。切替・バックアップ・復元の手順が検証できるまで本番移行しない。

## 経路調査の受入と比較計画（2026-10-19 Astra）

姫の返却は上記連絡DBレターに保存。確認版62fdebefe。Astraは `sync.py:48,135,279`、`inbox.py:46,69,84`、Studio READMEの取り込み手順、TASK_RULES採番節を直接照合した。経路調査として受け入れ、未実装のDB方式の正しさまで認定しない。

確認できた重要点：
- `sync.build()`は旧JSONを入力とせず、Registry・Milestones・Rulesから再生成する。この読取境界をDB版と比較できる。
- 保存は追記方式で、古い親からの保存を別seriesとして保持する。正本との照合・正式採番・反映は現在AI手順であり、自動書込コードではない。
- `source.sha256`はRegistry単体で、Milestones全体を覆わない。フィールド比較は別に存在するため、これだけで変更を見逃すと断定しない。V3ではtask・関係・版・HEADを含む基準版と、対象フィールドの三者比較を組み合わせる案とする。
- 現行ゲート状態にはHEAD/名前からの派生がある。保存値と派生値を区別し、画面互換を確認する。現行実装を原型仕様や実際の到達判断の代わりにしない。
- 現行採番規則は、採番後に同じ編集内で取りやめても欠番を保持する。V3でも外部へ発行済みの番号をロールバックで再発行しない。未公開の内部候補値と正式発行を分けて試験する。

比較は次の3群へ限定する案：
1. 正常構造：恒久親子を含むtask、先行辺、3版と中央HEAD、中間カード、ゲート欠落、START/task/END接続、エスケープを含む条件文。
2. 拒否構造：重複ID、不明端点、循環、複数ゲート、存在しないHEAD。現行readerが拒否する箇所と後段検査が拒否する箇所を区別して記録する。
3. 保存差分：独立変更、反映済み、競合、古い保存、分岐series、追加案の正式ID変換、版移動、相談待ち接続。正本への二重適用を防ぐ。

比較対象はID・値・関係・順序・表示上の現在区間。sourceLine/raw/パス・hash・生成時刻などの出典表現は別枠で検査し、DBで同じ値を捏造しない。既存JSONを受け取るクライアントとの互換層が必要な箇所を一覧化する。姫案の「出力をほぼ完全一致」は、この意味比較と出典比較へ分けて採用する。

これは調査・設計の初稿。実fixture作成・DB実装・本番変更は未実施。次の設計区切りは、保存モデルと互換層の具体案を上記3群へ対応させ、実験の範囲を確定すること。
