## 依頼と境界

ユーザーは「その区切りでタスクレジストリV3着手できる？」に対する設計・調査の提案を承認した。まずDBに載せる構造とMarkdownに残す内容、現行との照合方法を整理する。現行Registry/Milestonesを引き続き正本とし、設計資料や実験DBはそれを置き換えない。

維持する要求：固定ID、状態・担当・親子と依存の区別、版内の順序、START/END/ゲート、HEADから現在区間を読む境界、全体を俯瞰するStudio、ユーザーの保存編集を取り込む手順。予定の変更と実際の到達を混同しない。

成果：概念と所有元の対応表、読み書き境界、少数データでの照合案、段階移行/戻し方、残るユーザー判断。既存の連絡DBをそのままタスクDBとみなさない。判断DBはOPS158の関連検討であり、無条件で統合しない。

開始条件はOPS154全体DONEではなく編集欄区切り3の受入。調査前に該当正本の受入記録だけ確認する。実データ移行、現行正本の削除、実稼働DBへのスキーマ追加は本taskの範囲外。

## 着手と設計案（2026-10-19 Astra）

OPS154区切り3を62fdebefeで受入済み。調査を開始した。姫への読み書き経路調査は連絡DBの `LTR-20261019-151D3013E51C409FBC27B1010BB7D39F`。以下は採用前の設計案であり、現行正本や原型仕様を変更しない。

### 概念と保存先の分担案

| 概念 | V3での候補 | 維持する境界 |
| --- | --- | --- |
| taskの固定ID・状態・担当・詳細正本参照 | DBのtaskレコード | IDは再利用しない。ACTIVEを実行中や開始許可と同一視しない |
| 親子・先行依存・到達点接続 | 区別した関係レコード | 所属から必須依存を推測しない。各グラフのDAG条件・端点存在を検査する |
| 版・中間カード順・ゲート | 版と順序、カードのレコード | START/ENDを含む派生骨格を機械生成。ゲート欠落による未接続を勝手につながない |
| HEAD・現在位置 | 明示的な現在位置レコード | 到達と予定変更を分離。既定照会は現在以後、全体表示は別の照会 |
| 方針・理由・仕様・技術資料 | 当面Markdownと参照 | 構造化に不向きな本文を無理に列へ分割しない |
| ユーザーの保存編集 | 未適用の変更提案と基準版 | 正本とは別。更新で消さず、衝突を黙って上書きしない |
| 実行・連絡の記録 | 既存活動/連絡DBの責務 | task状態と通信状態を混同しない。物理DB統合は未決 |
| 判断とコピー判断 | OPS158で別途設計 | 接続変更を判断の自動変更と扱わない |

原型仕様の保全：ノードIDは全体で一意、同一ノードの参照は同一定義を使う。管理と進捗のグラフを区別する。版内順序・ゲート位置・HEADによるフォーカスを保存形式に依存させない。フォルダ比較方法は利用者が定める事項であり、現行実装の比較方法をこの設計で規則へ昇格させない。

### 読み書き境界の案

最初は現行Markdown/フォルダ → 隔離したDB写し → 現行互換JSONの一方向とする。Studioへ渡すtask/辺/到達点/現在位置の意味を比較する。生成時刻や出典形式の違いを意味の一致と混同しない。

将来の正本切替後は、更新APIのみがDBへ書き込む案を優先する。期待する基準版と変更操作を渡し、検証・更新・履歴を同一トランザクションで確定する。再送には操作IDを使う。画面やAIがDBを直接書き換える経路は作らない。承認・委任と、DBが更新を受け付ける技術的条件は別に保つ。

照会は選択task・直接関係・現在区間・全体を分ける。DB化の効果は全件を安く読み直すことだけでなく、必要な範囲だけを確実に取得できることに置く。

### 採番の案

ユーザーの指摘を受け、採番の機械化も対象とする。prefixごとの使用済み番号・退役番号を取り込み、次番号の確保とtask登録を一つのトランザクションにする。IDの一意制約と操作IDによる再送判定で、並行登録の重複を防ぐ。登録後の取り消しは欠番を許容し、再利用しない。先に番号だけ予約する経路が必要かは、既存運用調査で確認する。

採番表とRegistryの二重手更新をなくす案だが、task化の必要性、分類、委任の判断は自動化の対象としない。移行時は現行行だけで最大値を決めず、採番表と退役済みIDを照合する。

### 移行の区切り案

1. 現行契約を確定し、少数fixtureでDB写しから同じ構造を取り出せるか比較する。
2. 書き込みを許さない写しで、現行一式との照合と現在区間/全体照会を試す。
3. 隔離環境で編集差分・衝突・採番の並行実行・再送・失敗時の全取消を試す。
4. ユーザーの切替判断後に正本を一つへ切り替える。旧Markdownを同時編集可能な第二正本にはしない。

切替前は写しを捨てれば戻れる。切替後はDBで受け付けた変更を保った書き出し/復元が必要で、古いMarkdownへの単純な巻き戻しは不可。切替・バックアップ・復元の手順が検証できるまで本番移行しない。

## 経路調査の受入と比較計画（2026-10-19 Astra）

姫の返却は上記連絡DBレターに保存。確認版62fdebefe。Astraは `sync.py:48,135,279`、`inbox.py:46,69,84`、Studio READMEの取り込み手順、TASK_RULES採番節を直接照合した。経路調査として受け入れ、未実装のDB方式の正しさまで認定しない。

確認できた重要点：
- `sync.build()`は旧JSONを入力とせず、Registry・Milestones・Rulesから再生成する。この読取境界をDB版と比較できる。
- 保存は追記方式で、古い親からの保存を別seriesとして保持する。正本との照合・正式採番・反映は現在AI手順であり、自動書込コードではない。
- `source.sha256`はRegistry単体で、Milestones全体を覆わない。フィールド比較は別に存在するため、これだけで変更を見逃すと断定しない。V3ではtask・関係・版・HEADを含む基準版と、対象フィールドの三者比較を組み合わせる案とする。
- 現行ゲート状態にはHEAD/名前からの派生がある。保存値と派生値を区別し、画面互換を確認する。現行実装を原型仕様や実際の到達判断の代わりにしない。
- 現行採番規則は、採番後に同じ編集内で取りやめても欠番を保持する。V3でも外部へ発行済みの番号をロールバックで再発行しない。未公開の内部候補値と正式発行を分けて試験する。

比較は次の3群へ限定する案：
1. 正常構造：恒久親子を含むtask、先行辺、3版と中央HEAD、中間カード、ゲート欠落、START/task/END接続、エスケープを含む条件文。
2. 拒否構造：重複ID、不明端点、循環、複数ゲート、存在しないHEAD。現行readerが拒否する箇所と後段検査が拒否する箇所を区別して記録する。
3. 保存差分：独立変更、反映済み、競合、古い保存、分岐series、追加案の正式ID変換、版移動、相談待ち接続。正本への二重適用を防ぐ。

比較対象はID・値・関係・順序・表示上の現在区間。sourceLine/raw/パス・hash・生成時刻などの出典表現は別枠で検査し、DBで同じ値を捏造しない。既存JSONを受け取るクライアントとの互換層が必要な箇所を一覧化する。姫案の「出力をほぼ完全一致」は、この意味比較と出典比較へ分けて採用する。

これは調査・設計の初稿。実fixture作成・DB実装・本番変更は未実施。次の設計区切りは、保存モデルと互換層の具体案を上記3群へ対応させ、実験の範囲を確定すること。

## 保存モデルと更新契約の具体案

本節は設計提案。SQL実装・移行・原型仕様の改訂ではない。

| 保存単位 | 主な情報 | 整合性の単位 |
| --- | --- | --- |
| nodes / tasks / milestone_cards | 全体一意ID、種別、task属性、カード属性、本文参照 | nodesでIDを一度定義し、型別属性から参照。退役IDも予約を残す |
| versions / version_members | 版の識別名、版順、カード順、任意のゲート | 順序の変更は影響する骨格全体で検証。1版1ゲート以下 |
| graph_edges | グラフ区分、端点、Flow/条件など現行属性 | 管理の親子・進捗依存・到達点接続を区別。構造だけでは権限を表さない |
| focus | 現在の版への参照 | 版移動とは別操作。全体データを削除せず照会範囲を変える |
| id_allocations | prefix、最終発行番号、発行済みID、発行操作 | 退役後も再利用しない。旧同名IDの履歴は出典付き別記録 |
| revisions / operations | DB世代、改訂番号、操作ID、要求digest、前後差分、実行者・根拠参照 | 同一操作ID・同一内容は同じ結果、内容違いは拒否 |
| edit_submissions | 保存ID、series/parent、基準snapshot、編集内容、適用結果 | 保存と正本反映を分離。未解決/適用済みを保存単位で残す |

START/ENDは版から派生するが、参照用nodesへ同じトランザクションで機械生成する案とする。利用者が独立編集する属性にはしない。派生骨格の辺は独立した手編集データとして保存せず、版・カード順・ゲートから導出する。既存reader由来のDONE表現は互換層で保持し、到達の一次記録として再取り込みしない。

版順の初回取り込みは現行readerが実際に出した順序と比較方針を証拠として保存する。未決の一般的なフォルダ比較規則を導入しない。DB上の明示順を正式採用するかは移行前の判断事項とする。

### 書込1回の流れ

1. 変更提案を保存する。まだ正本や実行許可ではない。
2. 任された担当が変更範囲・根拠を確認し、操作ID、基準DB世代/改訂、対象ID/フィールドの基準値、操作内容を送る。
3. サーバーが既処理操作IDを照会する。同内容なら前回の結果を返す。
4. 書込トランザクション内で基準値と最新値を照合する。無関係な変更だけなら継続可能。同じ対象の競合・参照先退役・不明な条件は適用しない。
5. ID・端点・各DAG・版骨格・許される更新属性を検証し、一組の変更と履歴と新しい改訂番号を確定する。途中失敗なら全て取り消す。
6. 確定結果を返す。応答喪失時は同じ操作IDで照会/再送する。成功を推測して別操作IDで重ねない。

更新対象だけでなく、更新が依存した親子・順序・端点などもトランザクション内で再検証する。たとえば辺追加の直前に別の辺が追加されても、合成後の循環を拒否する。全文一致だけで無関係な編集を衝突にせず、逆にフィールド一致だけで関連条件の変化を見逃さない。

新規採番は登録操作内で行い、確定前の候補番号を外へ見せない。確定後に仕事を取り消した場合は退役記録を残す。番号だけ先に発行する必要が生じた場合は予約を確定する別操作が必要で、今回の最小試行には含めない。

### 読取とStudio互換

- 詳細照会：選択IDの属性と直接関係、正本参照、根拠となる改訂。
- 現在区間照会：HEAD相当以後の版と関連task。境界外の接続は「存在しない」扱いにせず参照IDと境界情報を返す。
- 全体照会：俯瞰・検証用。通常のAI読取に強制しない。
- 互換snapshot：既存のtasks/edges/milestones/milestoneRelationsを構成する。Markdownの行番号が存在するように偽装しない。旧source前提を使う箇所はadapterで明示的に扱う。

### 最初の隔離試行の受入条件案

まず読取だけの小さな試行とし、DB本番切替やStudioの現用入力切替は含めない。

1. 仕様と現行実装が一致する範囲の固定fixtureに限り、現行読取結果を比較値として保存し、DB写しからの意味比較が一致する。出典表現は別検査。
2. HEADを変えても旧データは消えず、現在区間と全体照会が意図した範囲を返す。欠落ゲートを自動接続しない。
3. 不正構造を拒否する検査位置を明記する。現行parserの未検査を規則と解釈しない。
4. 入力fixtureを変えたときに比較が失敗することも確認する。一致した正常例だけで試験を終えない。

更新・採番・競合・再送の試行はその次の区切りとする。同時登録、応答喪失後の再送、別内容で同操作ID、発行後取消、循環を作る並行変更を試験対象にする。

### 移行判断へ残す事項

- 明示的な版順をDB正本にすることと、フォルダを入出力表現にする範囲。
- DBの配置と復元単位。連絡DBとの同居は本設計の前提にしない。
- Markdownの状態表を読取用の生成物へ切り替える時期と、DB変更をGit等へ保存するバックアップ/履歴方針。

これらを決めなくても隔離読取の設計は進められる。実装着手は別の実行範囲として扱う。

## 具体案レビューと補正（2026-10-19 Astra）

姫のレビュー `LTR-20261019-98D29BF2273045F782171C919DCF5CC0` を受領。Astraが `sync.py:add_ends` を直接確認し、次の補正を採用する。レビューは作業ツリーを対象としたもの。返却文の基準commit記載62fdebefeは前回調査基準であり、新設節の確定commitではない。

### 現行実装との相違を互換要求へ昇格させない

`add_ends`はゲートID末尾を接続先folderとみなし、単一の連結経路を要求する。一方、原型仕様は順序上の次folderへ接続し、最後のゲートとゲート欠落による未接続を許容する。従って、全ケースで現行readerを期待値とする案は撤回する。

試行は「原型仕様と実装が一致する共通部分」と「食い違いの再現」に分ける。後者は期待する意味と実装結果を両方保存し、不一致を成功扱いにしない。現行コードの修正や上位仕様の変更は本調査では行わない。HEAD由来のDONEは互換表示値と記録し、実際の到達の証拠としてDBへ自動昇格させない。表示範囲用focusと正式な到達記録を分離する場合の意味は、切替前に判断が必要。

### 更新契約の補足

- 版名変更/削除は派生START/ENDを参照する辺も含めて検証する。関連参照を一括変換できない操作は拒否する。カードの版移動は所属/順序の操作として扱う。退役IDへ辺を取り残さない。
- 連番採番はtask用。MS等の名前付きIDは登録し、START/ENDは機械生成する。全種別でnodesの一意制約を共有する。
- 保存提案の正式化は `(saveId, draftId)` と正式IDの対応を永続化する。別保存へ引き継いだ同じ提案は系列上の元提案も照合し、再度採番するか曖昧なときに自動追加しない。
- 一括保存から独立した変更群を選び、一群を一つの更新操作とする。競合した群は未適用で残す。確定的な拒否後に内容を減らして再申請する場合は新しい操作IDを使う。応答不明時は元操作の結果を先に確認する。
- 既存クライアントが要求する `source.sha256`、raw、関係source等は互換adapterの検査対象。DB改訂番号をSHA-256と偽称して詰めない。旧保存の識別と新しいDB基準版の識別を明示的に分ける契約が必要。既存画面への無変更接続をこの設計で約束しない。

この補正で設計調査の成果を一巡した。実装開始前の判断点は、版順/ゲート接続の仕様と実装の差、HEADと到達の扱い、正本切替・復元の方針。これらを曖昧にしたまま本番移行しない。共通部分の隔離読取試行は切り出せるが、まだ実装依頼は出していない。
