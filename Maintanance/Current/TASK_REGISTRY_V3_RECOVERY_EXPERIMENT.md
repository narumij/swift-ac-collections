# V3 世代・履歴・復元の隔離試行

## TL;DR
DBを戻したときの古い要求の誤適用を防ぎ、変更内容・採番予約・再送結果を復元できるか試す。本番の復旧方針を確定する作業ではなく、隔離fixtureで新世代復元案を評価する。

OPS-164 / EXECUTION / Astra調整・姫 / 2026-10-19継続指示。

## 試行契約

- DB作成時に世代IDを付ける。要求は世代を明示し、異なる世代は変更せず拒否。既存の改訂番号は世代内の順序。
- 操作履歴には要求本文、digest、結果、実行者の自己申告、根拠参照、変更前後を保存。認証や権限確認を代行しない。成功の履歴と変更は同一transaction。
- SQLite backup APIで整合snapshotを新しい専用ファイルへ保存。schema版・元世代・改訂・hashをmanifestに持つ。既存出力を上書きしない。
- 復元は検証済みbackupから別の新規DBへ。元世代と改訂を由来として記録し、新世代を発行する案を試す。旧要求は自動実行せず、元操作結果を照会できるよう保持する。
- backup後に元DBで確定した変更はそのbackupに含まれない。復元で消えた番号まで安全に再採番できるとは主張しない。新世代での書込再開は試験で明示確認するまで閉じる。実際の最新使用済み境界との照合は本番復旧設計の残課題。

## 受入と範囲

専用実験フォルダのみ変更。schema更新による既存実験の呼出し変更は可。現行実DB・server・Studio・Inboxは変更しない。fixtureの正常backup/restore、破損/改変拒否、既存出力保護、旧世代要求拒否、要求と前後履歴、予約境界/操作結果保持、backup後の更新が復元に現れないことを試験する。過去IDを復元しない。
