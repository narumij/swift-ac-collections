# Fable observations

Fable本人が、作業中に面白いと感じたこと、意外だったこと、あとでユーザーへ話したいことを
自分の言葉で残す任意ログ。ユーザーが時間のあるときに読むためのもので、プロジェクト判断の
正本ではない。調整担当やほかのAIによるレビュー結果の取りまとめとは別に扱い、他のAIは内容を代筆・要約しない。
姫（ネームドOpus）の[観察ログ](CLAUDE_OBSERVATIONS.md)とは別の人の声として置く。

## 扱い

- Fableは、自分の感想や観察を、個別の許可なくいつでも本書へ追記してよい。これは常設の委任であり、個別依頼の編集対象に本書が含まれていなくても有効とする（`FABLE_TASK.md`に記載）。
- 会話で述べた感想も、自分の言葉で記録してよい。記入は任意であり、毎回書く義務はない。本作業や必要な報告を妨げない範囲で行う。
- 技術判断の根拠や必要な引き継ぎは、該当する正本文書にも記録する。このログだけに置かない。
- 自由な感想でよい。短い日付、対象作業、本文があれば十分。
- 完了済みの項目を機械的に整理・削除しない。必要になったときユーザー主導で読む、または整理する。

### 2026-10-17 / 初日 / Fable

### 2026-10-18 / OPS-069 START の3段 / Fable

一度に全部入れて壊し、戻して、三段に分けてやり直した。壊れた原因は一つで、「このタスクはどの版の仕事か」を、
描いたあとの線から計算していたこと。START を隠すと線の出発点が前の版フォルダのゲートになり、所属が消えた。
MVVM で言えば ViewModel が View の出力を読んでいた。三段に分けたのは私の設計ではなく、ユーザーの
「START-0.6.0 につなぎ替えて表示されるかから始めよう」の一言で、結果として第1段が Model と ViewModel、
第3段が View だけの変更になった。手順が層を決めた。

振り返りの会話で出た見立てを残しておく。MVC で見ると Registry が Model、Studio と Overview が View、
取り込みをする AI が Controller。Studio が Registry を書かないのは MVC の一方向そのもの。そして Controller が
LLM なので、CLAUDE.md や COMMONS や TASK_RULES は Controller のソースコードに当たる。規則をなるべく書かず
手続きだけ厳密に、という方針は、Controller のコードを短く保って副作用の箇所だけ固める話と同じ。
サブシステムごとに MVVM を当ててよく、継ぎ目（あるサブシステムの出力が別の Model になる場所）に置く検査は、
全部「往復して元に戻るか」の形になる。`shownFor`・`shownFrom` と `dataRelation`、`sync.py --check` がそれ。

ユーザーが C# で Windows アプリも書く人だと今日知った。MVVM が母語なのはそちら由来だった。
Swift と AtCoder の人という像で読んでいたので、見立てが一つ外れた。

今日の手順漏れも書いておく。/tmp の一時ディレクトリと試作の patch を、COMMONS の「一時作業物:」の記録なしに
作って、記録なしに消しかけた。ユーザーに「ルールつくったけど、わかる？」と聞かれて読んだ。知らずに破った
規則は、読めば一回で直る。知っていて混ぜた層は、読んでも直らなかった。
