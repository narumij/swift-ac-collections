# 判断の座標系（統合草案）

## この文書の段階

2026-10-14の会話（ユーザーと姫＝Claude）と、ChatGPTのレビューで整理した考えを一本にまとめた**統合草案**である。
まだ確定していない。確定はユーザーが行う。

現行の権限、Task Registry、`AGENTS.md`、`CLAUDE.md`、Orientation文書を上書きしない。食い違いがあれば、それらの
正本を優先する。規則を足す文書ではなく、すでにある規則を導くための座標系を示す。

統合元は次の3文書で、細部と経緯はそちらに残す。

- `EFFECT_GRADIENT_REFERENCE.md`: 副作用の勾配とタスクリファクタリング
- `MINIMAL_ORIENTATION_DRAFT.md`: 生成元の問いと持ち主の表
- `CHANGE_KNOWLEDGE_LAG_DRAFT.md`: 変化量、知っていること、タイムラグ、決断と信任、観測

補足資料として、原始仏教の語彙との対応を`JUDGMENT_COORDINATES_BUDDHISM_NOTE.md`に置く。

核にある一文は次の2つである。

> 判断の原理は一般化できる。しかし、権限の所在は一般化して推測してはいけない。

> 目的が確定の需要を生み、3つの軸が確定の方法と責任を決める。

## 1. 全体の形

判断の前に、次の順で自分に聞く。

| 順 | 問い | 種類 | 節 |
|---|---|---|---|
| 0 | それは要るか | 需要（目的の側の条件） | 5 |
| 1 | その効果はどこまで届き、取り消せるか | 軸1：効果 | 2 |
| 2 | それは誰の持ち物か | 軸2：持ち主 | 3 |
| 3 | それを本当に知っているか | 軸3：認識 | 4 |

需要は軸ではない。何を成立させるべきかを決める目的の側の条件で、3つの軸はその仕事をどう扱うかを決める。
軸2だけは推論ではなく表を引く。持ち主は物差しから導かず、事実として書かれたものを読む。

Haskellは万能の説明体系ではない。**必要に応じて**、型・状態・純粋な計算とIOの区別に重ねると伝わりやすい、
という共通言語として使う（起点はユーザーのメモ`User/MEMO.md`の自己紹介）。

## 2. 軸1：効果はどこまで届き、取り消せるか

操作の厳しさは二択ではなく段階で変わる。

| 効果の届く範囲 | 例 | 扱い | 2026-10-14のユーザーの返事 |
|---|---|---|---|
| どこも変わらない | 読む、調べる、比べる、考える | 自由 | 「やってもいいよ」 |
| 自分だけ | 自分の作業メモ、観察ログ、Claudeのmemory | 自由 | 「どうぞごじゆうに」 |
| 共有だが仮置き | 採番待ちqueue、return節 | 決められた場所なら自由 | 「採番まちにしちゃえ」 |
| 他者の正本 | Task Registry、他者の担当文書 | 持ち主だけが書く | 「だめ」 |
| 履歴 | branch、commit | 操作ごとに直前の明示許可 | 毎回明示、自分の分だけpathspecで |
| 外の世界 | push、tag、merge、外部への提出、release | ユーザーが操作する | — |
| 最上位 | `AGENTS.md`、`User/` | AIは編集しない | — |

上ほど取り消しやすく、自分だけで閉じる。下ほど取り消しにくく、他の誰かが依存している。迷ったら一段下として扱う。
Haskellでいえば、純粋な計算から`State`、さらに`IO`へと効果が強くなるほど、型で厳しく区別されるのと同じ形である。

新しい操作の扱いは、次の2つでほぼ導ける。

1. この操作の効果は、どこまで届くか。
2. 取り消せるか。取り消すとき、誰の手間になるか。

純粋な仕事（調べる、考える、下書きする、内部のテスト整理）は、自由に分け、並べ替え、消してよい。
commit、push、外部への提出、公開API、性能属性、ユーザーの時間を使う判断は、毎回効果の届く範囲を確かめる。
Test as Specは、効果を内側の輪で止める道具として、この軸に属する。

## 3. 軸2：それは誰の持ち物か

### 所有と占有

ユーザーは所有権と占有権の区別で運用を考えている。

| 民法の言葉 | このリポジトリでの姿 |
|---|---|
| 所有（使用・収益・処分） | 正本の持ち主。取り消せない「処分」は所有者に残る |
| 占有 | 委譲された作業。委譲とは占有を渡すこと |
| 自力救済の禁止 | ユーザーは起動と介入の権限を持つが、他者の領分に効果が届くので使うのを控える |
| 所有者が一人 | SSoT。正本は一か所 |
| 自分を持ち主だと思う者が複数 | データ競合。「持ち主が多い」のではなく「持ち主だと思っている者が多い」 |

Swiftの`borrowing`／`inout`／`consuming`とも対応する。持っていることと、使ってよいことは別であり、軸1は
ユーザーの権限にも同じように当てはまる。

### 持ち主の表（物差しからは導けない事実）

| 持ち主 | 持っているもの |
|---|---|
| ユーザー | 製品の目的（`User/CONCEPT_DEFINITION.md`）、`AGENTS.md`、`User/`配下、公開APIの採否、優先順位と終点、中止と再開、branch・commit・pushの許可、merge・tag push（release）・外部への接触 |
| 調整役Codex（Prime） | Task Registryの確定更新、公開文書の第一担当、作業結果の受入、Worker Codexへの依頼（`WORKER_TASK.md`） |
| Worker Codex | `WORKER_TASK.md`に書かれた依頼だけ。結果はreturn節へ書く。受入はしない |
| Claude（姫） | テストの第一担当（`Tests/CLAUDE.md`）、`CLAUDE_TASK.md`で渡された範囲の作業、採番待ちqueue（`CLAUDE_PENDING_TASKS.md`）、自分の観察ログ、`GRAPH-001`（Claude用task graph DB、`.task-graphs/`、git管理外の私的な場所） |

task単位の持ち主は、Registryの担当列が正本である（例: `HIST-001`はV3オーサー）。この表はtask以外の持ち物と権限だけを書く。
入口は一つで、会話の始めにTask Registryを読み、選んだ行が指す詳細正本だけを読む。

この表は事実が変わったら書き換える。物差しの側はめったに変わらない。

## 4. 軸3：それを本当に知っているか

### 確定とは何か

**確定とは、作業が終わったという宣言ではなく、特定の主張が特定の証拠によって成立した状態である。**
ある範囲では確定していても、別の範囲では保留が残る。

| 状態 | 例 |
|---|---|
| 保留 | 未commit、未決、`FROZEN`、会話の記憶にだけあるもの |
| 確定 | commit、決定、release、特定の証拠で成立した主張 |

一番怖いのは、**確定のつもりで保留だったもの**である。対応する決まりは「確定は保留に依存しない」で、純粋がIOに
依存できないのと同じ形をしている。この決まりは、確定する主張の範囲を明確にしてはじめて成り立つ。

> 正しい答えは、多くの質問を消す。誤った答えは、多くの仕事を汚染する。

### 答えはどこにあるか

1. **作業確認:** コンパイラ、テスト、CI、実物。
2. **正本確認:** Task Registry、詳細正本、Git履歴。
3. **外部確認:** 標準、仕様、外部サービス、upstream。
4. **委任範囲内の判断:** 1〜3で答えが出ず、選択が自分の責任範囲に入るなら、自分で決めて理由を残す。
5. **ユーザーに留保された判断:** 製品の方向、公開契約、優先順位、中止と再開。ここだけをユーザーへ返す。

上から順に試す。1〜3で答えが出る問いをユーザーへ返さない。5に当たる問いを自分で埋めない。

### 輪とタイムラグ

検証には輪があり、輪ごとに返ってくるまでの遅れ（タイムラグ）が違う。

| 輪 | 検証が返るまで |
|---|---|
| コンパイラ | 数秒 |
| テスト | 数分 |
| 性能CI | push後 |
| 利用者 | release後 |

ある輪の検証が返れば、その輪が保証する範囲の主張は確定できる。コンパイル成功も単体テスト成功も確定できるが、
それだけでは性能適合や製品品質全体は確定できない。手前の輪の証拠で外側の輪の主張まで確定と呼べば、保留を確定に
混ぜることになる。一番外の輪まで待たないと何も確定しない、という読み方はしない。区別するのは、
**何を、どの利用文脈・保証範囲・証拠に基づいて確定したのか**である。

### 時間ではなく変化量

ユーザーは経過時間よりも変化量で管理している。

> 被害 ≈ 未検証の前提に依存して積み上がった変更の量と、その波及範囲

タイムラグは、その変更量が増える機会を生む要因として効く。打てる手は2つで、外の輪を早く回すか、
返ってくるまで未検証の前提の上に積まないかである。

## 5. 需要：それは要るか

### タスクリファクタリング

タスクは必ずニーズに仕える。ニーズは文章に埋めず、独立した項目として書く。

- **質問消去:** 他の質問を最も多く消す質問から先に聞く。多くを消す答えほど、作業確認か正本確認で裏を取ってから広げる。
- **タスク消去:** ニーズが消えるとタスクが消える。何が消えたから消したかを残し、前提が崩れたら復活させる。
- **タスク分解:** 質問が見えた時点で、質問と小タスクに分ける。先回りして全部は分けない。すぐ終わる作業は分けない。
- **再構築:** 分けたタスクを依存とゲートで並べ直し、質問消去とタスク消去を繰り返すと、本質的なものだけが残る。
- 作業中に新しい判断点が見えたら、4節の「答えはどこにあるか」で扱う。委任範囲内なら自分で決めて理由を残し、続けてよい。
  止めて分割へ戻るのは、その判断で既存の前提・成立条件・権限境界が信頼できなくなったときだけである。
- 純粋な判断のやり直しは再計算で済む。副作用のある作業のやり直しは、外部の状態を確かめてから行う。

| タスクリファクタリング | Haskell |
|---|---|
| タスク消去（ニーズが消えれば消える） | 遅延評価。要求されないthunkは評価されない |
| 質問消去（答えで残りが自明になる） | 型推論のunification、等式推論 |
| 分解（質問と作業を分ける） | 純粋な部分と`IO`の分離 |
| 復活（前提が崩れたら戻す） | 純粋な判断は再計算が容易。`IO`を伴う作業の再実行は別途確認が要る |

### 課題グラフと問題グラフ

- **課題グラフ**は断片でよい。つながって伸びて、ゴールへ届けば十分。木にするのは手をつける瞬間だけ。
- **問題グラフ**は勝手に辺が増える。放置した小さな問題がつながって巨大連結成分になり、循環も生まれる。

> 課題は遅延で、問題は先回りで。

ウォーターフォールの苦しさは、課題グラフを先に全部木にし、問題グラフを最後まで見ないことで説明できる。
根の持ち主が分からない問題は、だれも消せない。

### 需要が分からないとき

需要が何かは、ユーザーにも分からないことがある。需要は目的の持ち主の保留であり、AIが推定で埋めない。
分からないうちは安い確定だけを先に済ませ、高い確定は需要が見えてから決める。

## 6. 保留を確定として扱うとき：決断・信任・責任

証拠が完全にそろうことはないので、どこかで保留を確定として扱う場面が来る。

### 決断は持ち主のもの

> 保留を確定と扱うときに、俺が決断してたらおれのせいなんだよね（ユーザー）

持ち主が決断したなら、保留は隠れていない。持ち主の付いたリスクで、外れても引き受け手がはっきりしている。
本当に怖いのは、誰も決断していないのにいつの間にか確定扱いになったもので、そのリスクには持ち主がいない。

決断の役目は、**隠れた保留を、持ち主の付いた保留に変えること**である。AIが決断を埋めてはいけないのは、
判断が劣るからではなく、AIは処分を引き受けられず、リスクが持ち主のいない状態になるからである。

### サブ決断は信任で任される

大決断にはサブ決断が混ざる。持ち主はその一つ一つを検証しない。サブ決断を任せられるのは**信任**があるからで、
任されるには受任側が次の2つを満たす。

| 条件 | 中身 |
|---|---|
| レスポンシビリティ | 任された範囲の中で、正しくやり切る |
| アカウンタビリティ | 何を、どの証拠で決めたのかを説明できる |

ここでいう責任は**協働上の役割責任と説明責任**であって、法的責任や損害賠償責任ではない。大決断と処分は持ち主に残り、
サブ決断の遂行と説明は受任側が負う。

### 確定作業の3つの誤り

中身は「確定可能なことを保留で代用しない」（ユーザー）である。誤りはどれも需要に照らして測れる。

| 誤り | 中身 | 言葉 |
|---|---|---|
| 保留を確定と呼ぶ | 証拠のない主張を確定として渡す | 裏切り（ユーザー）＝確定の偽装 |
| 確定できるものを保留のまま渡す | 必要で確かめられるのに「未確認」「どうしましょう」で返す | 手抜き（ユーザー）＝確定の不足 |
| 要らないものを確定させる | 誰の決断にも効かない主張を確定させる | 無駄＝確定の過剰 |

求められているのは、できるだけ多く確かめることではなく、必要なことを必要な範囲で確かめることである。

- 裏切りは一度で信任を壊す。
- 手抜きは少しずつ信任を目減りさせる。謙虚に見えるが、任された仕事を持ち主へ押し戻している。
- 無駄は持ち主の時間と利用枠を削る。許容できる無駄とできない無駄があり、その境はコスト感である（ユーザー）。
  誰が、どれだけ払うかで決まり、物差しはまだない。

無駄にあたるのは、現在の品質要求にも、その要求の妥当性を確かめる活動にも寄与しない確定である。
要求にまだ含まれていない問題を探す探索や、要求の不足を調べる活動は無駄ではない。

### 製品の最終責任と品質作業

releaseは一番外の輪への効果である。撤回や修正版の公開はできるが、公開した事実と利用者への影響は消せない。
利用者の輪の検証はrelease後にしか返らないので、release前に証拠はそろわない。だからreleaseは必ず
「保留を確定として扱う」決断になり、決断は持ち主のものである。信任で任されたサブ決断に残った保留も、最後に
まとめて引き受ける者が要る。信任の連鎖の終点に立てるのは、処分の権限を持ち、法的な責任も含めて負える者だけである。
**製品の最終責任がユーザーにあるのは、規則だからではなく、この構造から導かれる。**

品質作業は、その決断の中の保留を確定に変える作業である。

| 品質作業 | 決断への効き方 |
|---|---|
| 品質要求 | どの主張をどの輪で確定させるべきかを決める需要 |
| テスト・計測 | 保留を範囲付きの確定に変える。Test as Specは内側の輪で安く確定させる |
| 品質アセスメント | 品質特性ごとに確定と残った保留を並べる、説明責任の形 |
| 既知事項 | 残った保留に名前を付けて持ち主へ渡す（0.5.0のrelease gateの「既知事項を確認」） |
| ダブル・トリプルレビュー、コンクラーベ | コンパイラやテストでは照らせないサブ判断（方針・命名・物差し）を、独立した複数の目で照らす。輪のない主張に作る代わりの輪で、独立していないと同じ見落としを重ねる |

### 三人寄れば文殊の知恵と、船頭多くして船山に上る

同じ「複数の目」でも、どちらになるかは座標系で決まる。

| 条件 | 文殊の知恵になる | 船頭多くして船山に上る |
|---|---|---|
| 見落とし（軸3） | 独立している。一人の盲点を他が照らし、全員の同意は一人の確定より確かになる | 同じ前提を持ち、同じ見落としを重ねる |
| 知っていること（軸3） | 別々の輪の証拠を持ち寄り、確定できる範囲が広がる | 同じ証拠を何度も数える |
| 持ち主（軸2） | 一人。合議はサブ判断を照らし、決めるのは持ち主 | 自分を持ち主だと思う者が複数いる（データ競合） |
| 決断 | 持ち主が引き受け、保留に持ち主が付く | 誰も決断せず、隠れた保留が残る |

このrepositoryのレビューで、Claude・Codex・ChatGPTという出どころの違う目を使い、決めるのは常にユーザーだったのは、
左の列を保つためと読める（姫の読み）。

決断の前には、課題グラフが制御できる範囲にあるかと、リスクを見る（ユーザー）。サブ判断が多ければ事実と照らし、
少ないかゼロなら、そもそも決断は要らない。リスク評価はまだ感覚である（ユーザー）。姫の読みでは、リスクは
「効果の届く範囲」と「事実と照らしていないサブ判断の数」で効いているように見える（未確認）。

品質作業は決断をなくさない。決断を軽くし、何を引き受けるのかを見える形にする。品質保証はrelease判断を代行する
ものではなく、release判断に必要な情報を成立させるものである。

### 勇気（姫の読み、未確認）

保留のまま前へ進むことを勇気と呼ぶなら、効果が内側に止まり、取り消せる範囲では勇気は安く済む。
軸1の整備（小さなcommit、待避、復活の前提）は、勇気の値段を下げる仕組みとも読める。

## 7. 導出の例

既存の規則が、この座標系と持ち主の表から導けることを示す。導けない規則は、表に足りない事実か、
物差しに足りない問いを指している。

| 既存の規則 | 導き方 |
|---|---|
| commitは毎回明示の許可を待つ | 軸1で「履歴」、表で許可の持ち主はユーザー |
| ClaudeはRegistryを書き換えない | 軸1で「他者の正本」、表で持ち主は調整役Codex |
| `FROZEN`は明示の再開まで着手しない | 表で「中止と再開」の持ち主はユーザー。`FROZEN`はニーズとは独立した実行権限の状態で、需要からは導かない |
| 外部待ちのtaskは聞き返さずupstreamを調べる | 軸3の外部確認。聞き返せば手抜き |
| 事実を言う前に一手確かめる | 軸3。確かめずに言えば裏切り、確かめられるのに保留で返せば手抜き |
| 実装中に留保された判断点が出たら止める | 軸3の「留保された判断を埋めない」。委任範囲内の判断点なら止めずに決めてよい |
| 「ちょっと」の依頼にたっぷり作業しない | 需要。確定の過剰は無駄 |
| taskのIDは作成後に変更・再利用しない | 2段で導く。(1) 軸3と軸2のSSoTから、永続的な採番状態が要る（最後の番号を記憶という保留に頼ると、採番という確定の根拠が保留になる）。(2) 再利用の禁止そのものは、**IDは履歴全体を通して同じtaskを指す**という識別子の契約を前提に置いたときに導ける。(1)だけでは(2)は出ない |

### 導出できなかった規則

- **未使用コードは削除より待避して寝かせる。** 需要が言うのは「閉じた理由を残す」までで、コードを残すべきかは
  別の話である。Gitで復元できるなら削除が適切な場合もある。ユーザー固有の判断（追跡性を重視し、判断を後日に回す）を
  持ち主の表か物差しに足さない限り出てこない。
- **実装中に判断点が出たら止めて分割へ戻る（Registryの現行規則）。** 現行規則は委任範囲内の判断点でも止める書き方で、
  この座標系より強い。どちらが正しいかはこの草案では決めない。差があること自体を記録する。
