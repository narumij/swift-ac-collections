# Milestones

版フォルダとカードの配置を計画の構造とし、スクリプトが接続を生成する。現在地は[HEAD.md](HEAD.md)。人間向けの実績・集計は[進捗報告](../MILESTONES.md)に置き、工程や到達条件を二重管理しない。

構造の基準はユーザー作成の[原型仕様](DESIGN.md)。このREADMEは、その構造を本リポジトリで使うための運用を説明する。現行実装との差は末尾に分けて記載する。

## 版フォルダとカード

- この直下のフォルダが各版を表す。名前が `_` で始まるフォルダは対象外。
- 各版フォルダには、名前をそのまま使った `START-<版>` と `END-<版>` が仮想的に付く。実ファイルは置かず、ドットを除去しない。
- ゲート以外のカードは、ファイル名順でSTARTからENDまで一本につながる。`10_`、`20_` のような桁を揃えた番号を推奨するが、番号は必須ではない。ノードの固定IDはファイル内部に記載する。
- `GATE-*.md` は各フォルダに最大一つ。ファイルはフォルダ内に置くが、構造上はその版のENDの外に位置する。
- ゲートのID・ファイル名は識別子であり、接続先の指定ではない。ゲートはフォルダ順で次の版のSTARTにつながる。**フォルダの比較方法は利用者が定める。具体的な比較方法は未決定で、現行コードの方式をそのまま確定仕様とはしない。**
- 最後の版のゲートは接続先がなくてもよい。ゲートがない版と次の版は未接続として許容し、飛び越して接続しない。
- `GOAL.md` はフォルダ保持用の置物として無視する。他の任意のMarkdownファイルまで置物扱いにはしない。

```text
START-現在の版 → 10_本文.md → 20_検証.md → END-現在の版 → GATE-識別子
                                                             ↓
                                                       START-次の版
```

中間カードがなければSTARTからENDへ直接つながる。

カードは[テンプレート](GATE_TEMPLATE.md)に従い、`# カード情報`（ID・名前・途中のカードだけ状態）、`# 正本`（リンクまたは「このファイル」）、`# 記録`の三部に分ける。正本はカード情報に含めず、記録本文は接続生成の入力にしない。

既存カードの固定IDとカード内の名前は、並べ替えや移動では変更しない。ファイル名の先頭番号は順序変更のために変更できる。新しいカードには新しいIDを付け、再利用しない。本リポジトリでは途中のカードに `MS-*`、版ゲートに `GATE-x.y.z`、名前に「x.y.z リリース」を用いている。版ゲートのIDはファイル名と一致させるが、そこに含まれる版番号から接続先を決めない。実施する版は置き場所で表し、カード内に重複して固定しない。

## 版内のDAGと接続の正本

マイルストーンカードの経路は一本道に限定する。一方、その工程へ合流するタスクは分岐・合流できる。STARTは作業開始側、ENDは到達側の接続点となる。タスクの接続はRegistryで明示し、全タスクを自動的にENDへ集めない。

- タスク間の依存は[Task Registry](../ProgressV2/TASK_REGISTRY_V2.md)の「Task precedence」。
- START・END・途中カードとタスクの接続は同書の「マイルストーン接続」。
- 線に種類はない（2026-10-17廃止）。線は関係の所在を示し、完了・着手・再開の条件はRegistryの制約文と各カードの本文で持つ。
- 版ゲートへ入る線は、そのフォルダのENDからだけ。途中カードにはタスクが直接接続してよい。 タスクは版の中の行動なので、開始側はSTARTから、到達側はENDまたは途中カードへ接続し、どの版の仕事かを明確にする。 背景の会話や補足情報が失われても、接続先から対象版を読み取れるようにし、どの版の仕事だったかを巡る混乱を防ぐ。

同期処理はタスクの接続先・方向を暗黙に付け替えない。線があることだけで、自動開始・ユーザー判断の代行・凍結解除を認めない。

## 計画の組み替え

版内の順序はカードのファイル名で変更する。別の版へ作業を移す場合は該当カードを移し、影響するタスクの到達先を確認する。

途中に版を挟む場合は、利用者が定めた比較方法でその位置になる新しい版フォルダを作り、既存のリリースゲートをそこへ移し、元のフォルダに新しい版へのゲートを置く。例えば `0.5.4 → 0.6.0` に `0.5.5` を挟むときは、`0.5.5/`へ`GATE-0.6.0.md`を移し、`0.5.4/`へ`GATE-0.5.5.md`を追加する。

この例のゲート名は命名慣行であり、接続は配置とフォルダ順で決まる。同じENDを目指すタスクの接続は変えなくてよい。既存ゲートのIDと条件は保持し、移動・改名した文書の参照リンクを調整する。条件自体を変える場合は判断者と理由を記録し、計画変更を旧条件の達成として扱わない。未達を引き受けて進む判断も、条件を変更する判断とは分ける。

**マイルストーンとゲートの作業は必ずユーザーが同席し、AI単独では行わない。** このためカードに担当欄は持たせない。

## HEADが示す境界

HEADは現在地であり、通常の探索・作業範囲の境界。現在地より前の版は履歴として保持し、通常の作業対象から外す。AIは前の版を毎回読み直さず、必要な証拠があるときだけ参照する。HEADを進める判断はユーザーが行う。

- 現在地以後の途中カードには `- [ ] DONE` / `- [x] DONE` を持たせる。版ゲートにはチェックを置かず、仮想ノードのSTART・ENDにもチェック用ファイルを作らない。
- HEAD変更だけでRegistryの個別タスクの状態や未解決事項を消さない。後続へ残す仕事は、その接続と条件を維持する。

HEADは探索境界を示す。ゲートIDに含まれる版番号だけで、ゲート条件の達成を判断しない。未接続区間がある場合も、HEAD移動をその区間の条件達成の証明にしない。

JSONは過去のカードも含む。Studioは初期状態の「HEAD から」で以前の版を表示対象から外し、「全体」で履歴を含めて表示する。表示の絞り込みと、条件の達成・個別タスクの完了は区別する。

## JSONとStudio

`RegistryApp/sync.py`がRegistry・カード・HEADからJSONを生成する。既存JSONを正本にせず、JSONなしでも作り直せる。報告用の差分比較を除き、古いJSONの情報は引き継がない。

```sh
python3 Maintanance/RegistryApp/sync.py
```

リポジトリ直下から実行する。Node.jsやMarkdown変換ライブラリの指定は[Studioの利用手順](../RegistryApp/README.md)に従う。

構造上、ID重複やカード情報不足、無効な端点、同一フォルダの複数ゲートは不整合となる。正本リンクも確認対象。版内のタスクの分岐・合流、ゲート不足による版間の未接続、最後のゲートの接続先不在は許される。線の種類は廃止済みで、種類の検証を要件にしない。

## 原型仕様と現行実装の差（2026-10-18確認）

このREADMEの改訂だけでは、同期処理やStudioの実装は変更しない。

- 現行のフォルダ比較は、数字部分を数値として比較する方式。利用者による方式の確定は別途必要。
- 現行の同期処理はゲートIDから接続先フォルダを求め、行き先不在や版間の未接続をエラーにする箇所が残っている。原型仕様の「次のフォルダへ接続」「末尾ゲート・未接続を許容」への追随が必要。
- 現行の状態表示には、ゲートIDの版番号とHEADの比較で済みとする処理が残っている。ゲートIDが行き先を意味しない構造に合わせ、配置とHEADによる表示規則を別途整理する必要がある。既存の表示を条件達成の証拠にしない。

`_Archived/`は履歴・証拠の保存先であり、現行の条件や権限を自動的に復活させるものではない。過去の版フォルダを残す場合も、HEADによる通常作業の境界を守る。
