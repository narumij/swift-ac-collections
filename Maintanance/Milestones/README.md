# Milestones

版フォルダとカードの配置を計画の構造とし、スクリプトが接続を生成する。現在地は[HEAD.md](HEAD.md)。人間向けの実績・集計は[進捗報告](../MILESTONES.md)に置き、工程や到達条件を二重管理しない。

## 版フォルダとカード

- この直下のフォルダが各版を表す。名前が `_` で始まるフォルダは対象外。
- 各版フォルダには、名前をそのまま使った `END-<版>` が自動で付く。ドットを除去しない。
- `NN_*.md` が版内のマイルストーンカード。ファイル名の昇順で一本につながる。順序番号は `10_`、`20_` のように桁を揃える。
- `GATE-<次の版>.md` がその版の最後のリリースゲート。行き先フォルダをファイル名で指定する。版番号のソート順から行き先を推測しない。
- `GOAL.md`など、それ以外のファイルはカードとして読まない。最後の版はリリースゲートを持たなくてよい。空フォルダをGitに残す場合は、カードにならない保持用ファイルを置く。

END-x.y.z は版フォルダごとの集合点で、実ファイルを置かない。名前や独自の条件も持たない。

```text
10_本文.md → 20_検証.md → END-現在の版 → GATE-次の版
                                             ↓
                              次の版の最初のカード（なければEND）
```

カードは[テンプレート](GATE_TEMPLATE.md)に従い、`# カード情報`（ID・名前・途中のカードだけ状態）、`# 正本`（リンクまたは「このファイル」）、`# 記録`の三部に分ける。正本はカード情報に含めず、記録本文は接続生成の入力にしない。

既存カードの固定IDとカード内の名前は、並べ替えや移動では変更しない。ファイル名の先頭番号は順序変更のために変更できる。新しいカードには新しいIDを付け、再利用しない。途中のカードは `MS-*`、版ゲートのIDは `GATE-x.y.z`、名前は「x.y.z リリース」とし、版ゲートのファイル名と一致させる。実施する版は置き場所で表し、カード内に重複して固定しない。

## 版内のDAGと接続の正本

マイルストーンカードの経路は一本道に限定する。一方、その工程へ合流するタスクは分岐・合流できる。版内では、前提から後続へ向かう線が最終的にENDへ集まるDAGになる。ENDを根として眺めると、矢印は根へ向かう向き。

- タスク間の依存は[Task Registry](../ProgressV2/TASK_REGISTRY_V2.md)の「Task precedence」。
- タスクとEND・途中カードの接続は同書の「マイルストーン接続」。
- 線に種類はない（2026-10-17廃止）。線は関係の所在を示し、完了・着手・再開の条件はRegistryの制約文と各カードの本文で持つ。
- 版ゲートへ入る線は、そのフォルダのENDからだけ。途中カードにはタスクが直接接続してよい。 タスクは版の中の行動なので、その版のENDまたは途中カードにつなぐことで、どの版の仕事かを明確にする。 背景の会話や補足情報が失われても、接続先から対象版を読み取れるようにし、どの版の仕事だったかを巡る混乱を防ぐ。

同期処理はタスクの接続先・方向を暗黙に付け替えない。線があることだけで、自動開始・ユーザー判断の代行・凍結解除を認めない。

## 計画の組み替え

版内の順序はカードのファイル名の先頭番号で変更する。別の版へ作業を移す場合は該当カードを移し、影響するタスクの到達先を確認する。

途中に版を挟む場合は、新しい版フォルダを作り、既存のリリースゲートをそこへ移し、元のフォルダに新しい版へのゲートを置く。例えば `0.5.4 → 0.6.0` に `0.5.5` を挟むときは、`0.5.5/`へ`GATE-0.6.0.md`を移し、`0.5.4/`へ`GATE-0.5.5.md`を追加する。

同じENDを目指すタスクの接続は変えなくてよい。既存ゲートのIDと条件は保持し、移動・改名した文書の参照リンクを調整する。条件自体を変える場合は判断者と理由を記録し、計画変更を旧条件の達成として扱わない。未達を引き受けて進む判断も、条件を変更する判断とは分ける。

**マイルストーンとゲートの作業は必ずユーザーが同席し、AI単独では行わない。** このためカードに担当欄は持たせない。

## HEADが示す境界

HEADは現在地であり、通常の探索・作業範囲の境界。現在地より前の版は履歴として保持し、通常の作業対象から外す。AIは前の版を毎回読み直さず、必要な証拠があるときだけ参照する。HEADを進める判断はユーザーが行う。

- 現在地以下の版ゲートは済みとして扱う。
- 現在地より前のフォルダのEND・途中カードは済みとして扱う。
- 現在地以後の途中カードには `- [ ] DONE` / `- [x] DONE` を持たせる。版ゲートとENDにはチェックを置かない。
- HEAD変更だけでRegistryの個別タスクの状態や未解決事項を消さない。後続へ残す仕事は、その接続と条件を維持する。

実装上、現在のJSONは過去のカードも含む。Studioの「全体」表示も過去を含み、HEAD以前の自動非表示はまだ実装していない。Studioの版の選択欄で「HEAD から」を選ぶと、HEADより前の版を外して表示できる（2026-10-17。開いたときはこの表示。「全体」も選べる）。上記の運用上の境界と、画面の自動絞り込みは区別する。

## JSONとStudio

`RegistryApp/sync.py`がRegistry・カード・HEADからJSONを生成する。既存JSONを正本にせず、JSONなしでも作り直せる。報告用の差分比較を除き、古いJSONの情報は引き継がない。

```sh
python3 Maintanance/RegistryApp/sync.py
```

リポジトリ直下から実行する。Node.jsやMarkdown変換ライブラリの指定は[Studioの利用手順](../RegistryApp/README.md)に従う。

ID重複、カード情報不足、正本リンク切れ、不正な関係種類・端点、循環などを検査する。版間経路の分岐・合流・孤立、同じ版の複数リリースゲート、行き先フォルダの不在も不整合となる。版内タスクの分岐・合流は許される。

`_Archived/`は履歴・証拠の保存先であり、現行の条件や権限を自動的に復活させるものではない。過去の版フォルダを残す場合も、HEADによる通常作業の境界を守る。
