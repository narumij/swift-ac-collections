<a id="release-0-7-0--現在の状態"></a>
## 現在の状態

0.6.0 release完了待ち。これはactive release Registryではなく、0.7.0のrelease検討を開始するための
入口と判断境界を保持する文書である。主要タスクはリリース工程準備とSPI登録・公開導線整備に確定。現時点ではrelease候補commit、その他の製品上の到達範囲、
branch方式、下記で確定した文書Validation計画レビュー以外の必須gate、tag位置を確定しない。

`_ReleaseTask/`へ人間向け工程表をコピーする前の段階では、release、branch作成、commit、tag、push、公開を
許可しない。

<a id="release-0-7-0--release検討開始条件"></a>
## Release検討開始条件

0.6.0 releaseが完了し、その完了証拠と0.6.0へ含めた範囲・後続へ残した範囲が現行記録から確認できることを、
0.7.0のrelease検討を始める前提とする。

前提が満たされたことだけでは、0.7.0の開始、到達範囲、残taskの採用、凍結解除は成立しない。開始判断に向けて委任された範囲で、0.6.0後の公開面、残課題、品質・文書状態を判断材料として揃え、
0.7.0へ含める製品上の到達範囲とrelease作業を開始するかを一つの判断として確定する。

<a id="release-0-7-0--開始判断までの依存"></a>
## 開始判断までの依存

0.6.0のrelease作業が具体化した時点で、その完了を表すtaskと証拠の置き場を確認し、本書から参照する。現時点では0.6.0の完了taskが存在しないため、架空のtaskや依存辺を作らない。

0.6.0から後続へ残したtaskは、その状態、担当、再開条件を維持する。0.7.0の候補になり得ることを理由に、
`FROZEN`を解除したり、`PROPOSED`を採用したり、`USER_ONLY`へ着手したりしない。

<a id="release-0-7-0--release作業の起動"></a>
## Release作業の起動

開始条件に到達したら、次の順序で起動する。

1. 0.6.0の完了記録、以後の差分、未完了task、品質・文書状態を確認する。
2. 0.7.0へ含める変更と後続へ残す変更、version固有要件の候補を分ける。
3. ユーザーへ、0.7.0の製品上の到達範囲とrelease作業を開始するかを一問で確認する。
4. Yesの場合だけ、`../User/RELEASE_PROCESS.md`を`_ReleaseTask/`へコピーし、versionを実値へ置き換える。
5. 確定したbranch方式、必要な品質gate、version固有taskを人間向け工程表と通常Task Registryへ反映する。
6. release中の状態と証拠は人間向け工程表と各工程の正本へ記録し、完了または中止時に本書と通常Task Registryへ還元する。

人間向け工程の正本は`../User/RELEASE_PROCESS.md`とする。release専用Task Registryを別に作らない。

開始判断のための照合で必要性、影響範囲、担当、受入条件を確かめ、独立した仕事が必要な場合だけ通常Task Registryへ

## 到達点と配置

0.8.0では、ドキュメントへのコードスニペット追加と、ドキュメントの再検討を扱う。
0.7.0 → 0.8.0を版の順序として配置する。SPI公開・人間レビューとの厳密な前後関係は今回確定していないため、追加の必須依存にはしない。

| task | 内容 | 完了時に残すもの |

| DOC-039 | ドキュメントの再検討 | 現行文書の構成・説明・導線を見直した所見、改善案、残るユーザー判断。公開方針の変更を独断で確定しない |

スニペットの材料は[サルベージしたアンケート](../../UserDocuments/SnippetSurvey/README.md)。調査済みDOC-019・020を復活させず、旧コードをそのまま使用しない。再検討による変更の必要性と範囲が決まったら、必要な判断・反映作業を分けて記録する。

<a id="release-0-8-0--060との境界"></a>
## 0.6.0との境界

今回の0.6.0文書作業では、既存スニペットの構成・掲載数を固定し、追加・削除しない。既存例の現行契約との照合・検証は行う。誤りがあれば内容の訂正として扱い、増減が必要な場合は無断で変更せず記録する。拡充と文書全体の再検討は0.8.0へ送る。これによって既知の誤りを合格扱いにしない。

各0.x.0での品質改善と、ユーザーによるrelease範囲・開始・最終判断は維持する。SPI登録や人間レビューの既存条件を置き換えない。

# SPI公開マイルストーン

2026-10-16、Astra。管理入口：[マイルストーン管理](../../MILESTONES.md)。

<a id="spi-publication-milestone--時期の決定"></a>
## 時期の決定

2026-10-16、ユーザーの判断で従来の0.9.x release後から前倒しし、0.7.0の主要タスクとした。0.7.0をリリースしてから登録し、結果確認と導線整備までを0.7.0の公開整備として扱う。今回の計画更新は対象版の登録可判定や登録実行そのものではない。

<a id="spi-publication-milestone--到達条件"></a>
## 到達条件

0.7.0 release後、対象版について[登録前の公開準備判定](../../Current/SPI_REGISTRATION_GATE.md)でユーザーが登録可と判断し、登録実行を委任する。DOC-026で登録し、実在するpackage page・互換性表示・module別DocC結果を確認する。続いてDOC-027でSPI提示のbadgeと確認済みURLをREADME・Pagesへ接続する。この一連が成立したことを証拠とともに記録する。

QUALITY-005の完了だけでは登録可とは限らず、判断内容を確認する。実行taskは有効な計画として依存条件で待たせ、追加の凍結解除を要求しない。現在の作業状態は[Registry](../../ProgressV2/TASK_REGISTRY_V2.md)を参照する。

<a id="spi-publication-milestone--後続"></a>
## 後続

公開後、文書が落ち着いた時点から1.0品質判断までの間に[文書Validation計画](../../UserDocuments/DOCUMENTATION_VALIDATION_PLAN_DRAFT.md)の人間レビューへ接続する。SPI公開の成立だけで文書の利用理解や1.0品質を合格にしない。具体的な登録・導線作業の資料は[文書CI計画](../../Current/DOCUMENTATION_CI_PLAN.md)を参照する。

<a id="spi-publication-milestone--判断と到達証拠"></a>
## 判断と到達証拠

今回の整理では登録・公開は行っていない。対象版、登録可判断、登録結果、DocC URL、公開導線の確認結果は成立した時点で参照を残す。登録可判断そのものはSPI_REGISTRATION_GATE.mdに記録し、二重管理しない。
