# タスクの分解と再構成

## 目的

この文書は、会話、調査、実装、および検証の途中で見えてきた作業をtaskとして分解し、既存のtask graphへ
組み込み直す原則を定める。

task分解の目的は、作業を細かくすることではない。事実確認、既存原則の適用、実装上の選択、条件付きの
問い、およびユーザーだけが決める本質的判断を分離し、不要な判断を減らすことである。

もう一つの目的は、失敗を局所化することである。一つのtaskに一つの成果と受入境界を持たせ、失敗時の
修正、再検証、切り戻し、および受入が他のtaskの成功部分を巻き込まない構造にする。

分解後は、task名を並べるだけで終わらない。既存taskを含む依存関係、Flow、ready集合、critical path、
優先順、および受入可能量を再評価し、実行可能な構造へ再構成する。

## 要旨

この文書の原理は、次の三点に集約される。

1. 偶有的な判断をtask整理によって消し、それでも残る本質的な判断だけを抽出する。
2. 独立した成果、状態、依存、判断、証拠、または受入を持つ作業をtaskへ分け、既存graphへ組み込む。
3. graphを再構成して継続条件を評価し、条件を失ったtaskは実行を止める。

後続の分類、基準、および手順は、この三点を異なる状況へ適用するための説明である。細則を個別に
暗記して運用することや、想定できるすべての事例を事前に列挙することを目的としない。

## 分解へ戻る契機

次の事象は、進行中の作業をそのまま拡張せず、task分解と再構成の必要性を確認する契機である。

- 会話の中で、当初見えていなかった独立作業が具体化した。
- 現在taskへ新しい前提、判断、証拠、担当、停止点、または完了条件が必要になった。
- 一つのtaskに、事実確認、製品判断、実装、Verification、Validationが混在した。
- 新しい作業によって既存taskの依存関係や着手順が変わり得る。
- 最優先task、critical path、または複数taskの合流点が変わり得る。
- 既存の前提、契約、証拠、または完了判定が反証された。
- taskのscopeが、途中状態や受入結果を独立して保持できないほど広がった。

新しい作業が見えただけで、必ずstable taskを増やすわけではない。重大な順序変化または新しい必須依存の
可能性がある場合は、先に影響範囲の実行を止める。停止と再開は
[`TASK_DEPENDENCY_RUNTIME_STOP.md`](TASK_DEPENDENCY_RUNTIME_STOP.md)を正本とする。

## 会話から本質的判断を抽出する

### 判断によるtaskの三分類

taskは、判断との関係から次の三つに分類する。

- **本質的な判断task:** 事実、既存原則、依存関係をどれだけ整理しても消えない判断を一つだけ扱う。
  選択肢、影響、証拠は整理できるが、最後は留保された権限を持つ者が決めなければならない。
- **偶有的な判断task:** 情報不足、未整理な前提、依存、順序、または現在の実装によって、判断が必要な
  ように見えている作業を扱う。taskを整理して答えが自明になれば、判断そのものが消える。
- **判断不要のtask:** 必要な判断と前提が現在確認できる範囲で閉じており、定められた方針、scope、
  完了条件に従って実行または検証できる作業を扱う。

task分解による判断削減とは、本質的な判断を消すことではない。偶有的な判断を事実、原則、依存関係で
解消し、それでも残る本質的な判断だけを抽出することである。偶有的な判断taskは、整理によって
判断不要のtaskになるか、消すことのできない核心だけを本質的な判断taskとして残す。

この三分類は「判断を誰がどのように閉じるか」を表す。`DISCOVERY / DECISION / EXECUTION`は「taskで
何を行うか」を表すため、両者を同じ分類軸として混ぜない。

会話中の発言を、そのままユーザー判断として記録しない。少なくとも次へ分類する。

| 分類 | 扱い |
| --- | --- |
| 事実不足 | `DISCOVERY`または既存task内の調査で確認する |
| 事実訂正 | 証拠と前提を直す。新しい製品判断にはしない |
| 既存契約の再確認 | 正本との一致を確認する。契約変更taskにはしない |
| 既存原則から一意に導ける結論 | 原則を適用し、同型のユーザー判断を増やさない |
| 実装上の局所選択 | 許可済みscopeと完了条件の範囲で担当agentが処理する |
| 条件付き判断候補 | 必要性を決める上流条件が閉じるまでstable taskにしない |
| 暫定措置 | 一時状態と解除条件を記録し、製品契約として固定しない |
| 本質的判断 | 公開契約、製品方向、許容risk、優先順位など、留保された権限へ返す |

判断削減とは、思考や確認を省くことではない。事実、原則、依存関係で閉じられる問いを処理し、それらでは
決まらない本質的判断だけを抽出することである。

本質的判断が後続taskの成立に必要なら、一判断一taskの`DECISION`として分離する。その判断を暗黙に埋めた
`EXECUTION`を作らない。上流判断の答えによって消える問いは、条件付き候補のまま保持する。

## taskへ分ける基準

見つかった作業が次のいずれかを独立して持つ場合は、別taskとすることを検討する。

- 状態遷移または再開条件
- ユーザー判断または権限境界
- 必須依存または独立した後続task
- 担当または受入担当
- 証拠、Verification、Validation
- 停止条件または失敗時の戻り先
- 完了条件またはcommit境界

反対に、独立した状態、依存、判断、証拠、受入を持たない単なる実行手順は、親taskのsubstepにする。
file数、関数数、手順数、作業時間の長さだけを理由にstable IDを増やさない。

各taskは、少なくとも次を単独で説明できる境界にする。

- 何を成立させるtaskか
- 何が既に決まっているか
- 何を決めてはいけないか
- 何を入力として必要とするか
- 何を成果と証拠として残すか
- どの条件で停止、再開、完了するか

## 分解とインライン化

task分解は、task数を増やした状態を完成形とする操作ではない。混在していた判断、依存、責任、成果、
失敗、および受入をいったん分けることで、不要な作業を削除し、それぞれの境界を適切な位置へ移動できる
状態にする。

分解後の整理によって独立した状態、依存、判断、証拠、または受入を持たなくなった断片は、親taskの
substepへインライン化する。分解によって構造を観測・編集可能にし、削除、境界移動、依存の再接続を
行った後、インライン化によって適切なtaskサイズと受入境界を回復する。

## task graphの再構成

taskを追加、分割、除外、または変更した場合は、そのtaskだけでなく既存graphへの影響を確認する。

1. 新しいtaskの前提となる既存taskを特定する。
2. 新しいtaskの成果を必要とする既存taskを特定する。
3. 各関係を`SEQUENCE`、`PARALLEL_JOIN`、またはsoft orderへ分類する。
4. 不要になった辺、逆転した辺、重複したtask、cycleを確認する。
5. トポロジカルに依存条件を評価し、ready集合を求め直す。
6. goalへの必要性、critical path、risk、および受入可能量から次の実行候補を選ぶ。

この列挙は必要になり得る確認を示すものであり、毎回すべての操作を義務づけない。既存taskの説明または
依存辺一つを直すだけで構造が復元できるなら、新しいtaskや文書を作らない。

### Flow

- `SEQUENCE`: 前提taskの成果なしに後続taskを開始または継続できない。
- `PARALLEL_JOIN`: 独立部分は並行できるが、後続taskの完了前に前提taskとの合流が必要である。
- soft order: 必須依存ではないが、効率、risk、critical path、受入可能量から推奨する順序である。

便利な順番を必須依存にしない。反対に、後続の成立に必要な作業をsoft orderへ落として、未充足のまま
実行可能にしない。

## goal、優先順位、taskを分ける

goalは、release、1.0採用、将来のjudge搭載など、複数taskを越える大きな到達点である。task連鎖の途中に
ある局所的な成果や、現在最優先の実装taskをgoalへ格上げしない。

最優先であることは、goalであることを意味しない。依存整理によって複数の後続を塞ぐtaskが判明した場合、
そのtaskをcritical path上の優先taskとして扱い、goal自体は維持する。

`ready`であることも、最優先であることを意味しない。ready集合から、現在のgoalに必要なtaskだけを残し、
critical path、risk、soft order、ユーザーの最新指示、および受入可能量で次のtaskを選ぶ。

## 分解と実行の境界

task分解は、進行中taskへ作業を追加して続行するための手続きではない。新しい必須依存によって現在taskが
readyでなくなった場合は、前提taskが完了するまで元taskを再開しない。

分解とgraph再構成が完了しても、自動的な実装再開を意味しない。依存上のreadyに加え、有効な委任が
必要である。ユーザーが直接編集または介入して委任を停止、縮小、または撤回した場合は、graph上readyでも
状態変更を再開しない。

## 検証中の仮説

task管理の中心原則となり得る候補として、次の二つを保持する。

- **依存の最小性:** 後続taskは、その成立に必要な前提だけに依存する。
- **受入境界の局所性:** 各taskは、成果と失敗を自身の受入境界に閉じ込める。

この二つは採用済みの規則ではない。既に分解された成功事例を説明するだけでなく、構造がまだ決まっていない
実作業へ先に適用し、task境界と依存方向を正しく導けるかを確認する。予測が外れた場合は、原則を守るために
事例を解釈し直さず、反証として残す。

## 成果

適切なtask分解と再構成によって、次の状態を作る。

- 不要なユーザー判断が除かれ、本質的判断だけが明示されている。
- 各taskの担当、権限、停止点、証拠、受入、commit境界が復元できる。
- 必須依存を満たさないtaskが実行されない。
- 順序変化がready集合と優先順位へ反映される。
- 途中停止しても、前提回復後に正しいtaskから再開できる。
- taskがgoalへ格上げされず、goalとcritical pathの関係が保たれる。
