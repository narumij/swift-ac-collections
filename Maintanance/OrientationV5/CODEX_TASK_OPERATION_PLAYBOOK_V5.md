# Codex Task Operation Playbook V5

> **文書状態:** 2026-10-14作成、採用前の候補。AGENTS候補V3に合わせた改訂案であり、現行正本や権限を変更しない。対象版と参照先は[作成メモ](README.md)に記す。

## この文書の役割

任された仕事を、事実確認、実行、受入、記録、次の仕事へつなぐときの扱いを示す。必要な場面の節を使い、毎回すべてを行うチェックリストにはしない。

協働の原理と操作権限は`AGENTS.md`、taskの種別・状態・依存・採番は`Maintanance/PROGRESS_OVERVIEW.md`、分解の考え方は[taskオリエンテーション](TASK_ORIENTATION_V5.md)で確認する。本書は別の権限やRegistryを作らない。

## 1. 現在地と今回の到達点を確かめる

最新の依頼、現在の目標、Registry、選択taskの詳細正本から、何を成立させる仕事かを確認する。必要な範囲でファイル、差分、実行結果などの現在の事実を照合する。

今回渡す成果、任された操作、受入条件を分ける。ドラフトの作成に、採用や現行正本の変更を含めない。外から受け取った成果は、受領だけで変更・採用できるものとして扱わない。

現在地の復元に必要のない過去資料や未選択taskは読まない。現行資料同士が食い違う場合は、どの決定や状態をどの正本が持つかを特定し、推測で一方を正本に変えない。

## 2. 答えを確かめ、境界を組み直す

疑問は、実物、実行手段、正本、権限者など、その答えの所在へ当てる。実行結果は実行した条件の事実を示し、履歴は起きた変更を示す。それだけで作者の意図や未承認の採用を確定しない。

見つかった仕事を、[taskオリエンテーション](TASK_ORIENTATION_V5.md)の「判断を一つかゼロにする」と「分け、不要なものを消し、組み直す」に従って扱う。新しい判断点が出たtaskは停止し、分割へ戻る。

再構成では、必要な前提と後続、独立した判断や受入、不要になった仕事を確認する。既存の説明や依存を直せば足りるときは、新しいtaskや文書を増やさない。状態や前提が変わった部分だけを見直し、すべてを再調査しない。

記録の変更と実行の許可を分ける。taskを分け直しても、新たな範囲の実行許可は生まれない。必要な前提がそろい、現在の委任に含まれる仕事を次に選ぶ。

## 3. 実行・委任する

実行するtaskの方針、範囲、入力、停止条件、証拠、受入を確認する。既に決まった範囲で作業を進め、同じ許可を繰り返し求めない。操作ごとの許可が定められているものは、その取り決めに従う。

別の担当へ渡すときは、これらの境界と返却先を明確にする。未確定の方針を「方法は任せる」に含めない。複数taskを一つの依頼で渡す場合も、各taskの判断と受入の境界を維持する。

Claudeへの一時的な受渡し、固定IDへの照合、XcodeでのWorkerへの依頼は、`AGENTS.md`の「委任と受渡し」と、そこで指定された担当文書に従う。割当を作るためだけに仕事を作らず、担当名を読んだだけで自分への委任とみなさない。

検証の返りが遅い場合は、未確認の前提、依存する範囲、外れたときの手戻り、現在の委任を踏まえて進める量を決める。未充足の必須前提や停止条件は、この扱いで飛ばさない。仮に進めた成果は、確定済みの成果と区別する。

## 4. 前提が変わったら、影響する作業を止める

`ready`は開始時だけでなく、実行中の成立条件でもある。必要な前提が欠けている可能性に気づいたら、依存表の更新が済むまで作業を続けず、影響する範囲を安全に止める。

状態を保ったうえで、何が確認済みで、何が疑わしく、どの成果に影響するかを調べる。依存関係を確定するための調査と、停止した作業の続行を混同しない。

| 判明したこと | 扱い |
| --- | --- |
| 新しい判断点がある | そのtaskを止めて分割へ戻る。未確定の判断を埋めて続けない |
| `SEQUENCE`の前提が欠けている | 依存する作業を止め、必要な前提成果と有効な委任がそろってから再開する |
| `PARALLEL_JOIN`の合流が未完了 | 影響を受けない独立部分は進められるが、合流前に後続を完了としない |
| 推奨順だけが変わった | 必須依存を追加せず、現在の目的と優先順位から次を選び直す |
| 必須前提の疑いが解けた | 不要な依存を追加せず、他の停止条件と委任を確認する |
| ユーザーの介入・共有作業領域の直接編集に気づいた | `AGENTS.md`に従って自律実行を止め、追加変更をせず影響を確かめる。影響する仕事は明示的な再委任まで再開しない |

新しい判断点に伴う停止は、そのtask全体に適用する。別のtaskについては、回答や影響に依存せず、着手条件と権限が成立するものを進められる。

状態を変える操作をやり直す前には、現在の状態を確認する。過去に成功した手順や、以前の必要性だけを根拠に再実行しない。`FROZEN`の再開などに必要な明示指示は維持する。

## 5. 成果を受け入れる

担当者の説明と成果の実物を照合し、必要な差分、実行条件、結果、反証、残る不確かさを受入条件に当てる。証拠を独立に確認することは、すべての検証を無条件にやり直すことではない。証拠の適用範囲や再現性に不足がある部分を確かめる。

確認できた主張と範囲を明らかにする。部分的な成功を全体へ広げず、外部待ち、判断待ち、除外、残るリスクを成功へ丸めない。未確認のまま採用する必要があるなら、その不確かさを引き受けられる持ち主の判断を得る。

到達条件がドラフトなら、その状態を受け入れる。後の採用や公開の条件を今回の完了へ混ぜない。受入の担当であることだけでは、委任に含まれない方針判断や他者成果の書換えはできない。

機能テスト、性能測定、文書生成、レビューなどは、それぞれが確かめられる問いに使う。選択taskが要求する品質について、必要な証拠が足りているかを見る。無関係な検査を一律に追加しない。

## 6. 記録をつなぎ、次の仕事を選ぶ

受入結果を、変更権限と委任の範囲で詳細正本とRegistryへ反映する。Registryの確定更新は、その仕事を明示的に割り当てられたCodexが行う。返却記録や一時queueの内容を、そのまま確定更新とみなさない。

記録には、何が成立したか、何がまだ成立していないか、証拠と判断理由をどこで確認できるかを残す。詳細をRegistryへ重複して集めず、そこから辿れるようにする。

上流の成果を受けた後は、下流の問いや作業がまだ必要かを見直す。不要になった仕事は理由を残して残作業から外し、失った独立性に応じて手順をまとめる。除外は実施済みの完了と区別する。

固定IDの採番・使用済み番号は進捗一覧の「Task ID採番状態」に従う。分割・統合・除外で古いIDを別の仕事へ再利用せず、必要な対応関係を残す。記録を簡潔にするときも、現在地、必要な前提、権限、証拠への経路を失わない。

依存、状態、再開条件、委任を確認し、現在の目標に必要な次の仕事を選ぶ。適切な仕事がなければ、割当や報告のために新しい仕事を作らない。

## ルーティーンとGit操作

「ルーティーン」の意味と各段階は、`AGENTS.md`の「会話と明示的な呼び出し」に置く。本書の一周を、新しい省略指示や別の許可として重ねない。

成果の受入・記録、成果のcommit、次の仕事の整理と割当、管理変更のcommitを必要に応じて行う。commit候補には受入済みの成果と対応する記録をまとめ、無関係な既存変更を保つ。

branch作成、commit、pushの操作直前の許可、ユーザーが実行する操作、リリース後の記録branchは、`AGENTS.md`の「Git操作の取り決め」に従う。ルーティーンという依頼だけで、これらの境界やtaskの再開条件は変わらない。

## 訂正と報告

訂正を受けたら、その内容を現在の作業モデルへ反映する。影響する事実、task境界、依存、受入条件、記録を特定し、変更できる範囲で整合させる。権限外の文書は訂正案として返す。

成果を引き渡し、変更権限を持ち主へ返した部分には、再び変更を任されるまで手を加えない。誤りを見つけたら、訂正案と依存する仕事への影響を示す。

報告は、成果とその意味、証拠が保証する範囲、残る保留、必要な持ち主の判断を先に伝える。内部のIDや状態の操作をユーザーへ押し戻さず、通常は平易な仕事名に直す。
