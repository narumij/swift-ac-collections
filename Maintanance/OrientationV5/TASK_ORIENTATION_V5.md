# Codex taskオリエンテーション V5

> **文書状態:** 2026-10-14正式採用。現行`AGENTS.md`と組み合わせて使うtaskオリエンテーションの正本。採用の経緯と参照先は[採用記録](README.md)に記す。

## この文書の役割

会話と現在の目的から、必要な問い、判断、作業、依存、受入の境界を組み立てる方法を示す。taskの種別・状態・依存・採番の規定と現在地は`Maintanance/PROGRESS_OVERVIEW.md`を正とし、本書はその使い方を説明する。

task管理で残したいのは、何が必要で、何が決まり、誰が何を行い、どの証拠で次へ渡せるかである。項目の数や細かさは成果ではない。

## 1. 需要と到達状態を確かめる

taskを並べる前に、今回何が成立すればよいかを確認する。

- 作業方法：コメントを書く。
- 到達状態：現行の契約を、ユーザーがレビューできる文書にする。

中間目標は、複数のtaskを通して実現したい到達点である。今いちばん重要なtaskを、そのまま目標へ格上げしない。目標に含まれることだけでは、着手条件や権限は変わらない。

目的が曖昧な場合は、任された範囲で判断に役立つ事実を調べる。推測で目的を決定したり、将来あり得る作業を先回りして登録したりしない。

## 2. 問いを、その答えの所在へ渡す

問いがあることと、新しい判断が必要なことを分ける。

| 問い | 先に当たるもの |
| --- | --- |
| 実際に何があるか、何が起きたか | 実物、差分、履歴、実行結果 |
| 定めた条件で成立するか | コンパイラ、テスト、測定など、その条件を確かめる手段 |
| 何が既に決まっているか | 現在の指示、該当する正本、記録された決定 |
| 何を目的とし、どの選択やリスクを引き受けるか | その判断を持つ者 |

事実や既存の決定で答えが出れば、根拠と適用範囲を確かめて使う。AI同士の合意で、得ていない証拠を代用しない。多くの後続を決める問いは先に確かめ、答えの誤りも広く伝わることに注意する。

一つの案しか残らなくても、権限者に留保された採用や操作の判断は残り得る。技術的な結論と、実行の許可を分ける。

## 3. 判断を一つかゼロにする

taskを作るときは、判断が一つかゼロになるまで分解する。種別は、進捗一覧の規定に従う。

| 種別 | taskが扱うもの |
| --- | --- |
| `DECISION` | ユーザー判断を一つだけ扱い、結論を後続の入力にする |
| `DISCOVERY` | 方針と境界が確定済みの事実確認。事実、選択肢、依存、判断候補を見つける。公開契約や実装方針を決定しない |
| `EXECUTION` | 必要な判断がすべて確定した範囲の実装、文書反映、検証 |

`DISCOVERY`と`EXECUTION`はノー判断taskである。既に定めた方針を適用し、証拠を読んで確かめる思考は必要だが、未確定の選択を担当者が埋めることは含まない。

**実行中に新しい判断点が見つかったら、自分で埋めて続けず、そのtaskを止めて分割へ戻る。** 「小さな判断」「委任範囲内の判断」という言い換えで、この停止点を消さない。必要な事実確認と、一判断ごとの`DECISION`を分け、その結論を必要とする実行へ接続する。

事実を調べれば解ける疑問や、既存の決定の再確認まで、新しいユーザー判断にしない。また、回答待ちのtaskと独立していて、着手条件と委任が成立している別のtaskは進められる。

## 4. 分け、不要なものを消し、組み直す

分解すると、混ざっていた判断、依存、担当、証拠、停止点、受入が見える。そこから、必要性が消えた作業を外し、必要な依存だけを結び直す。

独立した判断、状態、担当、依存、証拠、受入などを持つ部分は、別のtaskとして扱う。独立させる意味がなくなった手順は、親taskの手順へ戻す。これをインライン化と呼ぶ。

ただし、複数の判断を一つにまとめたり、必要な検証や受入の境界を消したりしない。まとめた後も、何を誰が決め、何を確かめ、どの条件で止まるかが分かる形を保つ。分解の必要性は判断や境界で決め、所要時間の短さだけで省略しない。ファイル数や手順数だけを理由に固定IDを増やさない。

例えば、設定の採否を聞く予定でも、既存の方針と確認結果から答えが確定すれば、改めてユーザーに決めてもらう必要はない。独立した判断が消えた部分は、根拠を記録する手順へ戻せる。反対に、採用がユーザーに留保されているなら、その判断は残る。

この分解とインライン化は、リファクタリングやコンパイラ最適化と似た見方ができる。対応と限界は[AI協働の基本思想](AI_COLLABORATION_PHILOSOPHY_V5.md)で説明する。

## 5. taskの境界を説明できるようにする

各taskでは、目的と現在の目標への関係、範囲と対象外、担当と権限、詳細正本、必要な入力と証拠、停止条件、完了条件と引渡先を説明できるようにする。

既存のRegistry行と詳細正本から辿れればよい。本書や比喩のために、同じ内容を新しい欄へ重複して記入する必要はない。成立に必要な範囲や条件が未確定なら、実行できるtaskとして扱わない。

成果の作成、成果の採用、公開や配置変更は、別の権限や受入境界を持ち得る。「完成したから採用まで行う」と繋げない。

## 6. 依存を必要な条件に絞る

依存は、後続の成果、検証、受入に不可欠な前提から求める。

| 関係 | 開始・継続・完了への影響 |
| --- | --- |
| `SEQUENCE` | 前提成果がなければ、後続を開始・継続できない |
| `PARALLEL_JOIN` | 独立部分は並行できるが、後続の完了前に前提成果との合流が必要 |
| soft order | 同時に着手できる仕事の推奨順。必須依存にはしない |

同じファイルを扱うことや、先に行うと便利なことだけでは必須依存にならない。一方、必要な前提を推奨順へ落として飛ばさない。共有箇所の競合など、実際の干渉は別途確かめる。

前提taskの除外は、前提条件の充足を意味しない。別の証拠で満たせるのか、その条件自体が不要になったのかを確かめる。循環が現れたら、必要な辺を都合で消さず、taskの境界と前提を見直す。

## 7. 着手できる仕事から、今必要な仕事を選ぶ

依存上の`ready`は、実行中も維持する条件である。次に進める仕事は、依存に加え、状態、担当、再開条件、現在の委任、目標への必要性を確かめて選ぶ。

`SEQUENCE`の前提と`PARALLEL_JOIN`の合流条件を区別し、全依存の完了を一律に着手条件にしない。並行可能でも、`FROZEN`や`USER_ONLY`などの制限は変わらない。

| 現在の目標との関係 | 意味 |
| --- | --- |
| `DIRECT` | 目標を直接閉じる、または判断可能にする |
| `NEAR` | `DIRECT`の必須入力 |
| `FAR` | 複数の段階を経て、現在の目標に必要 |
| `LATER` | 明示された後の目標・段階に属する |
| `OUTSIDE` | 記録された目標の外にある |

この区別は距離の数値や優先順位そのものではない。必要な`DIRECT`・`NEAR`・`FAR`から、完了までの依存、リスク、受入できる量を見て選ぶ。`LATER`・`OUTSIDE`へ進むには、ユーザーによる目標の変更か明示的な依頼が必要である。

## 8. 成果と証拠を、その範囲で受け入れる

完了は、taskが求めた状態が、必要な証拠とともに成立したことである。証拠がどの主張をどの範囲で支えるかを、受入条件と照合する。

レビュー可能なドラフトの引渡しが今回の完了なら、採用や公開までを余分な完了条件に加えない。反対に、必要な検証が残っているものを、担当者の完了報告だけで確定しない。

受入後は、成立した前提によって後続の判断や作業がまだ必要かを見直す。不要になった理由と記録への経路を残し、残作業から外す。固定IDは再利用しない。前提が後で変わった場合も、現在の需要、状態、権限を確かめてから扱う。

具体的な受入・記録・再開の手順は[Playbook](CODEX_TASK_OPERATION_PLAYBOOK_V5.md)を参照する。

## 初回理解確認

次の例は、書かれた条件だけで考える練習である。実際のtaskの開始や過去資料の調査には使わない。

### 例：現行名での文書ドラフト

ユーザーは「現行の契約をレビューできる文書ドラフト」を依頼している。契約と現在の型名は確認でき、書く範囲と検証方法も決まっている。公開名を将来も維持するかは未決であり、公開版の採用時までにユーザーが決める。

最初の計画では、名称判断を待ってからドラフトを書くことになっていた。しかし、今回の到達状態には、現行名で書いたドラフトで足りる。名称判断は公開版の採用前に必要なものとして残し、ドラフトの着手を妨げる依存だけを外せる。

ドラフトを書く、生成を確認する、結果を添えて渡すという手順を分けて眺めた結果、独立した担当や待ち条件がなく、同じ受入で確かめられるなら、一つのノー判断taskの手順へまとめられる。生成確認の証拠は残す。

### 説明できるか確かめること

1. 今回の需要と、後の段階で必要になる判断は何か。
2. どの依存を外せて、どの判断と証拠は残さなければならないか。
3. 分解した手順をまとめられる理由は何か。途中で新しい判断点が現れたらどうするか。
4. 文書が生成できることと、名前や内容を採用してよいことは、誰が何で確かめるか。
5. ドラフトの完成、採用、現行正本の変更は、それぞれどこで区切られるか。

固定した言い回しへの一致は求めない。不要な待ち、判断の埋込み、証拠の拡大解釈、権限の先取りを見分けられれば、依頼された実務へ進む。
