## taskの境界と記録

2026-10-17ユーザー明示委任：[Fable調整代理](../Current/FABLE_COORDINATOR_DEPUTY.md)の期間中は、同書の範囲でRegistry確定更新・採番・圧縮・掃除をFableにも委任する。現在の担当割当として扱い、他の判断・占有・文書保護・Git操作規則は維持する。

タスクを変更する前に、正本で現在の状態と最新の依頼を確認する。記憶や過去の状態を根拠に更新しない。

現在の目的に必要な問いを、実物・コンパイラ・テスト・正本・権限者など、その答えがあるところで確かめる。既知の型や設計パターンは、確認対象を選ぶために使う。実際の成立条件が分かる前に、あり得る全組合せや全後続taskを展開しない。

taskは判断一つかゼロになるまで分解する。新規登録・内容更新時は項目名の先頭へ種別を付ける。既存の未分類行を、今回一括で推測分類しない。

| 種別 | 閉じるもの |
| --- | --- |
| `DECISION` | 一つのユーザー判断。その結論を後続へ渡す |
| `DISCOVERY` | 方針・境界が定まった範囲の事実、選択肢、依存、判断候補の発見。公開契約や実装方針の採用は含めない |
| `EXECUTION` | 必要な判断がすべて確定した範囲の実装・文書反映・検証 |

`DISCOVERY`と`EXECUTION`はノー判断taskとする。実行中に新しい判断点を見つけたら、そのtaskを止めて分割へ戻す。「小さい」「委任範囲内」という理由で未決の判断を埋めない。事実確認や既存の決定を適用する思考は、新しいユーザー判断とは区別する。

調査が返した事実と、方式を採用する判断を分ける。採用・実装が必要な後続を、調査の完了だけで開始可能にしない。必要な判断・実行taskは、その必要性と境界が分かった時点で具体化する。

記録には、今回の到達点、担当と委任範囲、必要な前提・証拠、再開・停止・完了条件、詳細正本への経路を残す。既存の行と詳細正本から分かることを、追加の必須欄へ重複して記入しない。将来の未確定事項を、実行できるtaskとして扱わない。

独立した判断・担当・待ち条件・受入の意味がなくなった手順はまとめられる。複数の判断や必要な検証をまとめて消さない。不要になった仕事は理由を残して残作業から外し、実施済みの完了と区別する。IDは再利用しない。

完了はtaskの受入条件を必要な証拠が満たした状態である。担当者の完了報告だけでは確定せず、ドラフトの完成を採用・公開まで広げない。Task Registryの確定更新は、ユーザーからその仕事を明示的に委任された調整担当が行う。モデル名や共有記憶だけでは担当権限を得ない。

## 状態の扱い

状態は次の九つを使う。状態だけで、自分への割当・操作権限・現在の目的との関係を確定しない。

| 状態 | 扱い |
| --- | --- |
| `PROPOSED` | 忘失防止の候補。範囲・完了条件・担当・詳細正本・必須依存を確定し、状態を更新するまで着手・委任しない |
| `ACTIVE` | 現在扱う仕事として有効な状態。実行中ジョブや読み手への割当とは限らず、行の条件と現在の委任を確かめる |
| `WAITING_USER` | ユーザーの判断・確認を待つ。何を待つかを該当行と依存先で確かめ、依存先が`USER_ONLY`ならその制限に従う |
| `WAITING_EXTERNAL` | 外部条件が解消するまで着手可能とみなさない。解消は実際の情報・結果で確かめる |
| `FROZEN` | 明示的な再開指示なしに着手しない。前提の完了や候補の発見だけでは解除されない |
| `USER_ONLY` | ユーザー専任。本体の着手・代行・委任・催促をしない。整理・レビュー・検証などの補助を明示依頼された場合はその範囲だけ行い、本体の代行や完了受入にはしない |
| `DONE` | 定めた完了範囲が受け入れられた記録。残作業・着手候補に含めない |
| `EXCLUDED` | 必要性の消失や対象外などの理由で残作業から外した記録。実施成功や前提充足とはみなさない |
| `ARCHIVED` | 履歴へ移した記録。読むことによって現在の仕事へ復活させない |

`GRAPH-001`・`HIST-001`・`HIST-003`・`DOC-030`・`OPS-043`・`TEST-005`・`OPS-044`・`OPS-046`・`OPS-047`・`OPS-048`・`OPS-077`・`OPS-103`は常設の支援nodeとして`ACTIVE`を保つ個別の取り決めがある。現在の個別assignmentや実行中ジョブを意味しない。この意味をすべての`ACTIVE`へ一般化せず、各行の条件を読む。

外部待ちの仕事を開始できないことと、待っている条件が解消したかを任された範囲で確認することは分ける。凍結解除やユーザー専任の制限を、この確認から導かない。

## 依存関係の更新

Task precedenceには、内部task間の必須AND前提だけを記録する。Flowは`SEQUENCE`または`PARALLEL_JOIN`を必須とする。

- `SEQUENCE`：前提成果がそろってから後続を開始・継続する。
- `PARALLEL_JOIN`：前提に依存しない部分は並行でき、後続の完了前に合流する。
- soft order：同時に着手可能な仕事の推奨順。必須依存へ変えない。

前提taskの除外・履歴化は、条件の充足と同じではない。辺を整理するときは、何の証拠で前提が満たされたか、条件自体が不要になったかを確認し、後続の状態・再開条件との整合も見る。OR条件や外部条件を、内部AND辺へ無理に押し込まない。

記録を現行から履歴へ移すときは、[圧縮・アーカイブ手順](TASK_REGISTRY_ARCHIVE.md)を参照する。

同じ権限として扱わない。上位文書の変更統制は、下位taskの実行権限から自動的には導かれない。

正本を新規作成するときは、`Maintanance/Current/`へ配置する。ユーザーが別の配置先を明示した場合は、その指定に従う。

配置先の指定と正本として採用する権限は別である。既存文書の配置は、この規定によって変更しない。

### `Maintanance/User/`

`Maintanance/User/`は、ユーザーが作成、所有、または配置先として明示した文書の領域である。
AIは、自ら作成した成果物をこのfolderへ独自判断で新規作成、配置、または移動しない。既存文書の参照や、
ユーザーが対象と操作を明示して依頼した編集は、この配置禁止だけを理由には妨げない。taskの実行権限や
文書整理の委任は、このfolderをAI成果物の配置先として選ぶ権限を含まない。

### `AGENTS.md`

`AGENTS.md`はrepository内で最上位の統治文書であり、AIの編集対象外とする。下位文書、task、または
実装上の都合によって変更、迂回、失効、移動、改名、またはアーカイブしない。

### `Maintanance/Quality/CONCEPT_DEFINITION.md`

`Maintanance/Quality/CONCEPT_DEFINITION.md`は、ユーザーが定める製品目的の最上位正本であり、AIの編集対象外とする。
AIは品質要求、設計、評価、task、およびrelease判断の前提として参照できるが、内容を変更、補完、再解釈して
上書き、移動、改名、またはアーカイブしない。変更が必要な場合は、ユーザーだけが判断して反映する。

### Orientation文書

現行の参照先は`Maintanance/OrientationV5/`である。旧版と関連資料は`Maintanance/Archived/Orientation/`に保存し、現行の権限や指示として扱わない。

Orientation文書は、AIがrepositoryの目的、責任境界、および実務へ入るための上位正本群である。
ユーザーから委任された範囲では、AIも草案作成、レビュー、および内容編集へ参加できる。

ただし、次の操作はそれぞれ独立した境界として扱い、ユーザーの明示的な承認なしに実行しない。

- 新版または草案を現行正本として採用する。

新版候補の作成や内容上の完成は、採用、正本切替、または旧版のアーカイブを意味しない。必要な場合は、
完成候補の作成、採用判断、配置判断、および移動・参照切替の実行を別taskまたは別受入境界として扱う。

## ゲートの人間用資料とAI用キャッシュ

### 判断キャッシュ更新前の根拠固定

2026-10-18ユーザー指定。判断キャッシュの更新作業に着手する前に、更新対象の根拠となる正本・ユーザー判断・受入記録を必ずcommitして固定する。依頼する側は固定版のcommit SHAと対象資料を示し、更新する側はその版に基づくことを確認して、キャッシュまたは返却記録に参照SHAを残す。

無関係な未commit変更まで含める必要はない。固定版以後に対象の根拠が変わった場合は、その変更を黙って取り込まず、追加の根拠をcommitしてから更新する。commit操作には従来どおりユーザーの明示許可が必要で、本規則を自動commitの許可にしない。キャッシュ自体はGit管理外のままとする。

本規則は確定した判断を整理する更新作業に適用する。探索中の一時メモや循環を止める補助キャッシュの作成までcommit待ちにしない。それらを確定判断の更新として扱う際に、根拠を固定する。


2026-10-16ユーザー指定（CP-20261016-011、OPS-044で受入）：`Maintanance/Cache/`内は各担当直下の`README.md`を除きGit管理外とする。既存キャッシュも手元の内容を残して追跡から外す。通常のclone・pullでは他環境へ引き継がれないため、キャッシュ不在時は担当READMEと人間用ゲート・Registryから必要範囲だけ復元する。判断・契約・証拠・引継ぎに必須の情報をキャッシュだけに保存しない。キャッシュの強制追加や自動commitは行わない。

2026-10-16ユーザー決定。ゲートには人間用資料とAI用キャッシュ資料を対で置く。AI用ゲート・補助キャッシュの保存先は `Maintanance/Cache/<担当名>/` とする。現在のAstra用は `Maintanance/Cache/Astra/`。2026-10-16、CP-20261016-009の申請をOPS-044で照合し、Claude（姫）用を `Maintanance/Cache/Hime/` とする。担当別に分け、他担当のキャッシュを自分のものとして上書きしない。人間用資料は目的・到達点・判断事項・後続の概要を示す。AI用キャッシュは、その地点から仕事を続けるために必要な、現在有効なユーザー判断（行うこと・行わないこと）、制約・保留・作業状況を要約する。通常はキャッシュを起点とし、ゲート以前を遡って現在を再構築しない。

AI用は現在の作業負荷を軽減する自由領域とする。構成・粒度・記述を必要に応じて整理でき、固定テンプレートや人間用との逐語同期は求めない。後続の操作や判断変更により引継ぎ前提が変わったとき、必要な範囲を更新する。読むだけの更新や、全状態表の複製は不要。

ユーザーは自身の会話の進み方を「螺旋思考」と表現している。同じ話題へ戻っても、判断や理解が深まることがある。AI側で会話の追跡・前提の保持が難しくなったら、ユーザーの話し方を問題とせず、自分の負荷を短く伝え、何を整理したいかを示してキャッシュ使用の許可を願い出る。既に許可された担当領域・用途の利用は再許可を求めず進めてよい。未許可の範囲へ広げる場合に相談する。ユーザーの思考をAIが人物特性として診断する規則ではない。

2026-10-16追加のユーザー決定：同じ問い・資料・論点を巡回する探索に陥ったら、AIは都度の許可なしで補助キャッシュを追加してよい。保存先は `Maintanance/Cache/<担当名>/` とし、現在のAI用ゲートから参照できるようにして、問い、分かっていること、未解決点、確認済み範囲を必要な分だけ残す。この補助キャッシュに人間用資料の追加や新規採番は要求しない。 一時用途は `Maintanance/Cache/<担当名>/Temporary/` の作業別ディレクトリへ分け、作業終了・探索打切り時に必要情報を引継ぎ用キャッシュや正本へ移して片づける。記録・削除条件は[共通作業規則](COMMONS.md#aiの一時キャッシュを片づける)に従う。

探索前後でキャッシュの内容に実質的な変化がなければ、その探索を打ち切る。日時・言い換え・並べ替えだけを進展とみなさず、別キャッシュを作って同じ探索を続けない。未解決を解決済みにせず、停止理由と再開に必要な新しい情報・判断を短く残す。 循環に気づいたときは、AI自身が何を繰り返し、新しい情報が得られたか、どこで打ち切ったかをユーザーへ短く報告する。ユーザーの会話や思考を循環として評価する報告にはしない。独立して進められる依頼まで止める必要はない。新しい情報やユーザー指示で前提が変わった場合は、その変化に必要な範囲で再開できる。

キャッシュは判断・契約・権限の発生源ではなく、元の正本を置き換えない。操作直前のRegistry確認は維持する。矛盾・不足があれば必要な範囲の原文を確認し、確認結果をキャッシュへ戻す。要約からユーザー判断の条件・保留・適用範囲を落とさず、過去の指示を復活させない。

マイルストーン一覧から両資料へ辿れるようにし、恒久OPS-047で対の維持を扱う。既存ゲートは一括増築せず、作業対象になったときに適用する。最初の組は `Maintanance/MILESTONES.md` と `Maintanance/Cache/Astra/AI_GATE.md`。現在の作業範囲を引き継ぐ組であり、ゲート通過やリリース完了の認定ではない。

## 正本整理時の配置維持例外

配置維持の対象ファイルは、現行[Task Registry](TASK_REGISTRY_V2.md)の詳細正本欄で各パスに付けた「（配置維持; …）」を正本とする。本書へ同じファイル一覧を重ねて置かない。

この指定がある文書は、正本整理・folder分け・個別作業完了・task圧縮を理由に移動・改名・アーカイブしない。配置変更や指定の解除はユーザーの明示指示に従う。指定は対象文書を維持する恒久taskの行に置き、個別taskの完了で失わせない。

2026-10-16ユーザー決定：AIは理由を記録して「暫定保護」または「恒久希望」を付与できる。恒久希望は希望であり恒久判断ではない。恒久化の決定権はユーザーにあり、経過日数によって自動昇格・自動解除しない。両区分とも精査まで上記の配置保護を適用する。解除・移動はユーザーの明示指示による。

印はバッククォートで囲んだリポジトリ相対パスの直後に置き、拡張子を限定しない。各項目は「; 」で区切り、自由記述の「理由=」を最後に置く。理由中の括弧や「; 」はそのまま保持する。印の末尾は「）」とし、次のパスまでの間に別の括弧付き注記を続けない。

印には区分・付与日（YYYY-MM-DD、Asia/Tokyo）・記録者・理由を記す。既存指定は従来の効力を維持し、日付未確認なら「付与日=不明」と記録日を併記する。移記日を元の保護開始日と偽らない。新規付与の付与日は必須で、理由の編集や区分変更で付与日をリセットしない。解除後の再付与は旧記録を履歴へ残して新しい付与日を記す。

レジストリスタジオの「配置維持」タブはこの印から一覧を生成する。付与日当日を1日目として日本時間の暦日差で表示し、不明日は経過日も不明とする。一覧は写しであり別の管理正本にしない。今回以前の指定を勝手に暫定へ格下げしたり恒久へ昇格させない。

恒久taskへの所属や詳細正本欄のリンクだけでは、配置固定を意味しない。配置維持の印がない資料に保護を広げない。配置指定は内容の正本性・編集権限・受入状態を変更せず、文書内の履歴整理は各文書の権限と圧縮手順に従う。

AGENTS.md、CONCEPT_DEFINITION.md、Orientation、User領域などの独自の権限・配置制限は、上記「文書ランクと変更権限」に従う。Registryの指定がないことを制限解除と解釈しない。

整理前の一覧と理由は[OPS-053の保存原文](../Archived/PLACEMENT_EXCEPTIONS_BEFORE_OPS_053_2026-10-16.md)に残す。

## 履歴の照合とSQLite索引

Gitはcommitの履歴、MarkdownのRegistryと決定記録は現在の仕事・判断、SQLiteはGit履歴から再生成できる検索用索引を担う。2026-10-15、ユーザーの採用指示により抽出器と運用規則を採用し、repository内の索引を初回作成した。索引がない・古い・壊れた場合も、V2の利用や独立した製品作業を一律に停止しない。

生成物は`Maintanance/TaskHistoryIndex/`へ置き、SQLite本体と付随ファイルをGitの対象外にする。抽出器`Utilities/Maintenance/TaskHistoryIndex.py`と検索・更新手順は生成物から分けてGit管理する。V2のMarkdown一式もGit管理対象とする。

最初の索引は、commit・task ID・出現箇所（メッセージ、追加行、削除行）と元のファイルへの経路を保持する。どのref・commit範囲まで抽出したかも分かるようにする。索引の役割は、必要な履歴を絞って原文へ戻ることである。

番号の出現だけでtaskの実施・完了・担当・採用を確定しない。削除行の番号も過去の使用の手掛かりであり、番号解放ではない。出現しないことも未使用の証拠にはならない。未commitの採番や、取り消した採番があり得るため、索引から採番表の番号を引き下げない。

日常の採番はRegistry V3 DBの登録操作で行う。ここでいう履歴索引はRegistry V3 DBとは別物で、使用履歴の点検・復元やtaskと変更の照合に使う。履歴索引を現在の状態や採番の正本にしない。索引がない・古い・壊れた場合は、対象を絞ってGitと記録を直接照合する。全履歴の再調査を毎回の前提にしない。

索引の作成・差分更新・照合・再作成は、[メンテナンス手順](TASK_HISTORY_INDEX_MAINTENANCE.md)を必要時に参照する。通常起動時の通読対象には加えない。

## 停止・再開・担当交代時の占有

2026-10-19ユーザー整備依頼（OPS-145）。CLAUDE_TASK.md・WORKER_TASK.mdの「占有権と受渡し」を次で補う。実行状態と編集権限を分ける。専任役や第二の台帳は増やさず、明示委任された調整担当が受渡しの確定窓口を兼ねる。

- 依頼正本に依頼ID、担当を一意に区別できる名前または会話/agent識別子、編集対象ファイル・節、割当識別子、占有状態を残す。同名を区別できなければ同名の同時割当をしない。同一ファイルの編集は原則一人。節分担は範囲が重ならず他者の変更を失わない書込み方法を確認した場合だけとする。
- 停止要求中は解放しない。停止確認後も未返却範囲は「停止中・占有保持」。本人も他担当も停止を理由に編集を始めない。返却済み成果は固定されたままで、停止によって元担当へ占有が戻ることはない。
- 「速やかに停止」は新規作業に入らず、安全な最小区切りで止める。整合を保つため実行中操作を区切ることと、最低限の停止記録を許すが、仕上げ・検証・整理まで続けない。「即時停止」は中断可能な処理を中断し、保存・復元・検証・整理を追加しない。通知経路では次に受信して初めて停止できるため即時性を保証しない。停止ACKは可能な範囲で行う。指示が単に「停止」の場合は新規作業を止め、停止に必要な最小操作以外を増やさない。
- 停止範囲に含まれる常設作業も止める。全作業停止なら感想や圧縮も例外にしない。再開まで許すのは停止確認と状態通知に必要な最小記録。停止中・交代確定前は原文控えと再開に必要な一時作業物を消さない。交代後も通常の証拠保全・掃除条件に従い、自動削除しない。
- 交代時は停止確認の根拠、途中差分、未完操作、控えを確認し、必要なhash等で受渡し時点を固定する。旧割当の失効と新割当を一つの受渡し記録で確定する。未確認のまま同一対象へ新規編集を割り当てない。停止確認を得られない場合はユーザーへ返し、ユーザーの明示判断なしに交代しない。未確認のまま進める指示があっても停止確認済みとは記録しない。
- 再開時は最新の割当と停止後の差分を確認する。古い依頼だけで編集せず、他者変更や不一致があれば上書き・復元を止めて窓口へ返す。明示された復元依頼でも、対象が自分の最終書込と一致することをhash等で確認し、他者の変更を巻き戻さない。
- 強制停止した担当は、自分が確認できた停止操作の結果を代理記録できる。対象作業・担当識別子・停止要求ID・確認者・手段・時刻・成功/失敗/不明を区別し、本人の最終申告を改変しない。本人ACK、実行基盤での確認、要求だけの未確認を混同しない。送信後から受信までに進んだ操作は分かる範囲で残す。古い停止確認は別作業や正当に再開した作業へ適用しない。新しい作業中申告だけでは再開許可にならない。

これは文書運用の規則であり、自動ロック・強制停止・Studioの停止表示が実装済みという意味ではない。
