## 1. 位置づけ

本書は、`CONCEPT_DEFINITION.md`を上位概念として、
ISO/IEC 25010:2023を参照し、
swift-ac-collectionsの製品品質要求を定義する。

品質要求は、製品コンセプトの成立に必要な性質を表す。

具体的な達成水準、検証方法、受入条件、リリース工程は、
本書から派生する下位の定義と評価に委ねる。

既存品質資産との接続、VerificationとValidationの例、
不足仕様候補の詳細は、非規範的な
[`QUALITY_REQUIREMENTS_REFERENCE.md`](QUALITY_REQUIREMENTS_REFERENCE.md)に整理する。

## 2. 製品コンセプト

> CやC++標準に匹敵する性能をもつ、競技プログラミングで利用可能なデータ構造を、一般のSwift開発にも提供する。

### コンセプトの構成要素

- C1 — データ構造として正しく機能すること。
- C2 — C/C++標準に匹敵する性能を持つこと。
- C3 — 競技プログラミングで実用できること。
- C4 — 一般のSwift開発でも利用できること。

これらは独立した目標ではなく、同時に成立すべき製品価値である。

各構成要素の達成が、他の構成要素の成立を
不必要に損なわないことを基本とする。

特に、C2とC4には緊張関係がある。

C/C++級の性能を実現するために低レベルな実装を採用しても、
Swift利用者が期待する言語特性や安全性を
不必要に損なってはならない。

この両立が、本製品の品質設計における重要な課題となる。

### 1.0に向けた開発対象

1.0に向けた現時点の開発対象を次のように定める。

| モジュール | 位置づけ |
|---|---|
| RedBlackTreeCollections | 1.0提供対象として品質成立を目指す。 |
| PermutationModule | Swift 6.4以降の1.0提供対象として品質成立を目指す。 |
| OptionalArrayModule | 明示的なpackage traitで有効化する実験的データ構造として、留保付きで1.0の対象に残す。安定APIと同じ保証を既成事実とせず、実験提供に必要な品質境界を別途成立させる。 |
| BareArrayModule | 1.0提供対象から除外する。実装を放棄せず、source、仕様、test、benchmark、安全性、および既存利用への影響を保守する。 |

留保付きまたは提供対象外という位置づけは、有効化または保守する範囲の正確性、メモリ安全性、要素寿命、
初期化と破棄、およびbuild・test可能性を自動的に軽減しない。package traitも、性能上の未達や未検証を
解消済みとする根拠にはならない。

この位置づけは、各モジュールが1.0品質を達成済みであることを意味しない。品質アセスメントと
1.0品質ゲートによって、要求、証拠、反証、未検証領域、および残余リスクを確認する。

今後の開発または品質アセスメントで新しい問題、反証、前提の変化が見つかった場合は、現在の位置づけを
結論として固定せず、影響範囲を確認して再評価する。

### 1.0の提供環境（暫定）

1.0の提供対象は、Apple platforms 27以降およびLinuxの64-bit環境とする。32-bit環境は提供および
品質保証の対象外とする。

Apple platformsについては、`Package.swift`で対象platformごとの最低deployment versionを宣言し、
macOS以外も対象platform別のbuild・導入経路を確認する。platformsの宣言だけで、各platformにおける
実行時品質が確認済みであるとはみなさない。

代表品質評価環境は、macOS 27 / arm64およびUbuntu 24.04 LTS / x86_64とする。Ubuntuの評価は
GitHub-hosted runnerで行い、commit、workflow run、runner image、kernel、architecture、CPU、Swift、
依存解決、選択試験、完全log、および終了statusを実行ごとの証拠として残す。物理環境を固定できない
runner上の結果は、絶対性能またはC/C++との厳密な性能判定には用いない。

この提供環境と代表評価環境は現時点の方針であり、manifest実装、platform別build、品質アセスメント、
利用環境、および新しい反証を踏まえて1.0品質ゲートまでに再評価できる。

## 3. 上位品質要求

### QR-01 正確性 — データ構造として正しく振る舞う

各データ構造は、想定用途に必要な操作と状態遷移を備え、
公開契約に従って一貫した振る舞いを提供すること。

機能の過不足は、想定する利用目的に照らして判断する。

- コンセプト: C1、C3
- ISO 25010: 機能適合性

### QR-02 性能効率性 — C/C++標準に匹敵する性能を持つ

各データ構造は、対象操作と利用文脈において、
C/C++の標準的な実装に匹敵する性能を備えること。

計算量、実行時間、メモリ使用量、allocation、
入力規模に対する特性を含む。

性能の評価では、既存製品との相対的な回帰防止と、
C/C++標準との外部比較を区別する。

- コンセプト: C2、C3
- ISO 25010: 性能効率性

### QR-03 安全性 — 性能のためにSwiftの契約を損なわない

低レベルなストレージやポインタ操作を使用しても、
公開契約に含まれる値セマンティクス、
所有権、要素寿命、Indexの有効性などを維持すること。

利用環境や最適化構成によって保証範囲が異なる場合は、
その境界を明確にする。

性能最適化のために内部実装へ導入した危険を、
利用者へ不必要に転嫁しないこと。

- コンセプト: C1、C2、C4
- ISO 25010: 信頼性、セキュリティの関連側面
- 補足: メモリ安全性とISO 25010のSafetyは区別する。

### QR-04 理解可能性 — 利用者が契約を正しく理解できる

C++経験者とSwift開発者の双方が、
公開APIの意味、操作、制約、失敗条件を理解できること。

利用者が誤った期待を抱かず、
適切な操作を選択できること。

APIと利用者向け文書は、公開契約に整合していること。

- コンセプト: C3、C4
- ISO 25010: 相互作用能力

### QR-05 利用可能性 — 対象環境で導入し利用できる

競技プログラミング環境および一般のSwift開発環境で、
製品を導入し、他のコードと共存させ、利用できること。

対応するtoolchain、platform、build configuration、
公開APIの安定性と互換性の範囲を明確にする。

競技用途に固有の制約への対応が、
一般用途の利用可能性を不必要に損なわないこと。

同様に、一般用途への対応が、
競技用途で求められる性能や利用可能性を
不必要に損なわないこと。

- コンセプト: C3、C4
- ISO 25010: 互換性、柔軟性

### QR-06 持続可能性 — 製品価値を維持しながら変更できる

内部実装、公開API、toolchain、利用環境の変化に対して、
既存の機能、性能、安全性を意図せず失うことなく、
製品を変更・改善できること。

変更の影響を分析でき、
公開契約と品質特性への影響を評価できること。

品質上の問題や未確認事項を、
次の設計、実装、検証へ反映できること。

- コンセプト: C1〜C4の継続的な成立
- ISO 25010: 保守性、柔軟性

## 4. VerificationとValidation

### Verification — 要求を満たしているか

具体化された品質要求に対して、
製品が要求された性質を満たしているか検証する。

Test as Specificationを中心に、
必要に応じて独立した証拠を組み合わせる。

### Validation — 要求が目的に適しているか

品質要求の組み合わせによって、
製品コンセプトが実際に成立するか確認する。

特に、次の問いを重視する。

- 競技プログラミングで実際に利用できるか。
- C/C++標準に匹敵する性能が得られるか。
- 一般のSwift開発で無理なく導入・利用できるか。
- 性能、安全性、利用可能性が両立しているか。

Verificationの成功だけで、
Validationの成功を推定してはならない。

## 5. 品質アセスメントの原則

品質アセスメントは、品質要求への適合状況を
利用可能な証拠に基づいて評価する。

評価では次を区別する。

- 確認済み
- 未達
- 未検証
- 対象外
- 受容済みの残余リスク

証拠が不足している場合、
推測によって適合を主張してはならない。

品質アセスメント中に見つかった警告、失敗、矛盾、
未検証領域、および既存の主張に対する反証は、
解消する前に評価上の証拠として扱う。

評価対象、品質上の主張、前提、または証拠が変化した場合は、
影響範囲を確認するまで、従来の前提に基づく
適合判定や改善作業を継続してはならない。

問題を見えなくすることと、
問題の原因を解消することを区別する。

変更後に検証が成功したことだけを理由に、
変更前に得られた反証や未確認事項を失効させてはならない。

Test as Specification、CI、性能測定、
Sanitizer、設計上の根拠、独立レビューなどは、
それぞれ証明できる範囲が異なる。

AI同士の評価が一致したことを、
独立した証拠の代わりにしてはならない。

品質アセスメントでは、要求を満たしているかだけでなく、
要求そのものが不足または不適切である可能性も扱う。

## 6. 既存品質資産との関係

既存の品質資産は、品質要求そのものではなく、
品質要求を具体化し、その成立を検証・評価するために利用する。

### 品質要求と既存資産の対応

| 品質要求 | 主な既存資産 |
|---|---|
| QR-01 正確性 | Test as Specification、C++挙動比較 |
| QR-02 性能効率性 | Benchmark、性能回帰分析 |
| QR-03 安全性 | 値セマンティクス、寿命テスト、Death Test、Sanitizer、設計文書 |
| QR-04 理解可能性 | DocC、利用者向け文書、コードスニペット |
| QR-05 利用可能性 | Package構成、互換文書、利用者経路 |
| QR-06 持続可能性 | CI、品質評価、Git履歴、Release Checklist |

この対応表は非規範的な参照情報であり、
既存資産を調査・洗練する際の案内として利用する。

個別資産との接続や洗練の手がかりは、
[`QUALITY_REQUIREMENTS_REFERENCE.md`](QUALITY_REQUIREMENTS_REFERENCE.md)を参照する。

品質要求と既存資産の対応は一対一ではなく、
この表は網羅性や品質要求への適合を保証しない。

また、表への記載によって新たな検証義務や
受入条件を追加するものではない。

既存の検証手段が存在することを理由に、
品質要求を逆算して確定してはならない。

### モジュール品質プロファイル

上位品質要求を各モジュールへ適用する文書として、
次の品質プロファイルを置く。

| モジュール | 品質プロファイル |
|---|---|
| RedBlackTreeCollections | [`Quality-Profile.md`](../Sources/RedBlackTreeCollections/Documentation/Quality-Profile.md) |
| PermutationModule | [`Quality-Profile.md`](../Sources/PermutationModule/Documentation/Quality-Profile.md) |
| OptionalArrayModule | [`Quality-Profile.md`](../Sources/OptionalArrayModule/Documentation/Quality-Profile.md) |
| BareArrayModule | [`Quality-Profile.md`](../Sources/BareArrayModule/Documentation/Quality-Profile.md) |

各品質プロファイルは、上位品質要求を変更または複製せず、
対象モジュールにおける意味、重点領域、仕様、証拠、および
未確定領域への接続を定める。

この一覧は品質プロファイルの存在と接続先を示すものであり、
各モジュールの達成状態や適合を示すものではない。

## 7. 今後具体化する事項

以下は本書では確定しない。

- 品質要求間の優先順位とトレードオフ
- モジュール別の品質要求
- C/C++標準との比較対象と判定水準
- 競技用途を代表するValidation scenario
- 一般Swift開発を代表するValidation scenario
- 対応環境と公開契約の保証範囲
- 品質要求と検証証拠の対応範囲
- 残余リスクの許容条件

これらは独立した判断として具体化する。

未確定事項を、実装やテストによって
既成事実化してはならない。
