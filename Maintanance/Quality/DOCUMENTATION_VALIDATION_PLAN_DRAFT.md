# ドキュメントValidation計画 ドラフト

作成：2026-10-16 / Astra

利用者がREADMEとDocCを入口に、自分の用途に合うAPIを選び、必要な操作を実装し、保証と制約を理解できるかを確かめる計画案。文書が仕様と一致することに加え、その説明で利用目的を達成できるかを見る。

計画全体はレビュー待ち・未実施。2026-10-16のユーザー指示により、SPI登録後から1.0品質判断までの間に、公開ドキュメントの人間レビューゲートを置く方針を反映した。既存taskの開始・凍結解除は含まない。

計画レビューの到達記録は[文書マイルストーン](../Current/DOCUMENTATION_MILESTONES.md)で管理する。旧DOC-032はユーザー指示でマイルストーンへ移行した。レビュー完了や計画の受け入れを意味しない。

## 目的と評価対象

[品質要求](QUALITY_REQUIREMENTS.md)のQR-04（理解可能性）とQR-05（利用可能性）を中心に、QR-03（安全性）の境界を利用者が扱えるかを確かめる。仕様どおりの説明でも、用途選択や安全な利用につながらない場合は、説明の構成だけでなく要求・APIとの関係も課題にする。

対象は利用者向けREADME、生成済みDocC、公開APIコメント、およびそこから利用者が辿れる説明。内部の管理文書・設計経緯・Test as Specificationを読まなくても使えるかを評価する。日本語READMEから英語DocCへ進む導線も、言語を含めて観測する。

| 対象 | 利用者が判断・実行できるようにしたいこと |
| --- | --- |
| RedBlackTreeCollections | 重複とkey/valueの要否から4型を選ぶ。検索・挿入・削除を行い、Indexの有効範囲、連続削除、値の共有と変更の契約を説明できる |
| NextPermutationModule | 現在の並びからの列挙を選び、一時Viewの即時消費と結果の永続保存を使い分ける。旧名互換入口と推奨入口を区別できる |
| OptionalElementBufferModule | 実験提供と有効化条件を理解し、未計算状態を持つ多次元表を扱う。座標、nilへの復帰、再利用、所有・並行利用の境界を把握する |
| ElementBufferModule | 用途と言語バージョンに合わせてアクセス方式を選ぶ。Swift 6.2の競技供用とSwift 6.4の一般供用、package自体の必要toolchain・API availabilityを混同しない |

この表は試行の候補範囲であり、全API・全環境の網羅を開始条件にしない。各試行では一つの利用目的と対象版を固定する。

## Verificationとの分担

生成の成功、DocC診断、リンク解決、例のコンパイル・実行、Test as Specificationとの整合はVerificationとして利用する。これらが通っていても、利用者が必要な情報を発見し、適切な操作を選べるとは限らない。

Validationでは「文書の記述を説明できた」だけで終えず、利用目的を渡して、選択・実装・結果の解釈まで観測する。見つかった失敗は、文書、API・契約、実装、環境、課題設定のどこに原因があるかを後から切り分ける。

## 進め方の案

### 1 試行を準備する

対象commitと未コミット差分、READMEの言語、DocC生成対象・構成、Swift・OS、公開入口のURLを固定する。公開サイトとローカルプレビューの版が違う場合は混ぜない。プレビューは[文書整備の手引き](../DOCUMENT.md#astraによる自走プレビュー)で起動する。

一つの利用目的につき、参加者へ渡す短い依頼と、観測者だけが持つ判定根拠を別に用意する。依頼には用途・入力・必要な成果を示し、正解の型名、使うメソッド、注意すべき落とし穴を先に教えない。選択そのものを試す場合は、特定moduleのページから始めずREADMEから始める。

判定根拠は現行の品質要求・公開契約・Test as Specificationと照合して用意する。既存のValidation案にある旧名や過去の提供条件は、そのまま転用しない。

### 2 Astraが利用者の経路を試す

最初はElementBufferのSwift 6.4一般利用を一件試す案とする。プレビュー経路が確認できており、小さな利用目的で、導入・座標・借用・利用条件の説明を通して見られるためである。

課題例は「固定サイズの2次元作業表を用意し、各位置を更新して集計する。選んだ型と、その利用条件を説明する」。寸法は非対称にし、回答のコードはrepository外の小さなconsumerでコンパイラと実行結果に当てる。

AstraはREADMEから実際にページを辿り、参照した説明と作成したコードを残す。途中で内部知識を補った箇所は明記する。Astraは既に設計や文書を知っているため、この試行は文書の穴を探すための利用試行であり、初見の理解可能性の証拠にはしない。

一件の記録から課題文と記録方法を調整してから、他moduleへ広げる。赤黒木はまず4型の選択を横断して見て、型別の代表操作へ進み、最後に説明の違いによる混乱を横断確認する案とする。

### 3 公開ドキュメントの人間レビューゲート

SPI登録と対象版のDocC公開・導線確認が済んだ後、1.0品質判断までの間に実施する。対象APIと説明が落ち着き、指摘を修正する余裕が残る時点に置く。流れは、AIによる事前確認・修正・再確認 → SPI登録と公開導線確認 → 人間による一括確認 → 必要な修正 → 1.0判断への反映とする。

人間への依頼は原則一回にまとめる。AI側で導線、例の動作、説明の不足を事前に確認し、4モジュールの代表的な利用課題を短い一組へ整理する。人間に全APIの監査や内部資料の読解を求めず、初見で用途を選び、必要な情報へ辿り着き、重要な利用境界を理解できるかに絞る。

設計・本文作成に参加していないSwift利用者へ、実際の公開入口のURLと短い利用課題を渡す。SPIのpackageページからREADME・DocCへ辿る経路を含め、渡すURLと表示される対象版をAIが事前確認する。ローカルプレビューや内部草稿を公開導線の代わりにしない。C++経験とSwift経験、資料の言語、事前知識を記録する。参加者の選定と外部接触はユーザーが行う。

ゲートでは、観測結果、修正後の確認、未解決事項を揃えて1.0判断へ渡す。未実施や未解決の重要な誤解を、AIの評価だけで通過済みにしない。残余リスクの受け入れはユーザー判断に返す。

フレッシュなAIを使う試行も可能だが、人間の理解確認とは別に記録する。AIへは設計資料・過去の回答・判定根拠を渡さず、公開文書で得た情報と推測を分けさせる。AI間の一致や試行回数だけで一般利用者の理解を確認済みとしない。

観測中に正解へ誘導しない。質問や詰まりを記録し、補助が必要なら最初の回答を保存してから説明する。「助言後に完了」を「自力で完了」に書き換えない。

### 4 課題を返し 必要な範囲を再確認する

観測を固定してから、文書修正、契約・APIの判断、環境の説明、課題文の修正へ分ける。本文を直して通った場合も、元の誤解とその根拠を残す。

修正後はまずAIが影響範囲を再確認する。人間への再依頼は、初見の理解に関わる重大な問題など、AIの再確認では閉じられない部分に限定する。原則一回は負担を減らす方針であり、一回で必ず合格させる条件ではない。

同じ参加者の再試行は修正後に使えることの確認にはなるが、初見の分かりやすさは学習の影響を受ける。初見への効果を主張する場合は別の参加者による確認と区別する。修正に関係する操作だけを再検証し、全体を毎回やり直さない。

## 記録と判定

試行ごとに以下を残す。所要時間や質問数は摩擦を見つける材料とし、根拠のない合格点にはしない。

| 記録 | 内容 |
| --- | --- |
| 条件 | 対象版・差分、環境、参加者の区分と事前知識、言語、提示物、課題 |
| 経路 | 開いたページ、探した情報、読み戻し、利用者自身の選択理由 |
| 成果 | 最初の回答・コード、compile/run結果、予想と実際の違い |
| 補助 | 質問、追加説明、内部知識による補完と、その前後の回答 |
| 結果 | 自力で完了／補助後に完了／誤解または未完了／環境等により判定不能／未実施 |
| 課題 | 具体的な箇所、利用への影響、原因候補、必要な修正・判断・再確認 |

一回の試行は、対象用途について適切に選び、操作を完了し、重要な利用境界を誤認していないかで判定する。動くコードだけ、説明だけの成功で両方を確認済みにしない。提供条件の誤認、寿命・所有・並行利用に関する危険な誤解は、解消または権限ある持ち主による残余リスク判断まで未解決として残す。

計画の一巡は、選んだ対象について観測結果、残る課題、未実施範囲、必要な次の判断を整理した時点で閉じる。全員の合意や全APIの網羅を完了条件にしない。公開可否・1.0品質の受け入れは、この結果を入力とする別の判断である。
