# Refactoring from `release/AtCoder/2025`

## この記録の目的

この文書は、`release/AtCoder/2025`から現行実装への変化が、単調な整理や一括置換では
なかったことを示す。

移行では、部分的な破損や不完全な仮設を許容しながら、実行・比較・検査が可能な状態を残した。
動作から得られる観測を使って次の修正を選び、再び動かして確かめることで改善ループを回した。
その過程でIndexを整数からポインタへ変更し、Nodeの同一性、Storageの所有構造、`ManagedBuffer`の
役割、Copy on Writeの成立条件を段階的に組み替えた。

ここで動作している中間状態は、完成品として使い続けるためのものではない。破損範囲、成立している
責務、次に変更できる境界を観測するための実験装置である。目的はこの過程を成功談として誇張する
ことではなく、観測可能性を失わずに仮設、試行、撤去、復旧を繰り返したリファクタリングの実在を、
第三者がGit履歴と保存されたテストから確認できる形で示すことである。

コミット、旧新パス、中間形、短命な試行、未確定事項は、事実・証拠の正本である
[別紙](EVIDENCE.md)に置く。本紙は、その証拠から成立する説明の
正本とする。

## 作業主体と支援範囲

この文書が扱う赤黒木本体は、人間が手で育てたコードであり、Index、Node、Storage、
`ManagedBuffer`、CoWを組み替えた構造リファクタリングも手動で行われた。IDEの
リファクタリング機能を利用したのは名前変更に限られ、それ以外の構造変更は手作業で
編集された。

AIによる支援自体は以前からあり、技術的な問い合わせ、アセンブリの読解、テストコードの
作成などに利用していた。しかし、赤黒木本体の構造リファクタリングをCoding Agentへ
委任したことはない。2026年秋以降にCoding Agentへ依頼したリファクタリングは、主として
テストコードの再編・再建であり、文書整備、局所的なバグ修正、検証、履歴調査も後続の
収束作業として行われた。

このテストコードのリファクタリングを任せ始めた当初は、5時間の利用枠を約30分で
使い切る状況だった。その後、読む正本、責任境界、開始条件、判断の分担を`AGENTS.md`などで
整理し、同じ利用枠で約2時間の作業を継続できるところまで運用を改善した。この経緯は、
赤黒木本体の構造変更をAIが実行したことを示すものではなく、既に存在した実装のテストと
証拠を後から再建・整理する協働が成立していった過程を示す。

## 動く仮設から完成形を発見する

![旧Treeを稼働させたままIndex、Node、Storage、CoWを別々の速度で移管した構造](Images/unsafe-tree-live-migration.png)

整数Indexだけをポインタへ置換することはできなかった。ポインタはNodeの固定アドレスを要求する一方、
従来の連続StorageとCoW copyはNodeを移動する。そこで完成形を一度に実装せず、まず動く仮設として
ポインタIndexと`UnsafeNode`を並設した。その実行結果を手掛かりにStorageを専用Bufferとraw bucketへ
移し、Nodeの同一性とIndexの寿命を後から安全柵へ分離した。

改善は次の一方向の工程ではなく、動作と観測を挟んだ反復として進んだ。

```text
動く仮設を置く
      ↓
実行・比較・検査から手掛かりを得る
      ↓
破損範囲と成立条件を分離する
      ↓
責務を一段だけ移す
      ↓
不要になった仮設を撤去する
      ↺
```

この反復は、ポインタと`node_id`からtag・世代・seal・tieへの分解、旧Headerを再利用した
`ManagedBufferPointer`から専用Buffer・raw bucketへの移行、refCountとstrong uniquenessの試行と
撤去に現れている。検証網も完成形のまま固定せず、公開挙動のテストを観測の足場として残しながら、
内部`Fixture`と`Keystone test`を変更、一時無効化、再接続した。

## 一枚で見る移行

![Unsafe系統の移行史](Images/unsafe-lineage-timeline.png)

全体は単純な`UnsafeTree`から`UnsafeTreeV2`への名前変更ではない。旧実装を残した並行導入、
Node・Index・Iterator・Storageの責務分解、Deprecatedへの隔離、製品ソースからテスト資料への
移管が異なる時期に進んだ。

そのため、名前の連続と責務の連続は分けて読む必要がある。同じ名前でも実装が差し替わることが
あり、名前が消えても責務が別の型や層へ残ることがある。

## 内部構造の交換

![UnsafeTree内部構造の変化](Images/unsafe-tree-internal-evolution.png)

内部構造の中心には、相互に依存する四つの変化がある。

1. **Index:** Node番号を持つ整数Indexから、Nodeを直接指すポインタIndexへ移った。
2. **Node:** 連続領域内の整数リンクから、左右親を実ポインタで結ぶ生メモリNodeへ移った。
3. **Storage:** `ManagedBuffer<Header, Node>`の一体構造から、Headerがraw bucket群を管理する
   `ManagedBufferPointer<Header, Void>`中心の所有構造へ移った。
4. **CoW:** 全Nodeの再配置を伴うcopyから、bucketをin-placeで拡張しつつ、共有時には
   tracking tagから新しいポインタ関係を再構築する方式へ移った。

ポインタIndexによってNodeへ直接到達できる一方、NodeのアドレスとStorageの寿命が契約へ露出した。
bucket化は一意なStorageの容量追加で既存Nodeを動かさない構造を成立させたが、CoWでは別Storageへ
Nodeを再構築するためポインタが変わる。ここで避けるべき危険は、解放または再利用されたNodeを
古いIndexが有効な参照先だと誤認することである。その検査責務が、`node_id`、tracking tag、
recycle count、sealed pointer、tied storageへ段階的に外在化した。

これは一直線の設計ではない。途中では明示的な参照countやstrong uniquenessも試され、撤去された。
現行方式は、すべてを強く拘束するのではなく、Storageの一意性、Nodeの世代、Indexの寿命を
それぞれの境界で扱う構造へ収束している。

## 変化とテストの緊張関係

移行の要石として保存されているテストは次である。

`Tests/RedBlackTreeTests/UnsafeTreeV2/Instance/___RedBlackTreeContainerTests_unsafe.swift`

このテストはAtCoder 2025版の原本そのものではなく、旧コンテナを直接操作する`Fixture`テストから
移行中に分岐し、新しい内部構造へ追従した派生・再構成版である。固定したNode配置を使い、木の
不変条件、回転、探索、挿入、削除時の`begin`更新を公開APIより下の層で検証した。

このテストは常に実行され続けた守護テストではない。最初のunsafe版は`#if false`で追加され、
新構造へ追従した版は一時期実行対象になったが、`Fixture`とテストターゲットの再編後、現在は再び
`#if false`でコンパイル対象外になっている。それでも削除されず、「木の開発のブートストラップに
該当する部分」として保存されている。

Test as Specification自体はこの移行で新しく生まれたものではない。AtCoder 2025版より前からある
公開挙動のテストを足場にした一方、内部表現へ強く結合したテストは、構造変更に合わせて条件、期待値、
`Fixture`を変更し、一部を無効化・削除・保存した。旧テストをすべて通すことを移行条件にはしなかった。

ここでテストは、変更を一方向に拘束する絶対的な仕様ではない。旧実装の詳細を固定する期待は緩める
必要があり、緩めすぎれば同じ木としての不変条件まで失う。その間で`Keystone test`は、保証全体を
維持する壁ではなく、木の形、回転、探索、挿入、削除という同一性を次の検証系へ渡す支点として働いた。

したがって、この履歴から「すべてのテストが常に成功した」「無欠陥だった」とは主張できない。変更が
旧テストの正当性を問い、残したテストが変更の正当性を問い、薄くなった保証を新しい`Fixture`、
内部テスト、番号付きTest as Specificationへ再配置した。ここで確認できるのは、保証の縮退を
観測可能に保ち、その再建先を追跡・制御したことである。

## 互換境界の移動

`COMPATIBLE_ATCODER_2025`も、最初から完成した互換層だったわけではない。2025年10月には
package全体で既定有効な条件として導入され、通常実装の中で型、戻り値、APIの新旧を切り替えた。
新しい内部構造を開発しながらAtCoder 2025時点の外形を動かすため、互換性を製品コードの内側に
抱えた段階である。

内部構造の収束に伴い、旧APIや旧iteratorはDeprecated層と互換条件へ移された。2026年9月末から
10月初めにはdefineの有効・無効を短期間に切り替えながら両構成を調整し、最終的に通常構成を既定へ
戻した。互換性は日常の実装を規定する中心から、必要なときだけ選ぶ境界へ後退した。対応するテストも、
通常版と同じ期待値を共有するのではなく、互換専用の`Fixture`、比較テスト、スキップを含む別の保証面として
整理された。

2026年10月には同じ境界がPermutationにも使われた。ここでは旧APIを現行sourceへ混ぜ直さず、
AtCoder 2025版のsourceを専用directoryへ隔離し、通常版と異なる列挙・CoW・unsafe aliasingを専用の
Test as Specificationで固定した。公開Package traitとして一度試した構成はDocCとの衝突により撤回し、
通常リリースは通常版だけ、互換構成は`prepare/compatible/2`という専用ブランチで検証する形へ移った。

この変化は、互換性を守るほど通常設計が拘束され、分離するほど旧利用者への再現性が失われるという
別の緊張を示す。解決は互換性の全面維持でも全面削除でもなく、通常製品、条件コンパイル、Deprecated、
専用テスト、専用ブランチ、単一ファイル生成へ責任を分け、旧挙動が必要な地点まで境界を移動することだった。

## 外形も同時に組み替えた

内部構造だけでなく、ソース配置とモジュール境界も段階的に変わった。

- 内部層を`Implements/`へ集約した。
- 本体ディレクトリを`RedBlackTreeModule`から`RedBlackTreeCollections`へ移した。
- packageのターゲット名とテストの`@testable import`を同じ移行で切り替えた。
- 旧`RedBlackTreeModule`名には、`@_exported import RedBlackTreeCollections`だけを持つ
  互換ターゲットを残した。

このため、現行の「本体は`RedBlackTreeCollections`、旧名は薄い互換層」という構成も、
一括の名前変更ではなく、実装、物理配置、ターゲット名、互換入口を分けた移行の結果である。

## この履歴が示す方法

履歴から読み取れる方法は次のとおりである。

1. 完成度より観測可能性を優先し、部分的でも実行・比較・検査できる仮設を置く。
2. 動作結果から破損範囲と成立条件を分け、次に移せる責務を選ぶ。
3. Node、ポインタ操作、メモリ確保、Index寿命、CoWを一段ずつ別の境界へ移す。
4. 過剰な拘束や役割を終えた仮設は、動作確認後に撤去する。
5. 旧実装の詳細を固定する保証は緩めつつ、赤黒木の不変条件を観測軸として残す。
6. 新しい内部構造に対応する`Fixture`と仕様テストを段階的に再建する。
7. 旧契約を通常実装から条件コンパイル、Deprecated、専用ブランチへ段階的に外在化する。
8. 現行テストスイートで維持するコストが役割を上回る`Keystone test`は、コンパイル対象外の
   一次資料として保存する。

この方法は、差分を小さくするという意味で単調だったのではない。動く仮設を観測装置として使い、
仮説が外れれば一部を撤去して別案を試した。動作を維持したことで観測可能性が残り、観測可能性が
改善ループを成立させ、最終的に開始時とは異なる所有・同一性モデルへ到達した。

ここで行われたのは、名前変更やファイル整理を中心とする表層的なリファクタリングではない。
稼働状態と検証可能性を残しながら、データ構造の所有・同一性モデルを交換する作業である。
整数Index、移動するNode、`ManagedBuffer`、CoWが相互に拘束する状態から、固定アドレスを持つ
Node、raw bucketを管理するStorage、世代と寿命を検査するIndexへ移るため、各責務を異なる
速度で切り離し、再接続した。

## 拡張から収束へ

AtCoder 2025版からの移行では、内部層、公開4型、View、互換層、検証手段を広く用意する必要が
あった。現在は新しい構造を増やす段階から、既存の核を外部化された証拠で磨く段階へ移っている。

次の三点は、この文書が達成済みだと主張する評価結果ではない。今後、第三者が再実行可能な証拠を
揃え、それぞれを判断できる状態にするための評価軸である。

1. **正しさ:** C++標準コンテナとの決定論的な挙動比較と回帰テスト
2. **Swiftとしての価値:** CoW、値セマンティクス、Index寿命、Range/Viewを含む仕様テスト
3. **選択理由:** 外部候補との公平な比較と、未計測・不利な結果を含む限界の明示

実行可能な証拠を要石にして次の層へ進む点で、この収束フェーズもAtCoder 2025版から続く
リファクタリング方法の延長上にある。
