## 原案との接続で判断したこと

### 一般原理に統合した部分

- 「合意は証拠ではない」は独立した禁止規則を重ねず、「問いに答えられるものへ先に当たる」と「証拠の範囲で確定する」へまとめた。文書間の整合も、決定の正しさを保証しないと明記した。
- 「知識と事実の両方を使う」は、調べる対象や解釈に知識を使い、事実から前提を修正する行動として書いた。事実を集めるだけで終わらない点も残した。
- 目標への寄与、純粋な計算と副作用、意味の等しい代替は、需要・効果・仕事の選び方につないだ。比喩の理解を、運用の前提にはしていない。
- 原案の、全体を見ること、依存する未確認事項を明示すること、必要な検証を早く回すこと、証拠の範囲で報告することは保持した。
- 成果の受入と変更権限の返還は分けた。報告や受入だけで権限が消える規則にはせず、「引渡しと変更権限の返還が済んだ後」という原案の条件を残した。

### レビュー後に明確にした部分

Claudeのレビューを踏まえたユーザーの修正依頼により、「役割と権限」に次の二点を追加した。

- 成果物を受け取ることや管理を担当することだけでは、変更権限を得ない。外から持ち込まれたものも含め、変更は現在の依頼で任された範囲に限る。
- 役割表を読むことは、その担当への任命ではない。自分の担当は現在の依頼と明示された割当から確かめる。

いずれも、権限を推測しないという原案の原理を、誤解が生じやすい場面で明確にしたもの。すでに任された範囲に、新たな承認手続きを追加する変更ではない。

### 今回の制度を優先して残した部分

1. **操作直前の許可。** 共通原案の「同じ許可を繰り返し求めない」には、今回のGit操作の制度を例外として明記した。既存の委任がbranch作成・commit・pushまで自動的に及ぶとは書いていない。
2. **介入後の再開。** 前回の別プロジェクト用V2と異なり、今回の資料には明示的な再委任があるまで再開しない条件がある。影響する仕事について、この条件を残した。一般の不明点への確認待ちと、委任が中断された場合は区別した。
3. **最初からRegistryを使う。** 今回は「一つの依頼記録から管理を育てる」という前回の制度へ置き換えていない。バックアップで明示された具体的な制度として、Registryと固定IDを取り込んだ。
4. **Xcodeの条件。** 前回の「返却経路がない場合」という条件付き表現へ緩めず、今回の資料にあるXcodeでの内部委任禁止とファイル経由の受渡しを残した。

### 資料内で解釈が分かれうる部分

**「ルーティーン」の実行依頼と、操作直前の許可の関係。** 資料には、ルーティーンの中でcommitする指示と、commitごとに直前の明示的な許可を必要とする指示がある。ルーティーンという一語で複数回のcommitを包括許可するかは明記されていない。

今回の候補では、操作の個別許可を例外なく書いている節を優先し、ルーティーンのcommitにもその条件を適用した。これは曖昧な接続を整理した編集判断であり、新しく確定したユーザーの意思ではない。ルーティーンに含むcommitを一括で任せたい場合は、この一点を明示的に変える必要がある。

## 持ち込まなかったもの

- 前回の別プロジェクト用V2にあるWorker／Receiverの役割体系、役割別bootstrap、一仕事一依頼記録から管理を育てる制度、経験者への相談経路は、今回の入力にないため持ち込まなかった。
- 前回の`Maintanance/User/`専用領域の規定も、今回の入力にはないため、この候補へ推測で追加していない。これは既存の領域保護を解除する判断ではない。
- ユーザーの自己表現「人には優しいけれど、問題に対しては容赦がない。」は、資料が明記するとおり行動規則にはしない。このメモに表現を保持し、候補本文の指示には変換しなかった。
- 過去の管理体系や役職を、今回の入力の外から補わなかった。Registry等を残した根拠は今回渡された資料であり、過去から自動的に継承したものではない。
