# swift-ac-collections Quality Requirements — V3 Draft

## 1. 位置づけ

本書は、`CONCEPT_DEFINITION.md`を上位概念として、
ISO/IEC 25010:2023を参照し、
swift-ac-collectionsの製品品質要求を定義する。

品質要求は、製品コンセプトの成立に必要な性質を表す。

具体的な達成水準、検証方法、受入条件、リリース工程は、
本書から派生する下位の定義と評価に委ねる。

## 2. 製品コンセプト

> CやC++標準に匹敵する性能をもつ、競技プログラミングで利用可能なデータ構造を、一般のSwift開発にも提供する。

### コンセプトの構成要素

- C1 — データ構造として正しく機能すること。
- C2 — C/C++標準に匹敵する性能を持つこと。
- C3 — 競技プログラミングで実用できること。
- C4 — 一般のSwift開発でも利用できること。

これらは独立した目標ではなく、同時に成立すべき製品価値である。

各構成要素の達成が、他の構成要素の成立を
不必要に損なわないことを基本とする。

特に、C2とC4には緊張関係がある。

C/C++級の性能を実現するために低レベルな実装を採用しても、
Swift利用者が期待する言語特性や安全性を
不必要に損なってはならない。

この両立が、本製品の品質設計における重要な課題となる。

## 3. 上位品質要求

### QR-01 正確性 — データ構造として正しく振る舞う

各データ構造は、想定用途に必要な操作と状態遷移を備え、
公開契約に従って一貫した振る舞いを提供すること。

機能の過不足は、想定する利用目的に照らして判断する。

- コンセプト: C1、C3
- ISO 25010: 機能適合性

### QR-02 性能効率性 — C/C++標準に匹敵する性能を持つ

各データ構造は、対象操作と利用文脈において、
C/C++の標準的な実装に匹敵する性能を備えること。

計算量、実行時間、メモリ使用量、allocation、
入力規模に対する特性を含む。

性能の評価では、既存製品との相対的な回帰防止と、
C/C++標準との外部比較を区別する。

- コンセプト: C2、C3
- ISO 25010: 性能効率性

### QR-03 安全性 — 性能のためにSwiftの契約を損なわない

低レベルなストレージやポインタ操作を使用しても、
公開契約に含まれる値セマンティクス、
所有権、要素寿命、Indexの有効性などを維持すること。

利用環境や最適化構成によって保証範囲が異なる場合は、
その境界を明確にする。

性能最適化のために内部実装へ導入した危険を、
利用者へ不必要に転嫁しないこと。

- コンセプト: C1、C2、C4
- ISO 25010: 信頼性、セキュリティの関連側面
- 補足: メモリ安全性とISO 25010のSafetyは区別する。

### QR-04 理解可能性 — 利用者が契約を正しく理解できる

C++経験者とSwift開発者の双方が、
公開APIの意味、操作、制約、失敗条件を理解できること。

利用者が誤った期待を抱かず、
適切な操作を選択できること。

APIと利用者向け文書は、公開契約に整合していること。

- コンセプト: C3、C4
- ISO 25010: 相互作用能力

### QR-05 利用可能性 — 対象環境で導入し利用できる

競技プログラミング環境および一般のSwift開発環境で、
製品を導入し、他のコードと共存させ、利用できること。

対応するtoolchain、platform、build configuration、
公開APIの安定性と互換性の範囲を明確にする。

競技用途に固有の制約への対応が、
一般用途の利用可能性を不必要に損なわないこと。

同様に、一般用途への対応が、
競技用途で求められる性能や利用可能性を
不必要に損なわないこと。

- コンセプト: C3、C4
- ISO 25010: 互換性、柔軟性

### QR-06 持続可能性 — 製品価値を維持しながら変更できる

内部実装、公開API、toolchain、利用環境の変化に対して、
既存の機能、性能、安全性を意図せず失うことなく、
製品を変更・改善できること。

変更の影響を分析でき、
公開契約と品質特性への影響を評価できること。

品質上の問題や未確認事項を、
次の設計、実装、検証へ反映できること。

- コンセプト: C1〜C4の継続的な成立
- ISO 25010: 保守性、柔軟性

## 4. VerificationとValidation

### Verification — 要求を満たしているか

具体化された品質要求に対して、
製品が要求された性質を満たしているか検証する。

Test as Specificationを中心に、
必要に応じて独立した証拠を組み合わせる。

### Validation — 要求が目的に適しているか

品質要求の組み合わせによって、
製品コンセプトが実際に成立するか確認する。

特に、次の問いを重視する。

- 競技プログラミングで実際に利用できるか。
- C/C++標準に匹敵する性能が得られるか。
- 一般のSwift開発で無理なく導入・利用できるか。
- 性能、安全性、利用可能性が両立しているか。

Verificationの成功だけで、
Validationの成功を推定してはならない。

## 5. 品質アセスメントの原則

品質アセスメントは、品質要求への適合状況を
利用可能な証拠に基づいて評価する。

評価では次を区別する。

- 確認済み
- 未達
- 未検証
- 対象外
- 受容済みの残余リスク

証拠が不足している場合、
推測によって適合を主張してはならない。

Test as Specification、CI、性能測定、
Sanitizer、設計上の根拠、独立レビューなどは、
それぞれ証明できる範囲が異なる。

AI同士の評価が一致したことを、
独立した証拠の代わりにしてはならない。

品質アセスメントでは、要求を満たしているかだけでなく、
要求そのものが不足または不適切である可能性も扱う。

## 6. 既存品質資産との関係

既存の品質資産は、品質要求そのものではなく、
品質要求を具体化し、その成立を検証・評価するために利用する。

- Test as Specification: 観察可能な契約と実行可能な検証
- Design Documentation: 設計意図、構造、不変条件
- Benchmark: 性能特性と比較証拠
- CI: 指定構成における継続的な検証
- Quality Assessment: 品質要求の達成状況
- Git History: 変更と判断の履歴
- Release Checklist: 公開前の適合確認

既存の検証手段が存在することを理由に、
品質要求を逆算して確定してはならない。

## 7. 今後具体化する事項

以下は本書では確定しない。

- 品質要求間の優先順位とトレードオフ
- モジュール別の品質要求
- C/C++標準との比較対象と判定水準
- 競技用途を代表するValidation scenario
- 一般Swift開発を代表するValidation scenario
- 対応環境と公開契約の保証範囲
- 品質要求と検証証拠の対応範囲
- 残余リスクの許容条件

これらは独立した判断として具体化する。

未確定事項を、実装やテストによって
既成事実化してはならない。
