# swift-ac-collections 製品品質要求ドラフト — Codex V2

作成日: 2026-10-10

## 位置づけと独立性

この文書は、製品コンセプトから製品全体に共通する上位品質要求を導き、既存の品質資産との接続と、今後の
洗練に使える手がかりを示す。具体的な達成水準、CI構成、release停止条件、工程は後続で定める。

Codexは再作成指示より前にChappy版を読んでいるため、完全なblind独立案ではない。この制約を明示したうえで、
Chappy版の分類を転記せず、コンセプトの三つの主張とrepositoryで観測した既存資産から再構成する。

## コンセプトから導く品質の軸

製品コンセプトは、次の三つを同時に成立させることを求める。

1. **性能上の競争力:** CやC++標準に匹敵する性能を持つ。
2. **競技用途での実用性:** 制約の厳しい競技プログラミングで、問題解決の道具として使える。
3. **一般Swift開発への移植性:** 競技用途で得た性能を、一般のSwift利用者も扱える製品として提供する。

したがって品質は、速さ、正しさ、使いやすさを別々に最大化することではない。低水準な性能設計を、Swiftの
値semantics、公開契約、導入可能性と両立させ、異なる利用文脈へ同じ製品価値として届ける能力である。

## 上位品質要求

### Q-01 意図したデータ構造として振る舞うこと

各データ構造は、対象とする抽象データ型の操作、状態遷移、境界条件、計算量上の性質を備え、公開契約に従って
一貫して振る舞うこと。機能の多さではなく、競技用途と一般用途で必要な問題解決能力に照らして過不足を判断する。

既存資産との接続:

- Test as Specificationが、公開APIの振る舞い、境界、値semanticsを実行可能な契約として保持している。
- C++挙動比較、互換性matrix、公開surface testが、外部概念との対応を記録している。

洗練の手がかり:

- moduleごとに「どの利用目的を満たすための操作か」をTest as Specificationと対応させる。
- test件数ではなく、公開契約と未検証領域の対応関係を見えるようにする。

### Q-02 規模と用途に見合う性能効率を持つこと

実行時間、memory使用量、allocation、規模への伸び方が、対象操作と利用文脈に対して競争力を持つこと。
「匹敵」は単一の倍率ではなく、比較対象、操作、入力分布、規模、toolchainを明示して評価できる性質であること。

既存資産との接続:

- C++標準libraryとのbenchmark、規模別chart、release間performance comparisonが実測証拠を持つ。
- 計算量コメント、特殊化・witness table・memory layoutの調査記録が原因説明を支える。

洗練の手がかり:

- コンセプト上の性能主張と、現在比較できている型・操作・規模の範囲を分けて示す。
- 回帰検知、競合比較、性能原因分析を別の証拠経路として整理する。

### Q-03 Swiftの値と所有の規範を保つこと

性能のために低水準なstorageやpointerを使っても、利用者が期待する値semantics、copyの独立性、要素寿命、
CollectionのIndex契約、Sendableなどの性質を、明示した範囲で保つこと。保証できない領域は暗黙に安全と見せない。

既存資産との接続:

- copy-on-write、iterator copy、reference lifetime、View、Index validity、Death Testが具体的な契約を固定している。
- strict memory safety評価、runtime-check方針、`-Ounchecked`検討が保証境界を記録している。

洗練の手がかり:

- memory safety、値semantics、利用者の事前条件、ISO的なSafetyを同一語でまとめず、それぞれの責任範囲を結ぶ。
- compiler最適化や構成差で壊れ得る性質を、通常の機能testとは別の品質リスクとして扱う。

### Q-04 利用者が契約と制約を理解できること

利用者が、何ができるか、どの計算量か、どの操作が契約違反か、所有・寿命・互換性にどんな制約があるかを、
公開APIと文書から理解できること。APIの簡潔さだけでなく、誤った期待を作らない説明可能性を持つこと。

既存資産との接続:

- DocCコメント、利用者向けMarkdown、コードスニペット調査、API matrixが理解可能性を支える。
- Test as Specificationが文書表現の根拠となり、文書が実装だけから推測されることを防ぐ。

洗練の手がかり:

- Test as Specification、公開コメント、利用者向け文書の間で同じ契約を追跡できるようにする。
- DocCが生成できることと、説明やコード例が利用者にとって正しいことを分けて評価する。

### Q-05 利用環境へ導入し、他のSwiftコードと共存できること

対象とするSwift toolchain、platform、build configurationから導入でき、一般のSwift packageやアプリケーションへ
不必要な制約、symbol、警告、互換modeを持ち込まないこと。競技用途の特殊条件と一般用途の既定値を分離できること。

既存資産との接続:

- SwiftPM manifest、umbrella product、trait、対応branch、CI構成が利用環境との境界を形成している。
- 互換コードの分離とrelease treeの掃除が、用途別の構成を混在させない設計として機能している。

洗練の手がかり:

- 「buildできた環境」と「製品が対応を約束する環境」を区別する。
- 競技用互換性、実験的trait、通常版の公開面を、利用者が選択可能な構成として整理する。

### Q-06 変更しながら品質の由来を保てること

内部実装、compiler、Swift version、公開API、利用文脈が変わっても、どの契約と性能特性が影響を受けるかを判断し、
既存価値を意図せず失わずに変更できること。失敗や未確認事項を次の設計・test・文書へ戻せること。

既存資産との接続:

- Test as Specification、performance履歴、品質評価、設計文書、Git履歴が変更前後の比較基準を持つ。
- task Registry、release記録、事故後の停止原則が、判断と証拠を時間やagentの間で継承する。

洗練の手がかり:

- 管理資料の量ではなく、要求から契約、test、証拠、判断へ辿れることを保守性として評価する。
- 古い証拠を残すことと、現行の正本を明確にすることを両立させる。

### Q-07 品質の限界と不確実性を表明できること

未検証のplatform、測定noise、未確定の公開契約、compiler依存の挙動、性能比較の不足を、適合済みの品質と混同せず
表明できること。品質は全項目が緑であることだけでなく、何をまだ保証できないかが判断可能であることを含む。

既存資産との接続:

- `UNVERIFIED`、risk、判断候補、残余riskの記録方式が、不確実性を成果から切り離さず保持している。
- CI artifact、benchmark環境、独立reviewが、単一の結果を過大評価しない材料になる。

洗練の手がかり:

- module別品質評価で、未達、未検証、対象外、受容済みriskを同じ失敗状態として扱わない。
- release可否と、1.0へ向けて閉じる品質課題を別の時間軸で表現する。

## VerificationとValidation

Verificationは、具体化された要求と公開契約を製品が満たすかを、Test as Specification、build、文書検査、
benchmark、静的・動的検査などで確認する。

Validationは、その要求の組み合わせが、競技プログラミングと一般Swift開発の双方へ、C/C++級性能を持つ
データ構造を提供するというコンセプトに本当に適合するかを、代表的利用scenario、実利用、比較対象との測定、
利用者視点から確認する。

Verificationに成功しても、比較対象が狭い、一般利用の導入経路がない、競技用途の制約に耐えない場合は
Validationを満たさない。Validationで要求の不足が分かった場合は、testへ直接継ぎ足す前に上位要求へ戻す。

## 既存資産を洗練するための横断的な手がかり

1. 各moduleの品質評価を、Q-01〜Q-07のどの要求を扱うかで再接続する。
2. Test as Specificationを、要求を網羅した証拠と、まだ仕様化されていない領域へ分類する。
3. performance資料を、回帰、競合比較、原因分析、利用者向け主張へ分ける。
4. DocC、利用者向け文書、コード例を、対応する公開契約とtestへ接続する。
5. CIのjobを品質要求そのものとせず、どの要求に対するどの範囲の証拠かを明示する。
6. release工程を、上位品質要求を新設する場所ではなく、既存要求の適合と残余riskを判断する場所にする。

## 不足仕様候補

- C、C++標準、同等実装のどれを、各データ構造・操作の比較対象とするか。
- 「匹敵」を評価する規模、workload、時間・memory上の観点。
- 競技プログラミングで想定するSwift環境と、一般Swift開発で保証する環境。
- 公開契約、事前条件、`-Ounchecked`、View寿命、Sendableの責任境界。
- 一般利用者へ保証するAPI安定性と、0.xで許容する変更範囲。
- module別品質評価を製品全体の適合判断へ集約する方法。
- 代表的なValidation scenarioと、誰が何をもって用途適合と判断するか。

## このドラフトで確定しないこと

品質特性の優先順位、定量閾値、対応platform、個別API契約、release可否、CI構成、工程表は確定しない。
既存のtest、評価、文書、benchmarkを品質要求そのものへ昇格せず、要求を支える証拠と改善資産として扱う。
