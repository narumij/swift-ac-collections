## 抽出した願い

以下は入力本文の目的・期待を要約したものである。

| 願い | 入力の根拠 | V2での置き方 |
| --- | --- | --- |
| 相談し、一緒に考えられる相手であってほしい | Receiverは思考の相手でもあり、相談・探索・振り返りを早々に仕事へ変換しない | 冒頭の「目指す協働」と、相談には依頼記録を要求しない取り決め |
| ユーザーと各AIが、それぞれの力を使えること | 役割は上下関係ではない。認められた目的の達成方法はCodexが選べる | 役割表、自律的な方法判断、許可の不要な取り直しを避ける記述 |
| ユーザーへ管理の手間を押し戻さないこと | 内部記録はAIが扱い、ユーザーには本当に必要な判断や許可を返す | 冒頭、内部作業領域、委任・相談・報告の責任 |
| 権威や合意ではなく、確かめられるものに支えられること | 称号や合意は正しさの証拠ではなく、助言も検証する | 原案の「その問いに答えられるものへ先に当たる」と、証拠の範囲による確定 |

| 管理が実際の仕事を助けること | 管理体系の維持自体を目的にせず、実際の負荷と失敗から育てる | 一仕事一記録から始め、必要に応じてユーザーと管理の仕組みを育てる |

願いごとに新しい承認や報告の手順を増やすことはしていない。本文の冒頭に方向を置き、必要な具体策を制度の各節へまとめた。

## 抽出した制度

| 制度 | V2へ取り込んだ内容 |
| --- | --- |
| 適用範囲 | ユーザーが選ぶ別プロジェクトのWorker／Receiver協働。入力の`swift-ac-collections`への非適用条件を保持 |
| 役割と入口 | 状態変更前に役割を確認し、役割別bootstrap、Workerの作業依頼、Receiverの受入の取り決めを読む。未指定や混在を称号・能力で補わない |
| ユーザーの留保権限 | 目的、優先順位、公開上の約束、リスク受容、役割境界、継続的な管理設計 |
| 作業ごとの取り決め | Receiverが実行前に仕事を短い依頼記録へ整理。Workerは範囲内で実施し、結果と証拠を返す |
| 操作の許可 | 計画への記載と許可を区別し、操作・対象とプロジェクトの許可規則に従う |
| 正本 | 決定・依頼記録・規則・状態ごとに一つ。説明や複製が別の決定を持たない |
| 内部作業領域と例外 | `Maintanance/`はAIの内部作業領域。`Maintanance/User/`は対象・操作を明示した依頼が必要。綴りは入力のまま保持 |
| 委任と返却 | 入口・資料・範囲・返却先を明らかにし、Receiverが返却を証拠と照合して統合する |
| 経験者への相談 | ユーザーが選んだ相手も助言者として扱う。問いの整理と助言の検証はReceiverが行う |
| Xcodeでの条件付き受渡し | 内部の返却経路が使えない場合はファイルで受け渡す。ユーザーは環境上必要な会話間の伝達を担い、管理・検証はReceiverが担う |
| 管理の成長 | 委任範囲内の可逆な整理はReceiverが進め、継続的な管理構造は実際の負荷を根拠にユーザーと設計する |

これらは、今回の入力が明示している具体的な取り決めとして取り込んだ。一般的な判断原理から、Worker／Receiverという役割や特定のディレクトリ名が導かれるとしたものではない。

## 原案との統合で調整した点

1. **判断原理と制度を分けた。** 冒頭に目指す協働、次に需要と三つの軸、その後に具体的な制度を置いた。原案の四つの問い、俯瞰、必要な範囲での検証を骨格として残した。
2. **contractを「依頼記録」と表現した。** 実行前に目的・範囲・権限・成果と確認方法を整理する、という入力の要求を残した。明確な依頼や許可をもう一度承認してもらう手続きにはしていない。
3. **停止する範囲を明確にした。** 入力の「範囲拡張・新たな方針・検証経路がない場合は停止」を、判断に依存する操作の停止と、証拠のない主張の確定保留に分けた。権限が明らかな独立作業は進められるという原案の性質を保った。
4. **介入は影響と現在の委任を確認する契機として扱った。** ユーザーの直接編集も含めて影響する操作を止めるが、無関係な仕事まで一律に停止する条件にはしていない。
5. **操作の記載と、既に与えられた許可を区別した。** 計画だけでは許可を作れない。一方、明示された許可を範囲内で使うための再承認は求めない。
6. **受入と変更権限の返還を混同しなかった。** 原案の「成果を引き渡し、変更権限を返した後」という条件を保持した。単なる報告や受入だけで変更権限が消える規定にはしていない。
7. **過去の制度を推測で補わなかった。** 旧Prime中心の体制、Registry先行、固定の採番状態、commitの都度許可、外部操作をすべてユーザーに限定する規則は持ち込んでいない。今回の入力にある役割・領域・許可規則を明示的な候補として組み合わせた。
