# 製品品質要求 独立ドラフト（同抽象度の再作成） — Claude

`RELEASE-074`の再作成版。上位入力は`CONCEPT_DEFINITION.md`だけとし、指定された他の品質要求fileは読んでいない。
性能閾値、CI job、停止条件、工程表、実装案には進まない。

## 1. コンセプトの分解

> CやC++標準に匹敵する性能をもつ、競技プログラミングで利用可能なデータ構造を、一般のSwift開発にも提供する。

この一文には、品質の約束が四つ含まれていると読む。

| 記号 | コンセプトの句 | 含意 |
|---|---|---|
| C1 | 「データ構造を」 | 利用者は、コレクションとして正しく振る舞うことを当然の前提にする |
| C2 | 「CやC++標準に匹敵する性能」 | 比較の基準が外部（C/C++標準）にあり、自己比較だけでは約束を満たせない |
| C3 | 「競技プログラミングで利用可能な」 | C++を前提とした発想で書け、限られた時間と環境で信頼して使える |
| C4 | 「一般のSwift開発にも提供する」 | 競技以外のSwift利用者が、Swiftの通常の期待（安全性、値semantics、依存のしやすさ）のまま使える |

C2とC4には緊張関係がある。C/C++並みの性能のために低レベルの実装を選ぶほど、Swiftの通常の期待を守る責任が
ライブラリ側に移る。下の要求の多くは、この緊張を製品として引き受けるためにある。

## 2. 上位品質要求

ISO/IEC 25010:2023の特性名は対応の目安として添えるだけで、全特性は採用しない。対応しない特性は§5に理由を書く。

### QR-1 正しさ：データ構造として、宣言した意味どおりに振る舞う

- 必要な理由: 正しくないデータ構造は、性能や使いやすさに関係なく使えない。競技では誤答の原因を利用者側で切り分けにくい。
- 接続するコンセプト: C1、C3（C++の対応物と同じ結果を期待される）。
- 25010の目安: 機能適合性（機能正確性、機能完全性）。
- 既存資産との接続:
  - Test as Specification（`Sources/RedBlackTreeCollections/Documentation/Quality-Checklist.md`の方針、
    各moduleの番号付き仕様test）が、宣言した意味の実行可能な正本になっている。
  - `CppBehaviorReferenceTests`がC++標準との振る舞いの一致を確かめており、C3側の「同じ結果」の証拠になる。
- 洗練の手がかり: 仕様testは「何を宣言しているか」の正本だが、製品全体で「どの公開APIに仕様testがあるか」を
  横断して見る手段はmodule別に分かれている。C++比較は赤黒木系に偏っている（Permutationは`next_permutation`相当の比較がtest内コメントにとどまる）。

### QR-2 性能：計算量と実測の両方で、C/C++標準に匹敵する

- 必要な理由: コンセプトが名指しする約束そのもの。競技では実行時間制限に直結する。
- 接続するコンセプト: C2、C3。
- 25010の目安: 性能効率性（時間効率性、資源効率性）。
- 既存資産との接続:
  - 公開コメントの`Complexity`記述が計算量の宣言になっている。
  - `Benchmarks/`のC++標準（`std::set`等）との比較結果が、外部基準との実測の証拠になっている。
  - CIのbenchmark相対比較が、自己比較での劣化を見張っている。
  - `PERFORMANCE_REGRESSION_*`の分析文書が、計測ノイズ（コード配置）の扱いの知見を持っている。
- 洗練の手がかり: 自己比較（劣化していないか）と外部比較（匹敵しているか）は別の問いで、C2が直接求めるのは後者。
  外部比較の証拠は一部の型・一時点にとどまる。計算量の宣言と実装・実測の一致を確かめる経路は明示されていない。

### QR-3 安全性：性能のための実装が、Swift利用者の安全と値semanticsを損なわない

- 必要な理由: C4の利用者は、Swiftの標準コレクションと同じ安全性（メモリ安全、値semantics、Index無効化の検出）を
  前提に書く。C2のための低レベル実装は、その前提を破る危険を内部に抱える。
- 接続するコンセプト: C2とC4の緊張点、C1。
- 25010の目安: 信頼性（無欠陥性、障害許容性）、安全性。
- 既存資産との接続:
  - Quality-Checklistの「raw memory、payload、Indexの寿命」の品質方針と、その仕様test。
  - 値semanticsの仕様test（例: iterator copyの独立性。Swift 6.4での最適化事象への回帰testを含む）。
  - Death test、Address Sanitizer、各moduleの品質評価の信頼性・安全性の節。
- 洗練の手がかり: 「どの最適化構成（Debug／Release／`-Ounchecked`）で、どの安全性を約束するか」が製品全体で
  一つに言語化されていない。module別評価と赤黒木の方針に分かれている。

### QR-4 理解しやすさ：C++経験者とSwift開発者の双方が、APIの意味と制約を正しく読み取れる

- 必要な理由: C3の利用者はC++の名前と発想で探し、C4の利用者はSwiftの慣習で読む。どちらかに誤読されると、
  正しい実装でも誤用が起きる。
- 接続するコンセプト: C3、C4。
- 25010の目安: インタラクション能力（認識性、学習性、ユーザーエラー防止）。
- 既存資産との接続:
  - DocC（`RedBlackTreeCollections.docc`、`AcCollections.docc`）と公開コメント、README、`Documentation/`の互換性文書。
  - 各moduleの品質評価の「ユーザードキュメント作業で説明すべき事項」。
  - コードスニペット候補の調査（`DOC-019`／`DOC-020`）。
- 洗練の手がかり: 公開文書の記述やコード例が、仕様testや現行APIとずれても検出されない（2026-10-10に型コメントの
  例がコンパイルできない状態で見つかった）。文書は仕様testから導かれる、という関係が明示されていない。

### QR-5 導入しやすさ：一般のSwiftプロジェクトが、安心して依存できる

- 必要な理由: C4の「提供する」は、利用者のプロジェクトへ組み込めて初めて成り立つ。依存先として、対応環境、
  公開面の範囲、変更の予告が読めないと採用できない。
- 接続するコンセプト: C4（C3では、ジャッジ環境での利用可能性として現れる）。
- 25010の目安: 互換性（共存性、相互運用性）、柔軟性（適応性、設置性）。
- 既存資産との接続:
  - Package構成と再export（`AcCollections`）、package trait、AtCoder 2025用のbranch運用。
  - READMEのアンダースコア付き宣言の方針（公開面の範囲の宣言）、branch運用方針。
  - CHANGELOG、release checklist。
- 洗練の手がかり: 「どの環境・どのSwiftで使えると約束するか」「公開面のどこまでを安定と見なすか」が、
  0.5.xの実験段階として明示的に言語化されていない。

### QR-6 持続性：正しさと性能を両立したまま、変更を続けられる

- 必要な理由: C2を守る実装は壊れやすく、C1・QR-3との両立は一度達成すれば終わりではない。変更のたびに
  両立を確認できなければ、コンセプトはreleaseを重ねるうちに崩れる。
- 接続するコンセプト: C1、C2の継続的な成立。
- 25010の目安: 保守性（試験性、解析性、修正性）。
- 既存資産との接続:
  - Test as Specificationそのもの（変更時に何が守られるべきかを示す）。
  - CI（Debug／Release test、性能の相対比較、Sanitizer）、`Tests/TESTING.md`の観点管理、release checklist。
- 洗練の手がかり: 保守性は独立した品質目標ではなく、QR-1〜QR-3を維持するための手段として扱う
  （Quality-Checklistの方針と同じ立場）。

## 3. VerificationとValidation

| 要求 | Verification（宣言どおり作られたか） | Validation（コンセプトの用途に合うか） |
|---|---|---|
| QR-1 | 仕様testが通る。C++比較testが一致する | 競技で実際に正答に使える（実提出など） |
| QR-2 | 計算量の宣言と実装が一致する。自己比較で劣化がない | 同じworkloadのC/C++標準と比べて「匹敵」と言える |
| QR-3 | 安全性の仕様test、Death test、Sanitizerが通る | Swift利用者が、標準コレクションと同じ前提で書いて事故が起きない |
| QR-4 | 公開文書が仕様testと現行APIに一致する | 利用者が文書だけで正しく使える |
| QR-5 | 宣言した構成でbuildとtestが通る | 外部プロジェクトが依存して、困らずに使える |
| QR-6 | 変更ごとにQR-1〜QR-3の検証が回る | releaseを重ねてもコンセプトが崩れていない |

既存資産は主にVerificationの側にある。Validationの証拠は散発的（C++との実測図、AtCoderでの実提出の予定など）にしかない。
これは不足仕様（§4）の主要な出どころになる。

## 4. 不足仕様の候補

確定はしない。ユーザー判断が要るものは1問ずつに分けた。

- **G-1**（QR-2）「匹敵する」を何と比べて判定するか。比較対象、workload、どの型に求めるか。
- **G-2**（QR-2）計算量の宣言と実装の一致を、何を証拠に受け入れるか。
- **G-3**（QR-3）安全性の約束を、最適化構成（Debug／Release／`-Ounchecked`）ごとにどう言い分けるか。
- **G-4**（QR-4）公開文書と仕様testの関係（文書の記述やコード例は仕様testに裏付けられるべきか）。
- **G-5**（QR-5）0.5.xで約束する対応環境と、公開面の安定性の範囲。
- **G-6**（QR-1／QR-2）赤黒木以外の型（Permutation、BareArray、OptionalArray）にも、C/C++比較という外部基準を求めるか。
- **G-7**（全体）Validationの証拠を、製品として定期的に得る経路を持つか。

## 5. 25010の特性のうち、上位要求に立てなかったもの

- セキュリティ: 外部入力や権限を扱わないデータ構造ライブラリなので、独立した要求にしない。
  メモリ安全の面はQR-3に含める。
- 互換性のうち他製品との共存: 標準ライブラリやswift-collectionsとの共存はQR-5に含める程度で、独立させない。
- 利用時の品質（効果性、満足性など）: 製品要求としては、Validationの観点（§3）で扱う。
