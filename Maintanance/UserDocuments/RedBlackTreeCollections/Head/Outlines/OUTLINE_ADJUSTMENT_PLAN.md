# 赤黒木4型のアウトライン調整プラン

2026-10-16 / 作成：Astra。ユーザー依頼による計画案。
恒久task **DOC-030（文書整備）** の準備資料とする。状態・個別の実行割当はTask Registryで扱う。本書の作成はアウトラインの確定、調整の実施、本文作成開始を意味しない。

## 目的と現在地

4型の利用者向け文書を、現行の公開契約に沿って過不足なく書けるアウトラインに整える。全型を同じ長さ・同じ項目数に揃えることは目的にしない。

現在は[Astraの通読所見](ASTRA_OUTLINE_READING_NOTES_2026-10-16.md)まで。実装・テストとの照合は未実施。
[文書作成手順](../../../../Current/DOCUMENTATION_WORKFLOW.md)に従い、構成と必須事項はユーザーの判断を尊重し、技術的事実は実物で確かめる。本文作成準備の到達点は[文書マイルストーン](../../../../Current/DOCUMENTATION_MILESTONES.md#redblacktree文書の本文作成完了旧rbt-014)へ接続する。

## 進め方

### 1. 4型を横断して説明項目を比較する

概要、生成と容量、検索、更新・削除、合成・変換、走査、Index・Bound・View、所有とCoW、性能、利用上の制約について、各型の記載場所を対応づける。

各項目を「記載あり」「別節で扱う」「その型には非該当」「不足の可能性」に分ける。項目差だけで追加を決めず、対象の公開APIと利用者の疑問に照らす。

Setでは生成・容量、走査、範囲Viewの扱いを重点確認する。他型の節をそのままコピーするのではなく、Setで説明が必要な内容を特定する。

### 2. 共通契約を照合し、型ごとの違いを確認する

公開宣言、API Matrix、設計資料、Test as Specificationを問いに応じて参照する。実装一般論や過去アンケートの合意だけで確定しない。

| 対象 | 主な照合点 |
| --- | --- |
| 共通 | Indexの有効性・削除・slot再利用、CoW分岐後の扱い、無関係なIndex、Boundの解決不能・逆順範囲、Viewと所有、並行利用の説明範囲 |
| Set | 初期化・容量と走査の説明範囲、一意性、集合演算、範囲View |
| Dictionary | 重複キーを含む初期化、default subscriptの読み取りと更新、値更新、結合クロージャの引数順、keys・values |
| MultiSet | 同値要素の保持と更新、多重度演算、単一削除と複数削除、hintの挙動 |
| MultiMap | 同一キー内の順序とhint、mapped values viewを取り出した場合の値semantics、直接更新との違い、key-value range viewとの区別 |

性能の説明は、計測値と計算量を分ける。CoWの有無、探索済みIndex、比較・要素操作のコスト、償却の対象など成立条件を確認する。Combining APIの調査結果は実在と対象版を確かめてから接続し、見つからなければ未確認として残す。

RBT-026のMapped Values View契約再検討が関係する場合、現行仕様の説明と将来の変更判断を分ける。この調整で採否を先取りしない。文書作成に影響する範囲だけを明示する。

### 3. 必須コード例を割り当てる

[過去のスニペットアンケート](../../../SnippetSurvey/README.md)から、現行APIでも役立つ利用者の疑問を拾う。旧コードや旧順位をそのまま引き継がない。

各「コード例必須」の節について、例で示す操作と観察する結果を一行で具体化する。境界式、重複の扱い、逐次削除、default subscript、Viewの取り出しと直接更新など、文章だけでは誤解しやすい点を優先する。共通例で足りるものと型固有の例を分け、同じ説明を不必要に増やさない。

この段階で全例の完成を必須にしない。APIや挙動が不確かな例は最小のコンパイル・実行で確かめる。本文作成時には掲載する全例を対象条件で検証する。

### 4. 調整案をまとめ、アウトラインへ反映する

差分を「根拠のある技術訂正」「説明の欠落候補」「構成・例示の提案」に分け、変更理由と根拠を残す。ユーザー判断が必要な構成・必須事項は4型分をまとめて示し、細かな問いを繰り返さない。

既存の優先方針（初心者向けへの簡略化より対象型を過不足なく説明する）を維持する。確認済みの範囲でアウトラインを更新し、未決点を確定表現へ混ぜない。

### 5. 最後に4型を横断確認する

用語、共通契約、計算量の前提、コード例の役割を比較する。差異に理由があること、型固有の性質が共通説明で消えていないことを確認する。影響する箇所だけ再検証し、全文レビューを理由なく反復しない。

## 本文へ渡す成果

- 調整済みの4型アウトライン。
- 変更理由と技術的根拠。未確認事項は影響する節と解消条件を付ける。
- 各必須例で示す振る舞いと、実施した検証の結果。
- 構成・必須事項についてのユーザー判断の記録。

本文作成へ渡せるかは節ごとの未決点を見て判断する。契約や必須構成が未確定の箇所は保留を明示し、確定済みの部分まで一律に止めない。アウトラインの確認を、公開初版の完成・利用理解Validation・製品品質の合格とは扱わない。
