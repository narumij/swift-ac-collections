# RedBlackTreeCollections 品質観点とチェックリスト

## この文書の目的

この文書は、RedBlackTreeCollectionsで重点的に実現・維持する品質と、その確認方法を定義する。

品質の分類にはISO/IEC 25010:2023の製品品質モデルを参照する。ただし、この文書は規格への適合や認証を宣言するものではない。ISO/IEC 25010:2023は品質特性を整理する参照モデルであり、個別製品の合格値を規定しないため、本ライブラリの目的と利用条件に合わせて評価対象と判定基準を定める。

参考:

- [ISO/IEC 25010:2023 Product quality model](https://www.iso.org/standard/78176.html)
- [ISO/IEC 25023:2016 Measurement of system and software product quality](https://www.iso.org/standard/35747.html)
- [ISO/IEC 25040:2024 Quality evaluation framework](https://www.iso.org/standard/83467.html)

## 品質方針

RedBlackTreeCollectionsは、次の性質を自動化された再現可能な評価によって保証することを目標とする。

- 公開された操作契約に従って正しい結果を返す。
- 赤黒木に期待される計算量を維持する。
- Swiftの値型としてCopy on Writeによる値セマンティクスを維持する。
- raw memory、payload、およびIndexの寿命を設計上の契約に従って管理する。
- 内部実装を変更したとき、契約違反や性能回帰を検出できる。

対象品質は、実装とテストによって客観的に確認できる範囲へ絞る。

| 優先度 | ISO/IEC 25010:2023の品質特性 | 本ライブラリで扱う品質 |
| --- | --- | --- |
| A | 機能適合性 | 集合・辞書操作、順序、重複、範囲、Index、および値セマンティクスの正しさ |
| A | 性能効率性 | 操作の計算量、実行時間、メモリ使用量、確保回数、およびCopy on Writeの発生条件 |
| A | 保守性 | 不変条件、責務境界、テスト容易性、変更影響の検出、および構成差の検証 |
| 横断 | 信頼性・セキュリティに寄与する性質 | メモリ、所有権、payload、およびIndex寿命の健全性 |

## 1. 機能適合性

### 品質要求

- `RedBlackTreeSet` と `RedBlackTreeDictionary` はキーを一意に保持する。
- `RedBlackTreeMultiSet` と `RedBlackTreeMultiMap` は重複キーを契約どおり保持する。
- 全要素の順方向・逆方向走査結果は比較順と一致する。
- `find`、`lowerBound`、`upperBound`、`equalRange`などの検索結果は参照モデルと一致する。
- 挿入、削除、範囲削除後も、root、色、black height、親子リンクなどの赤黒木不変条件が成立する。
- コピー後に一方を変更しても、もう一方の論理的な値は変化しない。
- 削除済み、再利用済み、別の木に由来するIndexを、有効なIndexとして誤認しない。
- 空、単一要素、重複要素、最小・最大位置、および全範囲削除を正しく扱う。

### 確認方法

- 公開APIの決定論的な単体テスト
- Swift標準コンテナとソート済み配列などを用いた参照モデルとの比較
- seedを記録したランダム操作列またはプロパティテスト
- Debug構成での `TREE_INVARIANT_CHECKS`
- Indexの削除、再利用、木の相違、およびCoWを対象とする異常系テスト
- 実際のAtCoder問題を用いた利用例の回帰テスト

### 合格基準

- 有効化された決定論的テストがすべて成功する。
- 対象とするランダム操作列で参照モデルとの不一致が0件である。
- 検査対象とする変更操作後の赤黒木不変条件違反が0件である。
- サポートする公開APIに、正常系、境界値、および該当する契約違反のテストが存在する。

## 2. 性能効率性

### 計算量要求

| 操作 | 目標計算量 | 備考 |
| --- | ---: | --- |
| 検索 | O(log N) | `find`、`lowerBound`、`upperBound`など |
| 挿入 | O(log N) | ストレージ拡張に伴う償却コストを除く |
| 単一要素の削除 | O(log N) | 探索を含む場合 |
| 独自のIndex範囲式の生成 | O(1) | 同一ツリー性の確認のみ |
| K要素の順方向・逆方向走査 | O(K) | 各反復でO(log N)の端点比較を行わない |
| Copy on Write | O(N) | ストレージ分離と再配置を含む |

### 測定対象

- 代表的な入力分布における検索、挿入、削除、および走査時間
- 要素数の増加に対する実行時間の増加傾向
- 1要素あたりのメモリ量とbucketの確保量
- 連続挿入時のallocation回数
- 削除済みslotの再利用状況
- 一意なストレージを変更するときの不要なCopy on Writeまたはallocation
- 前回の基準版に対する性能変化

### 測定上の注意

- Debug構成の不変条件検査を性能値へ混在させない。
- Release構成で同一マシン、同一Swift toolchain、同一trait、および同一入力を使用する。
- warm-up後に複数回測定し、原則として中央値を比較する。
- 絶対時間だけでなく、要素数を増やしたときの傾向から計算量の退行を確認する。
- CI環境の揺らぎを考慮し、警告値と失敗値を別に設定する。

### 合格基準

- 計算量試験で、対象操作に期待される増加傾向からの明確な退行がない。
- 基準ベンチマークに対する許容回帰率を、測定環境とともに別途記録する。
- 性能を理由とする実装変更には、対象ワークロードと変更前後の測定結果がある。
- メモリレイアウトまたはallocatorの変更には、確保量、alignment、およびallocation回数の確認がある。

固定の許容回帰率は、安定したベンチマーク環境と基準値を用意してから設定する。環境を固定せずに単発の実行時間だけで合否を判定しない。

## 3. 保守性

### 品質要求

- allocator、node storage、tree algorithm、Index、およびpublic containerの責務境界が説明されている。
- 重要な内部不変条件に対応する検査またはテストがある。
- raw pointerを扱うコードには、所有者、初期化状態、および有効期間の前提がある。
- メモリレイアウトの変更時に再検証すべき項目が文書化されている。
- 公開APIとunderscored declarationの互換性方針が区別されている。
- build configurationやSwiftPM traitによる重要な動作差を検証できる。
- 性能最適化には、成立条件と回帰を検出する方法が記録されている。

### 確認方法

- 設計文書と実装の責務が一致しているかをレビューする。
- 不変条件をDebug assertionだけでなく、可能な範囲でテストからも確認する。
- 変更箇所に対応する正常系、境界値、異常系、および回帰テストを追加する。
- サポート対象のSwift toolchainと主要trait構成でbuildまたはtestを実行する。
- deprecated APIと互換APIを本体APIから区別する。

### 合格基準

- 変更した契約または不変条件に対応する文書とテストが更新されている。
- 通常のDebug構成とRelease構成でbuildが成功する。
- 対象とする構成のテストがすべて成功する。
- unsafeな実装変更について、所有権、初期化、破棄、alignment、およびIndex寿命への影響が確認されている。

## 4. 横断要件: メモリ・所有権・Index寿命

メモリ安全性は単一の品質特性として広く宣言せず、機能適合性、信頼性、保守性、およびセキュリティへの寄与を持つ横断要件として扱う。

### 維持する不変条件

- raw pointerを所有バッファの有効期間外でdereferenceしない。
- 未初期化のnodeまたはpayloadを読み出し、破棄しない。
- payloadは構築と破棄が一度ずつ対応する。
- recycleされたslotでは世代を更新し、古いIndexを拒否する。
- 別の木に由来するIndexを通常の操作経路で解決しない。
- CoW前後のストレージおよびIndexの所属を混同しない。
- tied bufferへの所有権移行後に、木とtied bufferの双方から同じ領域を解放しない。
- alignmentとstrideの算出は、同じ領域に配置するすべての型の要件を満たす。

### 確認方法

- Address Sanitizerなど利用可能なSanitizerで対象テストを実行する。
- allocationとdeallocation、およびpayloadのinit/deinit回数を検査する。
- 削除と再挿入を繰り返し、同一アドレスの再利用を含む試験を行う。
- 木よりIndexが長生きする場合を試験する。
- Copy on Writeの前後でコピー元とコピー先のIndexを混用する異常系を試験する。
- alignmentがnodeより小さい、等しい、大きいpayloadを試験する。
- capacity 0、1、および複数bucketの境界を試験する。

### 合格基準

- 対象Sanitizerによるメモリ違反が0件である。
- use-after-free、二重解放、未初期化アクセス、および不正なpayload破棄を再現する既知の回帰がない。
- 無効なIndexは契約に従って拒否され、確保領域外アクセスへ進まない。

## 5. 現時点で包括的な保証対象としない品質

次の特性を無視するわけではないが、現時点ではライブラリ全体の包括的な適合を主張しない。

### Compatibility

Swift toolchain、OS、およびAtCoder実行環境との互換性は、サポート対象を明示した上で個別に確認する。すべてのSwiftまたはすべてのplatformとの互換性は保証しない。

### Interaction capability

本製品はUIを持たないライブラリであるため、主要な評価対象にしない。APIの理解可能性は保守性およびdocumentationの観点で扱う。

### Security

脅威モデル、攻撃者モデル、およびセキュリティ評価を定義していないため、包括的なセキュリティ適合を主張しない。メモリ破壊を防ぐ設計と検査はセキュリティにも寄与するが、それだけでセキュリティ全体を保証しない。

### Safety

ISO/IEC 25010:2023におけるSafetyは、人、財産、または環境への危害を含む。本ライブラリの通常用途では、その意味でのSafetyを主要な評価対象にしない。

### Reliability

ライブラリ単体では可用性や障害復旧を包括的に評価しにくいため、正常な利用での故障防止、状態破壊の防止、および不正なメモリアクセスの防止に範囲を限定する。

### Flexibility

SwiftPM traitやtoolchainへの適応性は個別に確認する。ただし、中核3特性の品質ゲートが安定するまでは主要な品質目標にしない。

## 6. 変更時の品質チェックリスト

### すべての変更

- [ ] 変更対象となる公開契約または内部不変条件を特定した。
- [ ] 既存テストがすべて成功した。
- [ ] 変更に対応するテストを追加または更新した。
- [ ] Debug構成とRelease構成でbuildできた。
- [ ] 公開API、互換性、およびdocumentationへの影響を確認した。

### 木構造または検索アルゴリズムの変更

- [ ] 挿入と削除後の赤黒木不変条件を確認した。
- [ ] 空、単一要素、最小位置、最大位置、およびroot変更を確認した。
- [ ] 参照モデルと検索・走査結果を比較した。
- [ ] 計算量の退行がないことを確認した。

### node storageまたはallocatorの変更

- [ ] allocation byte countとalignmentを確認した。
- [ ] capacity 0、1、および複数bucketを確認した。
- [ ] nodeとpayloadの初期化・破棄が一度ずつ対応することを確認した。
- [ ] Fresh PoolとRecycle Poolの双方を確認した。
- [ ] accessor、traverser、iterator、およびdeinitializerが同じslot計算を使うことを確認した。
- [ ] Sanitizer対象テストを実行した。

### Index、削除、またはCopy on Writeの変更

- [ ] 削除済みIndexが拒否されることを確認した。
- [ ] recycle後に古いIndexが新しいnodeを指さないことを確認した。
- [ ] 別の木に由来するIndexが拒否されることを確認した。
- [ ] 木よりIndexが長生きする場合を確認した。
- [ ] CoW後にコピー元とコピー先の値が独立していることを確認した。
- [ ] CoW前のIndexとコピー後の木を混同しないことを確認した。

### 性能に影響する変更

- [ ] 対象ワークロードと測定環境を記録した。
- [ ] 変更前後を同一条件で複数回測定した。
- [ ] 実行時間だけでなくallocationとメモリ量への影響を確認した。
- [ ] 性能改善のために機能契約またはメモリ安全性を弱めていない。

## 7. リリース品質ゲート

リリース候補は、少なくとも次を満たす。

1. サポート対象構成の全テストが成功する。
2. 参照モデルを用いたランダム操作列で不一致がない。
3. 赤黒木不変条件の違反がない。
4. 対象Sanitizerでメモリ違反がない。
5. 記録された基準に対して許容範囲を超える性能回帰がない。
6. 公開APIまたは契約の変更がdocumentationとリリース情報へ反映されている。

品質ゲートを満たさない場合は、例外として黙認せず、未達項目、影響範囲、回避策、および解消条件を記録する。
