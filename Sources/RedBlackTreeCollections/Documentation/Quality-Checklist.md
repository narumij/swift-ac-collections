# RedBlackTreeCollectionsの品質方針

## 目的

この文書は、RedBlackTreeCollectionsで優先して守る品質を定める。

品質の分類にはISO/IEC 25010:2023を参考として用いるが、規格への適合や認証は目的としない。品質管理そのものを重くせず、このライブラリの用途に対して影響の大きい項目だけを扱う。

## 重視する品質

次の三つに絞る。

1. コレクションとして正しく動作すること
2. raw memory、payload、およびIndexの寿命を壊さないこと
3. 赤黒木を採用する目的を損なう性能退行がないこと

保守性、互換性、セキュリティなどを独立した品質目標として網羅的に評価しない。必要になった場合は、上の三つを維持するための手段または個別の要求として扱う。

## Test as Specification

外部または内部から観察可能な品質要求について、実行可能な正本はテストとする。

テスト名は、可能な限り実装の手順ではなく、満たすべき性質を表す。テスト一覧を読むことで、ライブラリが何を保証しようとしているか分かる状態を目指す。

例:

- 挿入後も全要素が比較順に走査される
- コピー後の変更はコピー元の値を変更しない
- 削除されたIndexは同じslotが再利用されても無効のままである
- CoWで分岐したコレクションでも、有効なIndexから対応する要素を特定できる
- 再利用前のIndexは、CoW後の木でも世代不一致として拒否される

品質要求とテストの対応表は原則として別に管理しない。仕様を追加または変更するときは、その性質を表すテストを追加または変更する。

設計文書は、テストだけでは表現しにくい前提、所有権、計算量、採用理由、および実装上の制約を説明する。テストは、それらの設計から外部または内部で観察できる性質を検証する。

テストで直接表現できない設計上の要求については、設計文書を正とし、その要求から観察可能な性質がある場合はテストで補強する。

### 内部実装のTest as Specification

`Tests/RedBlackTreeTreeTests/Foundamental/`は、公開APIの仕様ではなく、`__tree`移植層が上位のストレージ実装から独立して満たす内部契約の実行可能な正本とする。ここで固定するのは関数の行単位の実装ではなく、次のような移植可能な性質である。

- root、end、nullptr、および親子リンクが赤黒木の不変条件を表現できること
- 挿入、削除、回転、および走査の後も順序と赤黒木の不変条件が保たれること
- uniqueでは同値キーを一つに保ち、multiでは同値キーを木上の位置で安定して区別できること
- 比較とkey取得をstaticな`Base`から注入する経路と、状態を持つインスタンスから注入する経路が、同じ探索契約を満たすこと
- nodeとpayloadの隣接配置が型ごとのalignmentとstrideを満たし、構築と破棄が一度ずつ対応すること
- nodeの再利用後はrecycle countによって古いsealを拒否できること
- 不正なポインタ操作やtracking tagを、通常の成功系テストとは分離したDeath Testで停止契約として検証できること

Fixtureはこれらの契約を観測するための参照実装であり、製品ストレージそのものを仕様にはしない。特にメモリレイアウト計算は、`UnsafeNode`に置いた参照計算と`RawBuffer`の実計算を別経路で照合し、poison済み領域の塗り分けによってnode、payload、padding、guard領域の重なりや範囲外書き込みがないことを確認する。双方が同じ式を共有して結果だけ一致するテストへ退行させない。

`__tree`を変更するときは、公開コレクションのテストだけでなく、この内部契約も確認する。逆に、LLVM由来の制御構造との一致を優先して到達不能な末尾などを残す場合、カバレッジ率だけを理由に製品コードを書き換えない。到達不能である根拠と目視確認の結果をテスト保守記録へ残す。

## 1. 動作の正しさ

次をテストで保証する。

- SetとDictionaryはキーを一意に保持する。
- MultiSetとMultiMapは重複キーを契約どおり保持する。
- 検索、挿入、削除、範囲操作、および走査の結果が正しい。
- 全要素の走査結果が比較順と一致する。
- 変更後も赤黒木の不変条件が成立する。
- コピー後の変更で値セマンティクスが壊れない。
- 空、単一要素、最小位置、最大位置などの境界を正しく扱う。

可能な操作は、Swift標準コンテナとソート済み配列などの単純な参照モデルと比較する。

ランダム操作列を品質ゲートに使用する場合は、失敗を再現できるseedを用いる。失敗時にはseed、または再現に必要な操作列を確認できるようにする。

## 2. メモリとIndex寿命

### 2.1 メモリとリソースの安全性

次をテストで保証する。

- 未初期化のnodeまたはpayloadを読み出し、破棄しない。
- payloadの構築と破棄が一度ずつ対応する。
- node、payload、およびbucketのalignmentとstrideを守る。
- 同じ領域を二重に解放しない。
- 解放済みのnode、payload、またはbucketへアクセスしない。

通常のテストに加えて、GitHub Actions上でSanitizerを用いた検証を行う。

対象とするSanitizer、toolchain、build configuration、および実行頻度はGitHub Actionsの設定を正とする。少なくともraw memory操作に関する違反を検出できるSanitizerを、定期的またはリリース前の品質ゲートとして実行する。

Sanitizerで検出された問題は、通常テストが成功していてもメモリとリソースの安全性に対する品質違反として扱う。

### 2.2 Indexの有効性と所属

Indexの有効性と所属に関する挙動は、`ALLOW_CROSS_TREE_INDEX` および `USE_LAZY_DETACH` の設定に依存する。

現在の標準構成では `ALLOW_CROSS_TREE_INDEX` を有効とし、`USE_LAZY_DETACH` は使用しない。`USE_LAZY_DETACH` はdeprecatedであり、通常の品質保証では標準構成を基準とする。

Copy on Writeによって分岐したコレクションは、Indexの所属判定上は別の木として扱う。

標準構成では、次をテストで保証する。

- 同じ木では、有効なIndexから対応する要素を特定できる。
- CoWで分岐した別の木でも、対応する要素と世代が有効である場合はIndexを利用できる。
- `ALLOW_CROSS_TREE_INDEX` は、CoWで分岐したコレクション間でのIndex利用を保証するために有効化する。
- 世代の異なるIndexは、同じ木・別の木を問わず拒否する。
- 同じストレージでは、削除されたIndexを有効な要素Indexとして扱わない。
- recycleされた同一slotを、古い世代のIndexが新しい要素として指さない。
- 要素を持つ木のCoWでは、Indexの有効性判定に必要なノード世代を引き継ぐ。
- CoWで分岐した別の木の変更は、対象木で引き続き有効なIndexを無効にしない。
- 木よりIndexが長生きしても、解放済み領域へアクセスしない。
- `endIndex` は境界位置として扱い、要素を指すIndexとは区別する。

無関係なコレクションから取得したIndexの使用は事前条件違反であり、その検出および動作は保証しない。

`ALLOW_CROSS_TREE_INDEX` および `USE_LAZY_DETACH` の組み合わせごとの詳細な有効性規則は、Indexの設計文書および対応するTest as Specificationを正とする。`ALLOW_CROSS_TREE_INDEX` が有効な構成で別の木のIndexを利用できる場合でも、それは無関係なコレクション間での利用を保証するものではない。

## 3. 性能退行の防止

赤黒木およびCopy on Writeを採用する目的を損なう性能退行を防止する。

次の計算量を設計上の契約とする。

| 操作 | 目標計算量 |
| --- | ---: |
| 検索 | O(log N) node comparisons |
| unique storageへの挿入 | O(log N) |
| unique storageからの単一要素の削除 | O(log N) |
| 独自のIndex範囲式の生成 | O(1) |
| K要素の走査 | O(K) node steps |
| コレクションの値コピー | O(1) |
| Copy on Writeによるstorage分離 | O(N) |

検索、挿入、および削除の計算量は木上の比較回数を基準とする。キー比較そのものの計算量がO(1)でない場合、実際の計算量にはその比較コストが加わる。

共有storageへの変更では、木操作に先立ってCopy on WriteによるO(N)のstorage分離が発生する場合がある。このコストと、その後のO(log N)の木操作は区別して扱う。

有限回の性能テストだけで計算量を証明できるとはみなさない。代表的な入力サイズを増やした測定により、明らかな計算量の退行を検出する。

実行時間は環境によって変動するため、すべての性能テストに厳密な合格値を設けない。次のような、比較的決定論的に確認できる性質を優先する。

- unique storageへの変更で不要なCopy on Writeが発生しない。
- コレクションの値コピーだけでは全要素のコピーを行わない。
- 削除済みslotが再利用される。
- K要素の走査で、各要素ごとのO(log N)探索を行わない。
- 意図しないallocation増加がない。
- hint等によって高速経路を選択できる操作では、その経路が不要な探索へ退行しない。

実時間の回帰判定を行う場合は、同一toolchain、同一build configuration、同一trait、同一入力、および同一程度の実行環境で複数回測定する。

性能テストの目的は特定環境での絶対時間を保証することではなく、設計上期待する計算量、allocation特性、および主要な高速経路からの明らかな退行を検出することとする。

## 1.0採用品質ゲート（凍結）

競技プログラミング用途だけでなく、言語または標準ライブラリに近い基盤コンポーネントとして
外部利用者が採用を判断できる品質へ仕上げる作業を、1.0向けの独立taskとして保持する。

このtaskはIndex契約の確定後、ユーザーが明示的に再開するまで着手しない。再開時には少なくとも
次を扱う。

- 公開契約、互換性方針、保証しない範囲を1.0の利用者向けに確定する。
- macOSを含むサポート環境とSwift toolchainの範囲を定め、そのリリースゲートをCIで再現可能にする。
- memory safety、Index、Copy on Write、計算量、性能退行について、既存の検証証拠を利用者が
  短く確認できる形にまとめる。
- dependency更新、GitHub Actions、脆弱性報告、release手順などの供給網・運用上の品質境界を定める。

最高水準を、機能数や無欠陥の宣言ではなく、重要な保証境界が明確で、その証拠と変更時の検証を
第三者が再確認できる状態として評価する。既存のテストや設計文書を重複して作り直さず、不足する
ゲートと利用者向けの提示だけを追加する。

## 最小品質ゲート

通常の変更では、変更範囲に応じて次を確認する。

1. 関連する仕様テストが成功する。
2. 挿入または削除を変更した場合、赤黒木の不変条件を確認する。
3. storage、Index、削除、またはCopy on Writeを変更した場合、寿命と所有権に関するテストを確認する。
4. hot pathまたはメモリレイアウトを変更した場合、性能とallocationへの影響を確認する。

リリース時には、少なくとも次を確認する。

1. サポート対象構成の全テストが成功する。
2. 参照モデルを用いる再現可能なランダムテストが成功する。
3. 赤黒木の不変条件違反がない。
4. 対象とするSanitizerでメモリ違反がない。
5. 既知の重大な性能退行がない。

## 対象範囲の注意

- 同一の木への並行アクセスはスレッドセーフではなく、必要な同期は利用側が行う。
- 同じストレージでは、削除後のIndexは無効であり、再利用できない。
- 空の木のCoWでは、不要な使用済みslotと世代履歴をコピーしない。
- 無関係なコレクションから取得したIndexの使用は事前条件違反であり、検出は保証しない。
- underscored declarationは公開されていても互換性保証の対象にしない。
- 主開発系では、開発時点の最新安定版Swiftだけをサポートする。過去のSwift toolchainとの互換性は原則として保証しない。
- 互換性を目的とするブランチでは、そのブランチで明示した環境だけを追加のサポート対象とする。
- 主な自動検証環境は、GitHub Actionsで使用するUbuntu環境とする。すべてのplatformおよびSwiftPM traitの組み合わせは保証しない。
- `-Ounchecked`など安全性を弱める構成は、通常の品質保証と区別する。
